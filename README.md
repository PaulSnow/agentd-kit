# agentd-kit

Version 1.0. `agentd` started as phase 1 of a supervisor inside [agentic-kit](https://github.com/PaulSnow/agentic-kit), a fork of Wolf McNally's agentic-coding-starter, and moved here to be its own product: a service for the whole machine that supervises sessions across many repositories, which does not fit a template that governs one repository. `agentd version` prints the version.

## agentd

`agentd` keeps unattended Claude Code sessions going and delivers their work. The deterministic management, watching, restarting, nudging, delivering and routing, runs in this program and runs the same way every time. A model is called in only for judgment, through escalation. It replaces the Python session supervisor in phases; this is phase 1: the event log, the session state machine and the supervisor's policies.

## Running

`agentd` needs Go 1.21 or newer and nothing else.

```bash
go build -o ~/.local/bin/agentd .
```

```bash
agentd run --shadow
```

```bash
agentd run
```

```bash
agentd status
```

`run` reads `~/.config/agentd-kit/agentd.json` (`--config` for another file), replays its event log, then passes over every configured session each `poll_interval`. `--shadow` observes everything and acts on nothing: each action is logged as a `would` event instead (a fetch, which writes nothing to the remote, is the one exception). `--once` makes one pass. `status` prints one row per session from the event log, for the latest run's mode or `--mode live|shadow`: every configured session, those with no events yet too, with why a delivery waits, the escalations given up on, and any action cut short. `config` prints the resolved configuration. `mark-delivered SESSION WORKTREE REF` records a delivery made before `agentd` took over, so it is never repeated. `clear SESSION` lifts a crash-looping session's park. Both write to the event log, and a running `run` reads what they wrote at its next pass. `inventory` lists every repository in the tracking system's manifest, with its open issues and requests and the machines holding a clone, from the tracking snapshot. `report --out PATH` writes `report.json` for the tracking site from the event log (see Publishing). `ui` serves the owner's web UI (see The owner's UI).

Slow work runs in workers, so it never holds up the pass over the other sessions: each delivery (its fetch, gate, pushes and forge calls) and each escalation command runs in a goroutine of its own, one per delivery or escalation at a time, and the next pass starts no second one while it runs. A worker works on a copy of its session's memory: it appends each event to the log as it happens and hands it to the loop, which applies it to the session at its next pass, so the session's state stays the loop's alone, and an outcome a worker logged survives a crash of `agentd` before the loop applied it. A worker appends and queues each event under one lock, so the loop applies them in the order the log holds them; the Questions and dialog escalations carry the episode they were made for, so one that settles after its dialog went away or its Questions closed settles nothing. A delivery that is held, or waiting out its backoff, starts no worker. A failed append stops that worker's job, not the pass. The next pass comes after `poll_interval`, or sooner when another process has appended an owner record to the log (`agentd clear`, `mark-delivered`), which `run` looks for every 15 seconds, so the owner's word is acted on within a minute; what a worker finished is in the log already and is applied at the next pass. `run --once` waits for its workers before it stops; a `run` told to stop waits up to a minute, and a job still running then is cut short, which the next start warns of.

`run` is meant to live in a tmux session of its own, under `nice -n 19`. Only one `run` may use an event log: it holds an exclusive lock on the log's path, with symlinks resolved, plus `.lock` (by default `~/.local/state/agentd-kit/events.jsonl.lock`), and a second `run` exits with an error naming that file.

## Configuration

The configuration is JSON, not the YAML the issue sketched: `agentd` is standard library first, and Go has no YAML parser in it. Features live in this repository; the owner's specifics live outside it, in the config file. [`agentd.example.json`](agentd.example.json) shows every field; unset fields take the defaults in `config.go`, which are the Python supervisor's numbers. Relative paths in the file are relative to the file's own directory, not to where `agentd` runs; `~` expands to the home directory, and `~user` is refused. Every session's `workdir` and `cwd` must exist when the configuration is loaded, so a path that resolved wrongly fails at start, naming the session. An escalation command given as a bare name is found on `PATH`. Paths given on the command line (`--config`, `--log`, the `mark-delivered` worktree) are relative to the working directory.

- `timeouts`: how long one external command may run: `tmux` (default `10s`) for each tmux call, `forge` (default `2m`) for each git, glab and gh call, `escalate` (default `2m`) for the escalation command. Each command runs in a process group of its own, and one still running at its timeout is killed with everything it started; its action fails with an `error` event and the pass goes on. git runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and empty `GIT_ASKPASS` and `SSH_ASKPASS`, so it fails rather than waiting for credentials. It also runs with `GIT_NO_REPLACE_OBJECTS=1`, `core.fsmonitor`, `core.untrackedCache` and hooks off and literal pathspecs, so the worktree's config cannot start a monitor or a hook in `agentd`'s environment or answer for files from a cache. Clean and smudge filters, `core.sshCommand` and a credential helper that the worktree's config names still run; that config is the session's to write.
- `confidential_patterns`: regular expressions, in Go's [RE2 syntax](https://pkg.go.dev/regexp/syntax) and case-sensitive unless they start with `(?i)`, for text `agentd` must never post. An escalation whose text matches one, including Questions copied from `STATUS.md` (screened whole, then cut to 2000 bytes on a UTF-8 boundary), is replaced by a generic message that names the session and says the details were withheld; a `skip` event with `filtered` records it, without the matched text, and the event log never holds the original. A `STATUS.md` first line that matches is logged as withheld. A merge request whose title or text matches is not delivered, and neither is a branch whose name, or any commit message in `origin/<target>..HEAD`, matches; these are screened before the branch is named anywhere. One skip and one escalation say so, without the text, and delivery waits until the text or the patterns change.
- `repositories`: each forge project `agentd` may write to, with its `forge` (`gitlab` or `github`), its `host` (default `gitlab.com` or `github.com`), the `transport` delivery pushes over (`ssh`, the default, or `https`), its `project` path, the `console` escalations go to, the `assignee` for opened requests, and its `policy` (see *Repository policy*): what delivery may write (`delivery.allow`: `push`, `open`), and the `gate`: `gate.argv`, the argv `agentd` runs in the worktree before it pushes (a relative command such as `./bin/check` is run from the worktree), bounded by `gate.timeout` (default `10m`), with a scrubbed environment: `PATH`, `LANG`, `TMPDIR`, `HOME` set to a new empty directory removed after the gate, and the variables `gate.env` names, never `HOME`, `SSH_AUTH_SOCK`, a `*_TOKEN` or a `CLAUDE_*` variable (naming one is refused at load). A gate that needs a cache under the real home, such as Go's module cache, gets it through `gate.env` (`GOMODCACHE`, `GOCACHE`). The gate runs as `agentd`'s user, so files under the real home stay reachable by path; each gate event lists, under `reachable`, what it could still find: the common credential paths (`~/.ssh`, `~/.netrc`, `~/.config/gh` and the like), each configured account's `token_file` and `config_dir` (named by account, never by path), and the ssh agent's socket (`$SSH_AUTH_SOCK`). A HOME the gate left read-only is made writable and removed; one that cannot be removed is an `error` event. The last 64 KiB of its output is kept, and the end of it goes on a failed gate's event unless it matches a confidential pattern. A repository whose policy allows `push` or enables merge without `gate.argv` is refused at load.
- `repositories.<name>.policy.gate.paths`: files or directories, relative to the worktree and without wildcards, that are part of the gate besides the script its argv names (every relative path with a `/` in the argv). The gate that runs must be the target branch's (#3: authority comes from the target branch). Before the gate runs, and again after it, `agentd` asks the configured URL (as for a push) for the target branch's commit, never trusting `origin/<target>`, which the session can move. Each gate path must be at the commit being delivered as the target has it, and on disk too: the bytes, the file modes and the set of files are compared, ignored and untracked files included, and symbolic links are not followed. git's index flags and status are not consulted. A session that changed one is refused delivery of that commit, with a skip naming the paths and one escalation, and its gate is not run; the owner changes a gate through the normal review and merge into the target. Build output kept under a gate directory therefore counts as a change, so name files, not output directories. A gate path that is a symbolic link on the target pins the link, not the file it points to, so name that file too. A gate file changed while the gate runs and put back before it ends is not seen; one still changed at the end is refused. A worktree whose git config has a remote named after the configured URL, which git would use in its place, is refused for the gate check and the push. A gate none of whose paths the target branch has is pinned by nothing and is refused until `gate.paths` names its files (a `make` gate names its `Makefile`, `sh check.sh` names `check.sh`).
  A repository with `owner_only` set has every entry of the published report marked for the owner alone.
- `ui`: the owner's web UI: its `address`, the `hosts` it answers to, the `whois` command, the `owner` login, other configs' `logs` to show and `shadow` (see The owner's UI).
- `accounts`: each Claude login a session may run under, by name, with its `config_dir`, its `token_file`, or both. A restart under an account sets `CLAUDE_CONFIG_DIR`, and for a token account `CLAUDE_CODE_OAUTH_TOKEN`, which the launching shell reads from the token file as the command starts: the launch never puts the token in `agentd`'s memory, the event log, or any process's arguments (a usage reading reads it for that reading and drops it; see Account usage). The launch fails closed: if by then the file cannot be read or holds only white space, the shell stops before starting Claude, so it never falls back to another login. A token file that is missing, blank or white space only, or readable by group or others is refused at load and again before each restart; the session is not restarted, one skip and one escalation say why, and `agentd` never falls back to another account. An account's transcripts are read from its `config_dir`'s `projects` directory. Its `usage` is how its plan usage is read (see Account usage): `auto` (the default), `endpoint`, `headers` or `off`.
- `usage`: the reading of the accounts' plan usage and the placement by it (see Account usage): `enabled` (off by default), `every` (15m), `limit` (90 percent), `api` and `model`.
- `tracking`: the owner's tracking system's output files, which `agentd` reads and never writes: the repository `manifest` (a JSON list of `name`, `platform`, `path`, `active`, `audience` and an optional `note`) and the `snapshot` (each repository's issues, requests and commits, each machine's clones and local work). The manifest is the repository list; a repository is identified by its platform and path, ignoring case. `mail` names the tracking system's mail findings file, beside the snapshot (see New items). Each file is read strictly: one missing, not JSON, or of a shape `agentd` does not know (a field it lacks, a list where it expects an object, a manifest that is not a list, a snapshot without `AsOf` or `Repos`, a manifest entry, snapshot repository or clone on a platform other than `github` or `gitlab`, an issue or request state it does not know, a repository listed twice in either file) is an error naming the file, never a partial read.
- `sessions`: each tmux session, its `workdir` (holding `BRIEF.md` and `STATUS.md`), its `cwd`, its `account` (one of `accounts`; unset means the default login), its `repository`, optional `deliver` specs, and an optional `hold` reason that stops delivery. A session naming an unknown account is refused at load.
- `policies.restart`: restart a gone session with `command`. By default that is `claude` under a login shell with a fresh session id and a prompt built from the session's progress (see *Context and spend*): a fresh context, never `--continue`. `{brief}`, `{status}`, `{session_id}`, `{mcp}` and `{prompt}` are substituted as they are, so the default passes the id, the server and the prompt to bash as arguments of their own (`bash -lic 'exec claude --session-id "$1" --mcp-config="$2" "$3"' agentd ID MCP PROMPT`), which keeps them data whatever characters they hold; a command of your own should do the same, and should pass `--session-id {session_id}` so `agentd` knows which transcript to measure. `{mcp}` is the `--mcp-config` document that starts the session's case server (see *Case tools*), or one with no servers for a session that works no case. It keeps Claude Code's permission prompts; add `--dangerously-skip-permissions` to your own `command` only if you choose to. Restarts back off exponentially from `backoff_initial` to `backoff_max`, counted within `window`. A session gone while its `STATUS.md` has open Questions is `blocked-on-owner` and not restarted until the owner answers them (see *Owner answers*). The command ends with Claude itself, so the pane dies when Claude exits; `agentd` starts sessions with tmux's `remain-on-exit`, so a dead pane keeps its exit status (`#{pane_dead_status}`) and last screen, and is restarted with `respawn-pane`, which tmux refuses for a live pane.
- Crash loops park. Each disappearance of a session `agentd` saw alive or restarted is a `crash` event with its cause: the exit status when tmux kept it, and the hash of the last screen. A restart that fails is a crash too, its error the cause. A crash whose cause repeats an earlier one, or the `max_crashes`-th crash (default 3) however far apart, parks the session as `crash-looping` with one escalation. A parked session is never restarted, nudged or typed into, and being seen alive again does not clear it: only `agentd clear SESSION`, which writes a `clear` event that a running `agentd` reads at its next pass.
- `policies.nudge`: type `message` into a session whose screen has not changed for `stall`, at most `max` times per idle episode, then escalate once. A session with open Questions is never nudged. With nudging on, a session that ended its turn with work left is `idle` at once, not `working`: its last folded turn is a summary made since it was last launched, its transcript's last line, when read, ends the turn, it has a STATUS.md, and its screen ends at the input prompt (an empty `>` or `❯` line, or one showing only Claude Code's `Try "…"` placeholder, among the last six, and no `esc to interrupt` within the four lines above those; text typed at the prompt, a placeholder of other wording, or a status line taller than the window pushes the prompt out and leaves the session to `stall`). Once `settle` has passed since the turn ended and since the screen last changed, `agentd` types `continue_message` (one line) followed by the progress facts a restart prompt hands, read from STATUS.md (`why` `continue`, the brief, progress file, item, state, next steps and last merge; not a case's tools or rulings, which the session's context holds): a nudge, counted against `max`, typed once per ended turn (a turn whose end the transcript dates within the second or two the typing takes is taken as before it, and waits out `stall`). A turn the session ends after any nudge answers it, however soon: the nudge count and the idle clock start again from its end. The ended turn is judged from the transcript agentd launched the session under, while the transcript's last line is the newest file's, so another Claude writing in the same directory can hide an ended turn. Facts that match a confidential pattern are left off the line, and the `nudge` event records the message and the facts' hash, never the facts. A session continued `max` times in a row since its launch with the same facts is escalated once and then waits out `stall` like a turn that has not ended; `max` 0 continues nothing. A rotation due at a checkpoint the session reached comes first: its turn is not continued while the rotation waits out the grace or its backoff, unless the rotation has given up or its account refused it. DONE, open Questions and a blocking decision are judged first, so none of them is continued, and a turn that has not ended waits out `stall` as before. A CI fix (`policies.ci`) waits for a session to be DONE or idle, so it replaces a session whose turn ended with work left at once.
- `policies.usage_limit`: the screen `pattern`, a regular expression like every pattern in the configuration, that means wait; when it clears, `resume_message` is typed once, and only into a session that can take it: never one that is DONE, has open Questions, or shows a dialog.
- `policies.answers`: the `pointer`, one fixed line typed into a session when the owner has answered it, pointing at `answers.json` (see *Owner answers*).
- `policies.trust_prompt`: the `pattern`, a regular expression that must match a whole line of the visible screen, less indent and box border, so it is the prompt's own question and not the words quoted in a diff, a dialog or a session's output (by default it matches both "Do you trust the files in this folder?" and "Is this a project you created or one you trust?", the latter with the rest of its paragraph on the line; a pattern of your own replaces the default, so it needs both wordings), and the `keys` that confirm the selected option (by default `Enter`; only `Enter`, `C-m` and `KPEnter` are accepted, because any other key could move the cursor, pick an option, or cancel and exit). The menu is answered by the option that says Yes, found by its text, never its position: Claude Code has preselected "Yes, proceed" first in one version and "No, exit" first in another. When the cursor is elsewhere, `agentd` sends only the arrows that move it to that option, and sends the confirm keys on a later screen that shows it selected, so `Enter` never goes while a rejecting option is selected. Only the options below the last question line count, so a menu left higher on the screen is not read as its. A menu without a visible cursor (`❯`, or `>` on a terminal without Unicode), the `Enter to confirm` footer or exactly one accepting option gets nothing, with one skip, and the owner is told once the same screen has lasted a pass; so are keys still showing the same prompt after `policies.nudge.stall` (counted whether nudging is on or not). A relaunch forgets the screen the keys went to, so the new Claude's prompt is answered afresh. It is answered only when the pane runs in the session's configured `cwd` (a coordinator's `workdir`) and any directory the dialog prints, as a whole line, is that one, compared with symbolic links resolved; for any other directory the owner is told once and nothing is sent. A printed path that wraps, or has a space, is not read as one: a wrapped one only makes `agentd` refuse, and the pane's own directory is still checked. Before launching a session `agentd` reads Claude Code's state file for its login (`<config_dir>/.claude.json`, or `~/.claude.json` with no account) and, when neither the directory nor one above it is trusted there, tells the owner once per session and directory how to trust it ahead; the launch goes on, and shadow mode says what it would tell. A missing or unreadable file says nothing. Keys are sent at most once per screen hash, only when the prompt is on the visible screen, only in the session's start phase (since it was first seen or last restarted, before it was seen in any other state), and never to a session with open Questions. The `trust` action records the directory. It is the one menu `agentd` ever answers; after the start phase a menu on screen is a dialog.
- `policies.dialog`: `patterns`, regular expressions for a Claude Code permission or confirmation dialog on the visible screen (by default `Do you want to`, a `❯ 1.` option menu, and `Enter to confirm`). A session showing one is `blocked-on-owner`, the reason names the pattern, and nothing is typed or sent to it. One escalation is posted per dialog episode (from the first pass that shows a dialog to the first that shows none, whatever the screen does meanwhile), and at most one per 30 minutes per session. A screen with a dialog's shape is one too, with no pattern needed: a line ending in a question mark (less indent and box border; not a quoted `>` line or a session's own `⏺` line) followed within four lines by options numbered 1 and 2, one of them under the `❯` cursor, which is how a subagent's permission dialog shows as well as the main session's. A session whose screen has not changed for `stall` while its transcript's last turn is an assistant tool call is treated the same way: it is most likely waiting at a permission prompt. `decline_after` (off, `0s`, by default) declines a dialog still showing that long: `Escape` is sent once per episode, through the typing safeguards, which a refusal lets the agent adapt to; only a screen with a dialog's shape is declined, never one a pattern alone matches. The time counts from the first pass that showed the dialog's shape, and a dialog is declined only once its escalation was posted, which then says when it will be; a dialog still showing at a later pass is escalated once more. Nothing ever approves a dialog: `Escape` is the only key, and it is not configurable.
- Stillness is judged without timers: the screen hash that `stall` counts from, and that every typing action compares before it types, is taken with the spinner glyph and its verb, elapsed-time counters (`4m 12s`), token counts (`↓ 8.1k tokens`) and clock times replaced by fixed text, so a session stopped under a running counter is still. Timings in a session's own output read as fixed too. The other side of it: a long tool call whose screen shows only a moving counter, with no new transcript turn, is still too, and after `stall` is escalated as probably waiting at a permission prompt. A parked session is never typed into.
- `policies.pane_commands`: the values of tmux's `#{pane_current_command}` that mean the pane runs Claude Code (default `claude`, what a native install reports; an npm install reports `node`). Before typing a line or sending keys, `agentd` asks tmux what the pane runs, and skips with one `skip` event naming the command when it is anything else, such as the shell left after Claude exited; then it reads the screen again, and types nothing, with a skip, if the screen changed since the pass read it. A pane that has run anything else for longer than `policies.nudge.stall` is escalated once.
- `policies.context`: rotate a session whose context is over `threshold` tokens (default 120000) once `grace` (default 5m) has passed since a merge it reached whose subject matches `checkpoint` (default `^Merge [#!][0-9]+\b`, an issue's merge, not a merge of the base into a branch or a pull); `enabled` by default. See *Context and spend*.
- `policies.budget`: `session_tokens` and `run_tokens`, caps in input-equivalent tokens on one session's spend and on every session's together, and `stop_at`, an RFC 3339 time. Zero or absent is no cap. Reaching one stops the session (see *Context and spend*).
- `policies.escalate`: the command run once per escalation key, with `{console}` and `{message}` substituted. It is optional: without it an escalation, and a feed line, is logged only, as its `action` (or `feed`) event, and the UI shows it in its console. `default_console` receives the escalations of sessions that name no repository and match no `consoles` entry; without a command, a session whose escalations would go to a console no repository or `consoles` entry has is refused at load, since they would show nowhere.
- `consoles`: consoles that are no repository's, `{NAME: {"title": "...", "sessions": ["glob", ...]}}`: a general chat console, an infrastructure console, a project without a forge. The UI lists each after the repositories; posts and replies work for it; a reply there is an instruction for no coordinator, read only through `agentd console inbox`. A session that names no repository and matches one of its `sessions` globs (the first console by name) escalates to it. A name a repository, or a repository's `console`, already has is refused at load.

A session's Questions section has one open escalation at a time. It opens when Questions become non-empty and the escalation is posted once. While they stay open, each change to their text posts one short `update` to the same console that names the session, says the questions changed and gives the new text (filtered like an escalation), at most one per change and one per pass, and at most one per 30 minutes per session, carrying the text current when it is posted; rewording never posts a new escalation. When the section empties, or the session is DONE, the escalation closes, and a later non-empty Questions section posts a new one. The episode number and the text last posted are rebuilt from the log, so a restart re-posts nothing and a change made while `agentd` was down is one update.

## States and evidence

A session is `starting`, `working`, `idle`, `blocked-on-owner`, `usage-limited`, `done`, `failed` or `crash-looping`. Every transition comes from evidence and names it in the log:

- whether the tmux session exists, by exact name, and whether its pane is dead, with its exit status;
- the hash of the visible screen plus the 40 lines of history above it, and how long since it changed, with a nudge's own echo not counted as change;
- the patterns (usage limit, trust prompt, dialogs) matched against the visible screen only, so a prompt that has scrolled away is never answered;
- what tmux says the pane is running, asked before anything is typed;
- `STATUS.md`: its first line, whether its last line is `DONE`, and whether its Questions section asks anything; a line inside a ```` ``` ```` or `~~~` fenced code block is content, never a heading, so a `# comment` in a snippet neither ends nor starts a section (a fence still open at the end of the file is taken as a typo, and the file is read without fences);
- the transcript's last turn, role and stop reason, read from the tail of the newest transcript for the session's directory when one exists. A fresh transcript keeps a static screen from counting as idle, as during a long tool call. Sessions sharing a directory share transcripts, so this is supporting evidence only.

## Context and spend

A Claude session re-reads its whole context on every model call, so a session that has run for hours spends most of its tokens re-reading a context it does not need: its progress is in its progress file, the issues and the branches. `agentd` keeps contexts small.

- **Measure.** A worker reads each session's transcript, only the bytes appended since the last read, with its subagents' transcripts (`<id>/subagents/*.jsonl`). A call written as several lines with one message id counts once, with its last line's usage. The context is the latest main-chain call's input, cache write and cache read; the spend is `input + 1.25 × cache write + 0.1 × cache read + 5 × output`, over every transcript measured for the session. A `usage` event records a transcript's totals when they change. The transcript is the one `agentd` launched the session under (`--session-id`); for a session it did not launch, or whose launched transcript has not appeared 10 minutes after the launch (a command that does not pass `{session_id}` on), the newest transcript in the session's directory is taken and marked a guess. A guess counts only while it is the session's current transcript. When a launched transcript never appears, live mode skips and escalates once: it does not rotate or hold a session to its budget on a guess. A transcript with no call yet is unknown, shown as `?`, never zero. `agentd status` shows each session's context, spend and rotations.
- **Rotate at a checkpoint.** A checkpoint is a merge: the newest merge commit reachable from the head of the session's `cwd`, logged as a `checkpoint` event when a newer one appears (the first one seen is a baseline and is not a checkpoint; going back to an older merge, by checking out an older branch, is none, and so is a merge whose subject `policies.context.checkpoint` does not match). A session whose context is over `policies.context.threshold` is rotated once `grace` has passed since a checkpoint it reached after it was launched, so it has recorded the merge first: `respawn-pane -k` starts the restart command in its pane with a fresh session id. Never for a session that is starting, waiting on the owner, usage-limited, done, stopped or parked, and never twice for one merge. A rotation is a `rotate` action, not a crash, and it does not count toward the restart limits or the backoff. Live mode rotates only on a transcript it launched; shadow mode also records the rotation it would make on a guess.
- **The restart prompt.** A rotated or restarted session's prompt is a fixed instruction followed by one compact JSON document of what `agentd` recorded: why (`rotation`, `restart`, or `answered` with `answers`, the path of `answers.json`), the brief's and the progress file's paths, the current item and its state, the last merge, and the next items. The items come from the first table in `STATUS.md` with a `State` column; its first column names the item, and items whose state starts with merged, done, deferred, closed, dropped or skipped are finished.
- **Budget.** A session whose spend reaches `policies.budget.session_tokens`, every session once the run's spend reaches `run_tokens`, and every session at `stop_at` is stopped: one `stop` action with the reason, then `kill-session` of that exact session. A stopped session is `stopped`: not restarted, typed into or counted as crashed until `agentd clear`; after a clear its session cap counts from its spend at the clear (recorded by the run as it applies the clear, so a replay reads the same base), while the run cap and `stop_at` must be raised or moved first. A session that is DONE is left to deliver. A rotation that fails `max_restarts` times for one merge is escalated once and not tried again. Live mode counts only transcripts it launched.

## Coordinators

A repository's coordinator is the one Claude session that carries its judgment: reviews, owner questions, what to start next. `agentd` collects the repository's state for it and wakes it only when a judgment is due, so no model polls and a quiet repository costs nothing.

```json
"repositories": {"widgets": {"coordinator": {"session": "widgets-coord", "workdir": "/srv/agentd/widgets-coord", "account": "work"}}}
```

- **A session of its own.** The entry makes a supervised session with role `coordinator`, running in its workdir under its account, for that repository alone. It is configured there and not also under `sessions`, and a session coordinates one repository. It is restarted like any session, never nudged, and refused when the log shows another session's claim on the repository: the first `coordinator` claim holds until the owner runs `agentd coordinator release REPOSITORY`, and the refused session is not launched, woken or rotated.
- **Turns.** The worker that reads a transcript for usage also logs each main-chain prompt in the user's own words (not a tool result or a meta line) and each text an assistant turn ended with as a `turn` event, at most 300 bytes, its text left out when it matches a confidential pattern. Each is logged once by its line, so a restarted `agentd` reading the transcript from its start logs none again.
- **The pack.** `pack.json` in the coordinator's workdir is one compact JSON document, data and not instructions: what is due, the last wake, the repository's other sessions with their state, case and latest `policies.coordinator.turns` turns, their decisions and whether each is answered, and the repository's items the owner has not marked seen (never owner-only ones). It stays under `pack_bytes`: the oldest turns go first, whichever session's, then the oldest items, then decisions, then the last reasons due, then the owner instructions, and `summarized` counts what was left out.
- **Wakes.** A judgment is due when a session of the repository finished (DONE) or waits on the owner, an item for it is new, or the owner answered one of its sessions, each once: a wake records the facts it covered, so one logged by another process during a wake's pass is due at the next. Then, once the coordinator ended its turn after its last wake (its transcript says so; a turn that ended otherwise, or a pointer the transcript never moved after, counts once the screen or the transcript has been still for the nudge stall; without transcripts, the screen alone), can take a line and shows no dialog, `agentd` writes the pack through a temporary file and types `policies.coordinator.pointer`, one fixed line: a `wake` action with the reasons and the coordinator's spend. Nothing due types nothing. Shadow mode records the wake it would make.
- **Sessions it starts.** A repository with a `sessions` entry lets its coordinator start sessions that `agentd` supervises, through two MCP tools; its launch then passes the coordinator a server and its facts name the tools.

  ```json
  "repositories": {"widgets": {"coordinator": {"...": "..."}, "sessions": {"root": "/srv/agentd/widgets", "clone": "/srv/src/widgets", "target": "main"}, "policy": {"sessions": {"accounts": ["work"], "max": 4}}}}
  ```

  `start_session(kind, branch, issue, account, repository)` takes a plain branch name (no `refs/`, leading `-` or `..`; not the target or a branch a configured session delivers to), `kind` `work` (the default), `reviewer` or `judge` (both need the issue), an account from the policy's `sessions.accounts` (by default the coordinator's own), an issue the policy's `scope.reserved` does not name, and only the coordinator's own repository. Its name is `REPO-<branch slug>-<6 hex of the branch>`, with `-review` or `-judge` for those kinds, so a branch and kind have one session; a start for a running name, past the policy's `sessions.max` (default 4), or otherwise wrong is answered with the reason and not logged. The fold holds the first start of a name and none past the `max` the start recorded (so a replay under another `max` agrees), and the server reads the log back, so of two racing starts only the one that holds is told it started. A start is a shared `session` event; the sessions started and not ended are a projection of the log beside the configured ones, which every fold reads, so a replay rebuilds them. Before it is supervised, a started session is provisioned in a worker (a `provision` action, a would-be one in shadow, retried on the restart backoff and escalated after `max_restarts` failures): `root/NAME` with `BRIEF.md` (a fixed instruction and compact JSON: repository, kind, branch, issue, target, worktree, mr_file), `STATUS.md` when there is none (one that ends in DONE loses that line and notes the new start; its notes stay), and the worktree `root/NAME/work` unless it is there, added from `clone` after a fetch: a work session's on the branch as the clone or origin has it, else cut from `origin/target`; a reviewer's or judge's detached at that branch's commit, since its worker has the branch out. A branch that a configured session's worktree has out cannot be added; its provision fails and goes to the owner. Then it is a session like any other: launched with the restart command, restarted, rotated, budgeted and nudged; its turns are in the pack, its DONE is due for the coordinator, and where the repository allows push it delivers a draft request to `target` from `root/NAME/MR.md`. `end_session(name)`, for a session of the coordinator's own repository, or the owner's `agentd sessions end NAME`, ends one: an `end` action stops its tmux session, once (escalated when that keeps failing), and it leaves the projection; its workdir and worktree stay. A start of the same branch and kind later is a new session with a fresh record (restarts, crashes, deliveries) and a new brief, in the same workdir and worktree; while the end's stop is still due it waits, so the old Claude never runs on as the new session. A provision is keyed by its start, so a late outcome of an earlier start's provisions no later one. A reviewer started again keeps its detached worktree at the commit it was added at; its brief names the branch to check out again.
- **Small contexts.** A coordinator over the context threshold is rotated at a wake it has handled, never during one; its launches write the pack first, and its facts name the pack and the repository. `agentd status` shows each coordinator's wakes, its tokens per wake since the first, and how long it has been quiet; the UI shows its wakes beside its state.

## Event log

One JSONL file, append-only, one line per observation and action. Every line is version 2 of the format (`v`), with `time`, `session`, `kind`, the `mode` of the run that wrote it (`live` or `shadow`; `mark-delivered` and `clear` write `owner`, which both modes read) and exactly one typed payload, named for its kind: `start`, `stop`, `observe`, `transition`, `act` (for `intent`, `action` and `would`), `skip`, `crash`, `clear`, `error` or `warning`. Each payload has its own fields; nothing is an untyped detail. A line of another version, an unknown field, kind or mode, a missing mode, or a payload other than its kind's is malformed; `agentd` reads no older format, so a log from before this one is refused and is started afresh. Kinds are `start`, `stop`, `observe` (logged when the evidence changes), `transition`, `crash`, `clear`, `intent`, `action`, `would`, `skip`, `error` and `warning`. Every action is recorded before it is taken, as an `intent` with a random `intent` id, and its outcome after, as an `action` or an `error` repeating the id. When any append fails, the pass stops: the action whose intent could not be written is not taken, nothing more is done until the next pass, and `run --once` exits with the error. An `intent` with no outcome is an action cut short by a crash of `agentd`: the next `run` logs a `warning` naming it, `status` shows it, and an escalation, Questions update, nudge, resume or trust keys cut short this way count as done, so the owner and the session never see them twice. The file is created readable by its owner only (`0600`). Each append holds an exclusive `flock` on the file, so `mark-delivered` never interleaves with `run`, and is synced to disk before the action counts as recorded; an append whose write or sync fails is cut back out of the file, so it never leaves a fragment, and an event `agentd` could not read back is refused before it is written. At startup a malformed line is corruption: `run` refuses to start and names the line. Only a malformed last line that lacks its newline is a write cut short; `run`, `mark-delivered` and every append cut it off first and log a `warning` with its length, so a new record never lands glued to the fragment. An `observe` event carries `unchanged_s` only once the screen has been seen; until then the time is unknown and the field is absent.

The log is the only state, and one function reads it: `apply` folds an event into the state of one mode. Replay at start, the live path (each event is appended, then applied; apart from the screen memory a pass keeps between its own observations, which the observe event it logs then records, the supervisor changes its memory of a session in no other way) and every view (`status` and `report`) go through it, so a replay always rebuilds what the running `agentd` had. Live and shadow stay one log with a mode on each event: a run applies only the events of its own mode, plus the owner's records, so a shadow run's `would` events never use up a live run's restarts, escalations or deliveries, and a live run's actions never shape the shadow's decisions. In shadow mode `would` events count toward the shadow's own counters, so the once-per-key rules show in the log as they would have run. A restart shadow mode only would have made starts nothing, so a session still gone at the next pass has not crashed: shadow never records a crash for it or parks it, and logs the restart again on the backoff schedule.

## Safety

- Process control is by exact session name only. The tmux surface has no listing and no pattern; its only kills are a rotation's `respawn-pane -k` of the session's own pane, and the `kill-session` of that one session by a budget stop or the end of a session a coordinator started.
- Nothing is typed or sent as keys into a session that is DONE, has open Questions, is blocked on the owner or shows a dialog, or whose pane is not running Claude.
- Every forge write goes through one client wrapped with the per-repository policy. It can push and open where `delivery.allow` says so, and merge where `merge.enabled` says so, by the policy's method: a fast-forward, the forge's merge call pinned to the head (a merge commit or a squash), or the policy's own command; it never rebases or forces.
- No escalation, merge-request text, branch name or commit message that matches a `confidential_patterns` entry is posted or pushed, and none is logged.
- An error that git, `gh`, `glab`, a gate or the escalation command reports, a poll's error, and a skip's reason, is logged as `(withheld: matches confidential pattern N)` when it matches a `confidential_patterns` entry.
- The gate that decides a delivery is the target branch's: a session that changed it is refused (see `gate.paths`).
- Escalations, Questions updates and deliveries are keyed and posted once, across restarts of `agentd`. Before pushing, the forge is asked for an existing request on the branch: an open one, or a merged one whose head commit is the worktree's current HEAD, or whose head the target already contains while HEAD has nothing the target lacks (the forge rebased it before merging). One found is recorded as the delivery, with the HEAD it covers, so a lost reply or a lost log never opens a duplicate. Commits count as ahead of the target only when the target lacks their changes, so a branch rebased onto a squash merge has nothing to deliver; a merged request for older commits does not count, so new commits on a reused branch name are delivered. `mark-delivered` accepts only a worktree named in the session's deliver specs.
- Delivery pushes to one URL built from the configuration alone, `git@<host>:<project>.git`, or `https://<host>/<project>.git` with `transport: https`; never to `origin` or any remote the worktree names. The push names the exact commit that was checked, `<sha>:refs/heads/<branch>`, never whatever HEAD has become, and runs with hooks off (`-c core.hooksPath=/dev/null`, `--no-verify`). It is refused, with one skip, when git config rewrites that URL (`insteadOf`, `pushInsteadOf`), or when the git config changed while the gate ran. Origin still decides what the fetch brings and what counts as ahead, so every fetch and push URL it has (`git remote get-url --all` and `--push --all`; credentials never logged) must name the configured project on the configured host, or one skip says why and nothing is pushed. `glab` and `gh` are pointed at the configured host, and requests from forks are left out when looking for an existing request.
- Nothing is delivered without a gate `agentd` ran itself. Delivery runs the repository's `gate` on the worktree's exact HEAD and records a `gate` event with the command, the commit, the exit status and the duration. It pushes only when the gate exits 0 and the tree is still the one it ran on: HEAD unmoved and the worktree clean. A failing gate is retried on the backoff schedule and given up on that commit after `max_restarts` failures, with one escalation; a new commit gets fresh tries; a tree that changed under the gate is skipped, and the next pass gates the new tree. Shadow mode logs the gate it `would` run and runs none. The gate's script and the files `gate.paths` names are the target branch's, but what it tests (the code, and tests such as a `TestMain` that exits 0) is the session's own, as is the worktree's git config that the fetch and push read: the gate protects against honest mistakes and a session rewriting its own check, not against a hostile session.
- A worktree on the deliver target itself, or on a detached HEAD, is never pushed; one skip says why, and it is delivered once it moves to a branch.
- A failed action is not retried every pass: retries follow the restart backoff and stop after `max_restarts` tries, with one skip or escalation saying so.
- Every external command runs under a timeout, and when it hangs its whole process group is killed; a hung tmux is an error, never taken for a gone session.
- Shadow mode performs no tmux write, no push or open, and runs no escalation command; escalations and Questions updates are logged as `would` events. It does fetch, which changes only the worktree's remote-tracking refs and nothing on the remote, so its delivery decisions use current refs.

## New items

`agentd items` lists what changed since the owner last looked, newest first: `--new` only the items not yet marked seen, and `--seen ID,...` marks items seen. Each item has #7's shape: an `id` that stays the same however often it is seen, its `kind` (`issue`, `merge_request`, `discussion`, `mail_question` or `mail_report`), its repository (`platform/path`), title, link, when the source says it happened, its author, when `agentd` first saw it, and whether it is for the owner only. Before listing, `items` reads the tracking files. Snapshots are compared through a cursor, the `AsOf` of the snapshot read last: an issue or request created since then is a new item, and an open one updated since then is a `discussion`, one per update. The first snapshot read is the baseline and makes no items. Every mail finding is an item for the owner only, keyed by its thread; one whose subject or summary asks something is a `mail_question`, any other a `mail_report`. Items, cursors and the owner's marks are events (`item` and `cursor` with mode `shared`, facts both modes read; `seen` with mode `owner`), so a replay rebuilds them and an item is never listed twice. A file that cannot be read is an error naming it and changes nothing: the list is never emptied or rewritten by a bad file. A bad mail file leaves the snapshot read; mail waits while the manifest or snapshot cannot be read, since its items take their repositories from them. Each cursor only moves forward, so an older file read again adds nothing. Mail findings carry a day, not a time, and sort as that day's midnight in UTC.

## Polling the forges

With `poll.github` or `poll.gitlab` set, `agentd run` asks the forges itself every `poll.every` (default `15m`), in a worker, through the `gh` and `glab` logins already in place: no credentials of its own. What it finds becomes items, with the ids the tracking snapshot gives (`platform/path#N`, `!N` for requests), so an issue both find is one item. Only the manifest's repositories count; without a readable manifest a source is unknown.

- **GitHub:** `GET /notifications` (read ones too, 100 per page) with `If-Modified-Since` from the last `Last-Modified`, which is the `github` cursor. A 304 means nothing changed, costs no rate limit, and makes no event. `X-Poll-Interval` is honoured when it is longer than `poll.every`. A notification of an issue or pull request updated since the cursor is a discussion of it, unless it is not an item yet and was opened since the cursor: then one more call reads when it was opened, and it is a new issue or request. One already an item as opened since the cursor (the snapshot may find it first) adds nothing. Other notifications (check suites, releases) are not items.
- **GitLab:** each active repository's issues and merge requests with `updated_after` the `gitlab` cursor, and the pending to-do list for to-dos made since, on any manifest repository. One opened since the cursor is new; one only updated is a discussion. The new cursor is two minutes before the poll began, so a clock skew misses nothing. It moves with every poll that worked, but its event is written only with a poll record, so quiet polls write nothing and a restart asks again from the last record's cursor. Each list is read in pages of 100, up to ten; a longer one makes the poll unknown rather than leave out what is past it.
- **Cursors and gaps.** The first poll of a source is its baseline and only sets its cursor. Each cursor is an event, so a restart neither misses nor repeats. A source that fails leaves its cursor where it was, writes none of the items it found before failing, and is shown as unknown, never as "nothing new"; the next poll asks from the old cursor. A CLI's error status and message are kept in the error.
- **Cost and health.** A `poll` event records a poll that found items, moved its cursor, failed or recovered, and at least every six hours a heartbeat; each counts the quiet polls since the last record and all their calls. `agentd status` shows each source's health, its last record, its calls and polls; a source whose last record is older than six hours and two intervals, or any source while `agentd` is stopped, is shown as unknown, since no one is polling it. A source turned off is not shown. The tally is kept in memory, so a restart loses the quiet polls since the last record from the count.

### CI

With `poll.ci` set, `agentd run` watches the pipeline of every request a session delivered (and every one the owner recorded with `mark-delivered`) every `poll.ci_every` (default `5m`), in a worker, through the same `gh api` and `glab api` logins, on the repository's host. It reads the request (GitLab: the merge request's head pipeline and its jobs; GitHub: the pull request's head check runs). On a failure it reads the target branch's latest pipeline, and for a failure that is the branch's own, the end of the first failing job's log. A request merged or closed is no longer watched.

- **Whose failure.** A failure is the branch's own unless the target is red, every job failing on the request fails on the target too, no job the target fails passes on the request, and the request's title or description names neither the target's red commit nor its pipeline. A request that passes what the target fails, or says it fixes it, is the target's fix and never waits for itself. Any other failure on a red target waits until the target is green, and any failure waits while the target's latest pipeline has not settled (GitLab: its latest finished pipeline is read). A merged-results pipeline counts as the head's.
- **Fix session.** On its own failure, the delivering session, once DONE or idle, is relaunched through the restart policy's command with `why: "ci-fix"`, `policies.ci.pointer`, and a `ci` fact: the request, its head, the failing jobs and the log excerpt (its last 40 lines without timestamps, GitLab section markers or colour codes, at most 3000 bytes, withheld whole when it matches a confidential pattern; empty when no failing job's log can be read). Delivery waits until that session has finished its turn, then pushes its new commit to the same request. A `ci-fix` action is not a restart or a crash.
- **Bounds and decisions.** Fix sessions per request count against `policies.restart.max_restarts` in its `window` and follow its backoff. The same cause again after a fix (the same failing jobs and an excerpt that matches once clocks, counters, durations and commit hashes are stripped), seen on the head the fix delivered, or the count used up, raises a decision on the session, `C1` on, with `retry` (one more fix session) or `leave`; a retry that meets the same failure asks again. It is answered on the UI like any other, does not count against the session's own open decisions, and leaves its `D` numbering alone. `C` and a number is reserved in `questions.json`.
- **Events and views.** Each change of a request's CI is a `ci` event: its state (`pending`, `success`, `failed`, `none`, `unknown`, `merged`, `closed`), head, target state, verdict (`own` or `target-red`), failing jobs and cause. A forge that cannot be asked is `unknown`, never green. `agentd status`, the UI (beside each repository's requests), the report and `agentd cases` show each request's CI. Once `agentd` has stopped, or with `poll.ci` off, status and the report show the CI as unknown, and so does the report for a record older than the head a fix delivered.

### Merge when green

A repository whose policy sets `merge.enabled` may have its requests merged by `agentd` (#1, D2; #35). Off by default. Enabling it needs `gate.argv`, `gate` in `merge.require`, `merge.targets` (the branches `agentd` merges into) and `merge.authors` (the forge usernames whose requests count as ours), so it never means any target or any author. With `poll.ci` set, every `poll.ci_every` each watched request is merged when all hold: the CI watcher has recorded its head since its latest delivery (it is what knows the head); what `merge.require` names holds at that head (default `gate` and `ci`; `gate` always): `ci`, the CI record is `success` (never `none`: a pipeline not yet created, cancelled or skipped is not green), `gate`, agentd's gate passed on that exact head, `review`, the session's case stopped its review rounds `converged`; its session has no open blocking decision or Questions; the forge says the request is open with that same head and not a draft (GitHub: its `mergeable_state` is `clean`, `has_hooks` or `unstable`, since moving the branch skips the pull request's own review rules; a state not yet computed is waited for); the repository's own `.agentd/policy.json` at the target's tip, if any, leaves merge on and is not withheld (see *Repository policy*); the request's target is in `merge.targets`, its forge author in `merge.authors`, neither its number nor any of its labels is in `merge.exclude`, and each of `merge.approvals` approved it (GitHub: an `APPROVED` review on the head commit that is still its reviewer's latest review other than a comment, read from one page of 100; GitLab: the request's `approved_by`, which GitLab keeps across a push unless the project resets approvals, so it is not tied to the head); for `merge.method` `fast-forward` (the default), the head is a fast-forward of the target's tip (GitHub: the compare is `ahead`; GitLab: the merge base is the tip, and the project's merge method is `ff`, since any other would make a merge commit, and its squash option is not `always`, which would write a commit nobody gated); and the request and the target's tip, asked again just before the merge, have not changed. (A GitLab request retargeted in the instant between that second look and the merge call is not caught.) The merge, through `glab` or `gh` with prompts off and the forge timeout, is by `merge.method`: `fast-forward` is GitLab's merge call pinned to the head (`sha`, `squash=false`) or, on GitHub, which has no fast-forward merge method, a move of the target branch to the head without force; `merge` and `squash` are the forge's merge call pinned to the head (GitLab `squash` false or true, under the project's own merge method; GitHub `PUT pulls/N/merge` with `sha` and `merge_method`); `command` runs `merge.command`, an argv with `{repository}` (the project path), `{request}`, `{head}` and `{target}` substituted, with no shell and prompts off. Otherwise a `skip` event says why, once per head and reason, and nothing is done; CI still running, and a CI record the watcher has not yet brought up to the latest delivery, are waited for without one. A `merge` action records the request, its head, the target's tip and the method; a request is merged once, and a merge cut short is not tried again. A failed merge call is retried with the restart policy's backoff, `max_restarts` times per head. Then a skip says it was given up; the request stays open for the owner, and no decision is raised. Shadow mode merges nothing; since its gate is only a would-be gate, it records that the head was not gated.

### Every request

In a repository with a `coordinator`, the CI watcher also lists the open requests each round (GitLab `merge_requests?state=opened`, GitHub `pulls?state=open`, one page of 100) and watches each one no session delivered for the coordinator: its `ci` events and records carry the coordinator's session (#36). A request that leaves the list is still asked until the forge says merged or closed. Every record also holds the request's author (screened), whether it is a draft, whether it has an open discussion (GitLab: `blocking_discussions_resolved` false, or a resolvable thread not resolved, from one page of 100 discussions; GitHub: a reviewer's latest review other than a comment requests changes, from one page of 100 reviews, since REST has no thread state and branch protection's conversation resolution already shows as `blocked`; a full page holds the request as if one were open), the run that judged its head (the pipeline id, or the oldest check run's, so a job run again tests the same commit), and `base`: for a GitLab merged-results pipeline, the first parent of the merge it ran on; otherwise the target's tip when that run was first seen, running or settled, kept across a forge error, and `unknown` when the tip could not be asked then (a later tip never stands in for it). A run first seen settled took its base from a tip that may have moved while it ran, which is not caught. A merged-results pipeline counts for the head only while the head is its merge commit's second parent, so one left from an earlier head, after a push whose pipeline was skipped, is not green. A busy request whose first page of 100 discussions or reviews is full is held as if one were open.

- **Approve.** The coordinator's MCP tool `approve(request, sha)` takes a request of its own repository that the watcher has recorded, at its recorded head (whole, or a prefix of 7 or more hex digits); anything else, or a call from a session that is not the repository's coordinator, is refused and not logged. It logs a shared `approval` event; only the repository's coordinator's counts, the latest per request. An approval counts only while the request's head is that sha, so a push after it holds the merge until a new `approve`. A coordinator whose repository has no `sessions` entry gets `approve` alone.
- **Merging.** A request no session delivered merges under *Merge when green*, except that agentd's gate never ran on it, so `merge.require` is replaced by `ci` and `review`, and `review` is met only by an `approve` at its head; its coordinator's own decisions do not hold it. For a delivered request `review` is met by its case's rounds converging or by an `approve` at its head. A draft, or an open discussion, holds either kind; the discussions are read again when the merge is checked and just before it. Skips and merges of a request no session delivered are recorded on the coordinator's track.
- **A moved base.** With `ci.retest_on_base_move`, a request whose target tip is no longer the `base` its green run was recorded at is retested before it merges, once per head and tip: on GitLab a `retest` action asks for a new pipeline (`POST merge_requests/N/pipelines`, on the merge result where merged results pipelines are on), through the allow-listed forge client under `merge`; when the new run is green the watcher records the new base and the merge goes ahead. A base `unknown` counts as moved. While no new run has come after a retest, a skip says it is waited for. A retest call that fails is retried with the restart policy's backoff, `max_restarts` times per head and tip, then given up with a skip. GitHub has no call that retests a pull request's merge result, so there the merge is skipped with that reason. A base never recorded, because the tip could not be asked, is not taken as moved.
- **Red CI.** A request no session delivered whose own CI failed is due for the coordinator once per head, run and cause, as `ci: REF failed at HEAD`, however often a forge error or a new thread changes its record in between; the coordinator is never relaunched to fix it, and starts a fix session through `start_session`. Its pack has `requests`: each such request's ref, url, author, head, target, state, failing jobs, log excerpt (at most 600 bytes), whether it is a draft, has an open discussion, or is approved at its head.

With `ci.required`, `ci` is added to `merge.require` for delivered requests too. `review.others` and `review.*_model` are still not acted on: a request by an author outside `merge.authors` is watched, in the pack and never merged, whatever `review.others` says.

### Repository policy

Each repository's rules that `agentd` checks mechanically are one typed `policy` in the owner's configuration (#35), not prose in a coordinator's brief:

```json
"policy": {
  "delivery": {"allow": ["push", "open"]},
  "gate": {"argv": ["./bin/check"], "timeout": "20m", "env": ["GOCACHE"], "paths": ["Makefile"]},
  "merge": {"enabled": true, "method": "fast-forward", "command": [], "targets": ["main"], "authors": ["widget-bot"],
            "exclude": {"numbers": [12], "labels": ["do-not-merge"]}, "approvals": ["lead"], "require": ["gate", "ci", "review"]},
  "review": {"reviewer_model": "", "judge_model": "", "rounds": {"max": 3}, "others": "review-only"},
  "ci": {"required": true, "retest_on_base_move": false},
  "scope": {"reserved": {"numbers": [7], "labels": ["owner-only"]}},
  "sessions": {"accounts": ["work"], "max": 4, "models": [], "budget": {"session_tokens": 2000000, "run_tokens": 0}, "fallback": []},
  "confidential_patterns": ["widgets-internal-[0-9]+"]
}
```

The old repository keys (`allow`, `gate`, `gate_timeout`, `gate_env`, `gate_paths`, and `sessions.accounts`/`sessions.max`) are gone, not aliased: a configuration that still has them is refused. `review.rounds.max`, when set, is the backstop of the repository's cases in place of `policies.rounds.max`. `scope.reserved.numbers` are issues `start_session` refuses; `scope.reserved.labels` are matched where agentd sees labels, a request's own labels when it is about to merge, which hold it. `sessions.budget` caps each of the repository's sessions and all of them together, beside `policies.budget`. Each repository's `confidential_patterns` are added to the global ones, and everything agentd screens is screened with them all. The patterns a repository's own file adds screen what the supervisor and its workers log, escalate, feed and pack; the case tools' server, console instructions and the report screen with the configuration's patterns only. `ci.*` is acted on (*Every request*); `review.reviewer_model`, `review.judge_model`, `review.others`, `sessions.models` and `sessions.fallback` are checked and shown but not yet acted on.

A repository may add rules of its own in `.agentd/policy.json` on its target branch, in the same shape, read through the forge at the target's tip when a request into one of the owner's `merge.targets` is about to merge (at most 16 KiB); a request into any other branch is refused before its file is read. Its keys may only narrow the owner's policy: turn `merge.enabled` off; a subset of `merge.targets`, `merge.authors`, `sessions.accounts` or `sessions.models`; more `merge.exclude`, `merge.approvals`, `merge.require`, `scope.reserved` or `confidential_patterns`; a lower `sessions.max`, `sessions.budget` or `review.rounds.max`; `review.others` `review-only`; `ci.*` turned on; and `merge.method`, `merge.command`, `gate.*`, `review.*_model` and `sessions.fallback` only as the owner has them (an empty list is the same as none). `delivery.allow` is the owner's alone. A lower `review.rounds.max` is taken when it is below the backstop in force. A key that would widen the policy, or one the policy has not, is refused; a file that is no JSON object or too long is refused whole (`file`). The keys that narrow apply. A file that matches one of the configuration's confidential patterns (never one a file added, so a file cannot withhold itself) is withheld: nothing of it is logged, and merges into its target are off until it or the patterns change; it is screened again at every read. What was read is a shared `policy` event, once per repository, target and file hash, with the tip, the compact file and the keys applied and refused, so every process narrows the same way. As the read is recorded, a refusal or a withheld file goes to the owner once, as an escalation naming the keys (two requests to the same target checked in the same round may each send it; a post that fails is not retried, and the refusal stays in `policy show`). The file is read at the target's tip at every merge check, so a file that narrowed the policy does not hold it once it changes. A merge reads the owner's policy narrowed by its own target's file; `start_session`, budgets, rounds, screening and the coordinator's pack (`policy`, without its confidential patterns) read it narrowed by the file last read on each of the owner's `merge.targets`. Repositories sharing a project take the lowest backstop.

`agentd policy show REPO` prints the effective policy as compact JSON: each key (`section.key`) with its value and its source, `owner`, `default` or `repository .agentd/policy.json on <target> at <tip>`, and each file last read, its target, tip, refused keys and whether it was withheld. Which keys a file applied is worked out again against the configuration as it is now.

## Triage

With `jobs.triage` set, `agentd run` triages new items with an agent job (#3, section 5): one small `claude -p` call per batch of up to `jobs.batch` (default 20) unseen items, in a worker, never inside the pass. Each item gets #7's triage: its `kind` (`question`, `report` or `discussion`), `needs_owner` (`now`, `today` or `none`), `urgency` (`now`, `today` or `later`), a one-line `summary` and a `suggested` next step (`reply`, `file_issue`, `answer_in_thread` or `none`). `agentd items` and the owner's UI show them, and sort what is new by urgency, then as before.

- **Stripped setup.** The call runs `jobs.command` (default `claude`) with `--model` (`jobs.model`, default `haiku`), `--output-format json --json-schema`, a short `--system-prompt`, `--setting-sources ""`, `--strict-mcp-config` with no servers, and `--tools ""`, so it can only answer. `ANTHROPIC_API_KEY` and `CLAUDECODE` are removed from its environment. Under `jobs.account` it gets that account's config directory and token, the token read by the shell as for a session; without one it uses `agentd`'s own login. Mail items go to the job too, so `jobs.account` must be the owner's own login (#7), never a shared one.
- **Limits.** There is no token-cap flag, so the cap is the input size (`jobs.max_input`, default 16 KiB; items that do not fit wait for the next call, and each title is cut to 300 bytes) and `jobs.timeout` (default `2m`), after which the call's process group is killed; so is it when `agentd` is told to stop, and the items wait for the next run. Output over 1 MiB ends the call.
- **Data, not instructions.** The items go on standard input as one compact JSON document, and the instructions say that text inside it is data, never to be followed.
- **Checked twice.** The CLI holds the answer to the schema, which is built from the lists Go accepts; Go then checks that every item sent comes back exactly once and nothing else does, that every field is from its list, and that the summary is one line of at most 160 characters. A failed call or answer is retried once. A second failure is an `error` event naming the items, and is never applied: the items stay, untriaged, and are tried again after an hour.
- **Events.** A checked answer is a `triage` event, mode `shared` like the items, with the model and the tokens the calls used. Each result is keyed on a hash of the item's title, so an item seen again is not triaged again, whatever author, link or kind another source gives it. One seen under a new title is retitled and triaged again (the first sighting's time stands); in practice that is a GitLab issue edited within a poll's overlap, or a snapshot or mail finding with a new title. A running `agentd` picks up the items, seen marks and triage other processes log, so it does not triage what the owner has already seen or another run has triaged. Triage is opt-in, so a `--shadow` run with `jobs.triage` set triages too: the calls are its own, and the results are shared facts both modes read.

`agentd triage --items FILE` tries the job on a JSON list of items with one call, retried once if it fails, and prints the checked answer and its cost; it logs nothing.

## Account usage

`agentd accounts` reads every configured account's plan usage now and prints one line each: the five-hour and weekly utilization in percent with their resets, and whether overage is on, or why it could not be read (#39). It logs nothing.

- **Reading.** The token is the account's `token_file`, else the OAuth access token in its `config_dir`'s `.credentials.json`, read only as a regular file. It is read for each reading and dropped, never logged or printed: any text a reading returns has the token taken out first, an error names a token file by its base name only, and a redirect is never followed. `usage.api` must be https (http only to this machine). A `.credentials.json` token past its `expiresAt` is not sent: Claude Code refreshes it only while it runs under the account, so an idle account read this way may read as expired until it runs again. `endpoint` asks `{api}/api/oauth/usage` (`five_hour`, `seven_day`, `extra_usage`). `headers` makes the minimal request Claude Code makes, one token of `usage.model` with Claude Code's system line, and reads its `anthropic-ratelimit-unified-5h-*`, `-7d-*` and `-overage-status` headers; it costs one tiny call. `auto` asks the endpoint and falls back to the headers when the token may not read it (HTTP 401 or 403, a token without the profile scope).
- **Events.** With `usage.enabled`, `agentd run` (live only: a shadow run makes no reading of its own) reads each account every `usage.every`, in a worker. A reading is an `account` event, mode `shared`, no session, with the numbers only, or its error, screened. It is logged when a utilization moves by a percent or more, a reset, overage or the error changes, or, saying the same, after an hour or half of the time a reading stands for (three `every`), whichever is sooner, so a steady account never goes stale. The fold keeps each account's latest reading, its numbers across a failed one.
- **Placement.** A coordinator's `start_session` that names no account, in a repository whose policy has `sessions.fallback`, is recorded with no account. Before preparing it, `agentd` places it on the first fallback account whose latest reading is no older than three `every` and has both utilizations under `usage.limit` (with `usage` off, the first fallback account; an account whose `usage` is `off` always counts as having room). The placement is a shared `session` event of action `place`, naming the start's id and the account; the fold sets the session's account once, so it never moves to another account afterwards. While no fallback account has room, the start waits: a skip once, and one escalation per start, when every fallback account was read and is at or over the limit, naming each one's utilization and reset, or when the readings have not come for three `every` since the start; never only because the first reading is not in yet. A start recorded for placement never starts on the default login, even if the fallback order is taken out of the policy while it waits. A shadow run places nothing and waits for the live run's placement. An earlier fallback account this run has not yet read is waited for, never passed over for a later one, since a placement holds for good; a run just started reads before it places, and counts a start's wait from when it began reading. The fallback order widens the accounts a placed session may go on beyond `sessions.accounts`, which still bounds an account the coordinator names; the default login is never a fallback. An account the coordinator names is used as before.
- **Views.** The coordinator's pack carries `accounts`, the readings of the accounts its repository's sessions may use and fall back to. The UI's top bar shows a chip per account: its utilizations and resets, overage, how long ago it was read, and whether it has room, is over the limit, or is stale.

## The owner's UI

`agentd ui` serves the owner's web UI on `ui.address` until interrupted (#41; it replaced `agentd page`, and serves the consoles' view #37 asked for). `ui.address` must be one IP address and port (the machine's private-network address, never every address). Every request is checked before anything is read. Its `Host` header must be one of `ui.hosts` (by default the address itself; case is ignored), so the UI reached through another name is refused. It must not come from the UI's own address or from loopback (an IPv4 address written as IPv6 too), so a process on this machine cannot borrow the machine's own identity. Then `ui.whois`, an argv with `{addr}` replaced by the caller's address and port, must name `ui.owner`: the command prints the caller's login on its first line, or a JSON object whose `UserProfile.LoginName` is the login, as a private network's `whois --json` does. It runs under the tmux timeout; an answer is kept for a minute per address, at most four run at once, and a failure is logged. Anyone else, and anyone whois cannot name, gets 403.

**One server, many logs.** `ui.logs` lists other agentd config files (relative to this one), such as the coordinators' when they run under a config of their own. Each config's event log is one source, named after its config file; with `ui.shadow` (off by default) each config's shadow run is one more, named `NAME-shadow`. Each source is a projection of its log: one state, folded by the same `apply` as `run` and `status`, brought up to date with only the lines appended since the last request. Repositories are merged across the sources by their configured name. Every form names its source, so an answer or a mark goes to the log that holds the decision or the item.

**Pages.** Server-rendered HTML, one embedded stylesheet with light and dark colours from one token set, system fonts, laid out for a phone as well as a desktop. The content security policy allows the UI's own `/ui.css` and `/ui.js` only. The script fetches the UI every 30 seconds and swaps in each refreshable section, unless the owner is typing or has changed a field in it; without it the UI is complete.

- `/`: a chip per source (live or shadow, when it started or stopped, its spend against `policies.budget.run_tokens`, `stop_at`); **Needs you**; and **Repositories**, one card each.
- **Needs you** is worked out from each source's state as it is now, never from the escalations' history, so an item goes when its condition clears (a dialog gone, a session moved on): each open decision not yet answered (STATUS.md's Questions as one text decision, `questions.json`'s, those raised through the tools), and each session blocked on the owner with no decision of its own, usage-limited, crash-looping, stopped or failed. A `done` session is never listed. Each card names the repository and the session, how long it has waited, and the question rendered as Markdown, with its control: buttons for `yes_no` and `choose_one`, boxes for `choose_many`, a field for a `number` or `date`, and a text box only for `text`; the others may also be answered in the owner's own words. A decision with a default has a deadline field.
- A repository's card lists its coordinator (state, wakes, the latest, tokens per wake), its working sessions as rows (state, STATUS.md's first line as the session reports it, context, spend, last turn), its open requests with CI, those it delivered and the outside ones a coordinator watches (#36: author, draft, open discussion), its new items with a form that marks them seen, and its finished sessions folded into a count. It links to its console.
- `/console/REPO`: the repository's open needs, then its messages newest last, from every source: feed posts, escalations of its sessions, posts to its console (`agentd console post`, with their kind), its sessions' turns (`prompt` and `reply`, linked to the session), the owner's instructions and imported history; then a reply box. `/console/NAME` is a console under `consoles` the same way, its title from the configuration, its reply recorded for no repository. A reply is the owner's instruction for that repository (#33), `from: "ui"`, recorded in the live source whose run has the repository's coordinator, the run that reads it (else the first live source that configures the repository), through the same dedup as a console reply. Messages are kept in time order, the latest 200 per repository and source, so imported history never pushes out what is new; a shadow source shows only its own run's messages and items, not the owner's records again.
- `/session/SOURCE/NAME`: the session's row and needs, its latest turns, its STATUS.md rendered as Markdown (read only as a regular file, never through a link, and withheld whole when it matches a confidential pattern), and its last 40 events, newest first.

Markdown is rendered by a small built-in renderer over escaped text: paragraphs, headings, lists, code spans and fences, bold, and links to `http` and `https` only. No raw HTML passes. Sessions, questions and escalations go through the report's screening, so the UI leaves out what the report leaves out as confidential, and every message, turn and event is screened again. Every other text is escaped by `html/template`.

`agentd console --repository REPO import FILE` imports the old console's history once: one JSON object per line, `{"at": RFC 3339, "from": "...", "text": "..."}`, with `repository` to name another. Each line is a `feed` event of phase `imported`, mode `owner`, carrying its own time and author; a line already imported (the same repository, time and text) is skipped, a screened line keeps no text, and a file with a bad line imports nothing. The feed's fold ignores the phase; the console shows the lines in time order.

`POST /answer`, `/deadline`, `/seen` and `/reply` are the UI's writes. Each must also carry the UI's own `Origin` and the token the UI put in its forms, a random value made each time it starts, compared in constant time, and goes back to a path of the UI's own. The UI's referrer policy is `same-origin`, because under `no-referrer` a browser sends a form's `POST` with `Origin: null`; other sites still get no referrer. That stops another site in the owner's browser from posting. It cannot stop a program running as the owner on another of the owner's machines, which whois names as the owner too: it can read the UI, token and all. The UI limits what such a program can do: marking items seen hides nothing for good (`agentd items` lists every item); an answer or an instruction reaches a session only as data, with the fixed pointer line typed, never the text; and every mark and answer records the address it came from.

## Owner answers

A session asks the owner in two ways. Every running session writes its questions under Questions in STATUS.md, and that keeps working: the section is one decision of type `text`, its id `status-` and a hash of the section, so a reworded section is a new question. A session may also raise decisions in `questions.json` in its workdir, in #3's `raise_decision` shape: `{"decisions":[...]}`, each with an `id` (letters, digits, `-` and `_`, at most 32, and not `D` or `R` and a number, which agentd gives raised decisions and the owner's rulings), a `type`, the `question`, its `context`, `why`, `if_wrong` and `recommendation`, for a `choose_one` or `choose_many` the `options` (each a `key`, `label` and `consequence`), optional `limits`, `default` and `deadline`, and `blocking`, as for `raise_decision` (see *Case tools*). The file is read only as a regular file, never through a link, and at most 64 KiB. Each field has a length limit, and a file that breaks a rule is refused whole and logged once (the decisions read before stand). A changed file is a `decision` event, so a replay rebuilds what was raised. Its words are screened against `confidential_patterns` first: a decision that matches is logged by its id, type, option keys and whether it blocks, and the UI shows it without a form, so the owner answers it from the session itself.

The owner answers in the UI, under Needs you, below each decision (what is true today, why it came up, what breaks if the call is wrong, the recommendation): `answer` (`true` or `false`) for a `yes_no`, `choice` (an option's key) for a `choose_one`, `choices` (distinct keys, as many as its limits allow) for a `choose_many`, `value` (a number, or a date `YYYY-MM-DD`, within its limits) for a `number` or a `date`, `text` for a `text`, or, for every type but `text`, `other`, the owner's own words instead, which is delivered but does not settle the decision. A decision's default is applied only when the owner sets a deadline on it on the UI (a `deadline` event, mode `owner`, bound to the decision as it was asked) and that deadline passes with no answer: `agentd` then records the default as the answer, an `answer` event of the run's mode marked `by_default`, with the note `the default, applied at the owner's deadline`, and delivers it as any other. The session's own `deadline` is only shown as a suggestion. A question with no owner deadline is never decided for the owner. STATUS.md's Questions are shown as the file holds them now, and offered for an answer only while they are the section `agentd` last read, so an answer is to the text the owner read. The answer is checked against the decision as the log holds it and recorded as an `answer` event, mode `owner`, keyed by the decision id, with the address it came from and a hash of the decision as it stood. A decision reworded since, or an id raised again for another question, no longer has that answer and waits for the owner again. A blocking decision, or STATUS.md's Questions as they stand, no longer holds the session as `blocked-on-owner` once it has a binding answer, or any answer not yet delivered; an answer in the owner's own words holds it again once delivered. Answers are owner events, so one given through the UI's shadow source is delivered by a live run too.

In live mode `agentd` writes every answer to the session's open decisions to `answers.json` in its workdir, `{"answers":[...]}` in the same shape, through a temporary file renamed over it, then types `policies.answers.pointer`, one fixed line pointing at the file, through the typing safeguards and only into a session that can take a line (working, idle, or waiting on its own questions; never one showing a dialog, the trust prompt or the usage limit). The answer itself is never typed. At most one line is typed into a session per pass, so the pointer waits a pass after a resume, and an idle session is not nudged in the pass its pointer is typed. A file that cannot be written is tried again on the restart backoff, and a delivery cut short by a crash of `agentd` is made again. A session that is gone with answers waiting is restarted, once the file is written, with the pointer line in its prompt and the file's path in its facts; every later fresh session's facts name the file too. Each answer is delivered once: a delivery marks the answers it carried, by decision and the time each was given, so a replay delivers nothing again and an answer given meanwhile is still delivered. Shadow mode records the answers and the delivery it would make, and writes and types nothing.

## Consoles

With `policies.feed.enabled` (off by default), each repository's console receives a plain line for each thing the UI shows of that repository: a decision a session raised that does not block, each settled CI result of a delivered request's head (`success`, `failed`, `merged` or `closed`), each delivery, each merge `agentd` made (not one cut short, whose outcome is unknown; its request's CI record saying `merged` is not a second line, unless the CI watcher saw the merge before the merge's own outcome was logged), and each new item of that repository not yet seen. A blocking decision, and STATUS.md's Questions, are in the session's escalation, which goes to the same console, and are not fed again. The line goes through `policies.escalate.command`, when it is set, with `{console}` the repository's `console` (else its name) and `{message}` the line. Each line has a key that stays the same however often the state lists it, and is posted once: a `feed` event (no session, the run's mode) records the intent, then `posted`, `failed` or `gave-up`, or in shadow mode `would`, so a restart does not post it again. An intent with no outcome counts as posted, as an escalation's does: a post cut short by a crash or a stop, or whose failure could not be logged, is not made again, and nothing warns of it. A failed post is tried again on the restart backoff, `max_restarts` times. A pass posts at most 10 lines, and the rest follow in later passes. The first pass that feeds a repository records a `baseline` of its lines already there and posts none of them: when the feed is turned on, when a repository is configured later, or taken out and put back, and when the feed is turned on again after it was off (a `paused` event records once that the feed was off, or which repositories left). Each line is screened against `confidential_patterns` before it is posted or logged, then its text is cut so the line, with the reply it ends with whole, is at most 1000 bytes; a match posts a line naming only the repository, and the event records the pattern's number, not the text.

The owner replies in a console through `agentd console reply CONSOLE TEXT...`, which the console's tool runs with the reply (`--shadow` answers the shadow run's decisions). `SESSION ID ANSWER` answers a decision, read by its type: `yes` or `no`, an option's key, keys separated by commas, a number or date, or text; `other: ...` gives the owner's own words. A fed decision's line ends with the reply to type, its id written `ID@VERSION`: a reply to such a decision without a version, or naming one the decision no longer has, reworded or raised again since, is refused, so a late reply cannot answer another question. A blocking decision's escalation shows its id but not its version or option keys; it is best answered on the UI. `seen ID...` marks items seen. The reply goes through the same checks and records as the UI's `POST`, from `console:CONSOLE`, so it is an owner event that wakes a running `agentd` within the wake check. A reply is refused unless the session's, or the item's, repository feeds that console, so one repository's console cannot answer for another.

Any other reply is an owner instruction for the repositories that console feeds: a `seen` naming no known item, or words that do not begin with a session and one of its decisions or a word like a decision's id (`D3`, `R1@…`). A `seen` naming some known items and some unknown, or an answer with an unknown decision, stays an error. The instruction is an owner event (`instruction`, id `I…`, from `console:CONSOLE`), screened with the confidential patterns (its text, and its hash, left out when one matches), and the same words from the same console are recorded once until a wake has carried the earlier copy to each coordinator it is for; after that, they are the owner's again. It is due for each of those repositories' coordinators until a wake carries it (a wake an agentd crash cut short leaves it due), waking each once, and the pack lists it under `owner_instructions` until the coordinator has handled a wake that carried it; under `pack_bytes` instructions go last, oldest first, counted in `summarized.instructions`. Which instructions a coordinator was woken with is kept on its session, so a coordinator newly configured for a repository is shown that repository's earlier instructions, as it is shown its finished sessions and answers. A reply in a console under `consoles` is an instruction with that `console` and no repositories: it is due for no coordinator and wakes none. Any other console that feeds no repository takes no instruction. The console's tool is expected to run `agentd console reply` for every owner reply; its own inbox stays readable as before.

Sessions and coordinators post to a console, and read the owner's replies there, through `agentd` itself, so no outside console program is needed (#42). Both write to the log of the configuration given with `--config` (the default as for every command), so the old command names can point at the configuration the UI serves.

- `agentd console post [--kind KIND] [--from NAME] [--to SESSION] CONSOLE TEXT...|-` records a `message` event (mode shared, no session): an id `M…`, the console, the kind (`info` by default, `decision`, `delivered`, `ci` or `finished`), the author (`--from`, by default the name of the tmux session it runs in, else `cli`) and the text, Markdown, at most 16 KiB; `-` reads it from standard input. CONSOLE is a repository's console (its `console` key, else its name) or one under `consoles`; any other is refused. The text and author are screened with the confidential patterns: on a match both are left out and the event records the pattern's number, and the UI shows the post withheld. `--to SESSION` also types the text into that tmux session first, as one line (line breaks and tabs become spaces; any other control character is refused), by its exact name, with a nudge's checks: the session exists, its pane runs one of `policies.pane_commands`, and its screen shows no dialog (a `policies.dialog` pattern or a dialog's shape); a refusal records nothing. The event says it was typed.
- Session turns (#38): each prompt a session is given (the owner's or agentd's) and the text it ends a turn with, read from its transcript as the coordinator's pack reads them, is posted to the session's console as a `message` event of kind `prompt` or `reply`, from the session, with an id `T…` made from the session, transcript and line. It is posted right after its `turn` event, which is logged once by its line, so a restart posts none again (a crash between the two loses that post; it never repeats it). The text is the turn as read (at most 1200 bytes), screened whole with the confidential patterns (with the session's name), then cut at `policies.feed.turn_length` bytes (300 by default, 40 to 1200); a match posts it without its text, still from the session. A turn read more than an hour after it was written (from a transcript agentd reads for the first time, of a session it did not launch, or written while agentd was stopped for longer), or with no time, is logged but not posted, so a backlog does not flood the console. The console keeps the latest 200 turns apart from its other messages, so turns never push those out. Which turns are posted is `policy.feed.turns`: `all`, `prompts` (prompts only) or `off`, set on a session (`sessions.NAME.policy.feed.turns`, or a coordinator's `repositories.REPO.coordinator.policy.feed.turns`), else on its repository (`repositories.REPO.policy.feed.turns`), else `all`; a coordinator's are `off` unless its own rule says otherwise, since its pack sums them up. This does not depend on `policies.feed.enabled` and runs no command: the UI shows the turns. A shadow run posts none, since the live run posts the same turns, and a session whose console no repository or `consoles` entry has posts none.
- `agentd console inbox [--from NAME] CONSOLE` prints the owner's instructions for that console that this reader (`--from`, as above) has not read, oldest first, one compact JSON object a line (`id`, `text` or `withheld`, `from`, `at`), and records them read with one `inbox` event naming their ids, so a second call prints nothing. A reply that answers a decision or marks items seen is not an instruction and is not printed: it reaches the session through its answers file, as it always has. Each reader has its own reading. A coordinator still reads its instructions from its pack.
- `agentd console import` also reads the outside console program's lines: `ts` (Unix seconds, fractional), `from`, `kind` and `text`; a line's `repository`, or `--repository`, may name a console under `consoles`.

## Cases

A case is one issue. A session names its issue with `issue` (the number in its `repository`), and its case id is the issue item's id: forge, project and number, such as `gitlab/example-org/widgets#17`. The case is a projection of the event log, never a separate store. A `case` event carries exactly one of:

- **pack:** the facts document a restart or rotation handed the session, as compact JSON, with its hash;
- **report:** what the session's STATUS.md table says (the current item, its state, the next items), logged when it changes;
- **ruling:** the owner's one-shot restriction or waiver (`R1`, `R2`… for the case's life, kept verbatim), or the case closed or reopened. Closing expires the case's restrictions and waivers.
- **goal:** the issue's done-when items, recorded by the owner with `agentd cases goal CASE FILE` (`-` reads standard input) from the list under the body's "Done when" heading. Items are `A1`, `A2`… for the case's life: recording the goal again keeps an unchanged item's id, gives an edited one the next id and marks the old one superseded. Every item is the owner's to judge for now;
- **call:** a session's call of one of its case tools, accepted or refused with why (see *Case tools*). A call is a shared fact, read by the live and the shadow run.

The state comes from facts, never from the report, and from the sessions that name the case now (a session moved to another issue stays listed but no longer speaks for it): closed by the owner; needs you while a session waits on the owner or is parked; stopped by the budget; delivered once a session's work went out; working; or not started, which includes issue items no session works yet.

`agentd cases [--json] [--shadow]` prints the cases ranked (for the live run, or the shadow run's with `--shadow`): the owner's pins first, then what needs the owner, then the repository's priority this week, then triage urgency, the oldest waiting and the id; closed cases last. Pins and priorities come from `tracking.priorities`, the weekly review's file: `{"week":"2026-W43","repositories":[{"repository":"gitlab/example-org/widgets","priority":1}],"pins":["gitlab/example-org/widgets#17"]}`. A field agentd does not know refuses the file; without the file the ranking has no pins and no repository order. `agentd cases rule CASE restriction|waiver|close|reopen [TEXT]` records a ruling; a close's text is the demo line, saying how to see the change working, or `N/A: reason` (see *Review rounds*).

### Case tools

A session that works a case reports through tools, not prose. `agentd mcp --session NAME` serves them over MCP on standard input and output, bound to that session's case; the restart command's `{mcp}` starts it for every session agentd launches, and the fresh session's facts name the tools, the current done-when items and the active rulings with their text. A call never names a case, and an argument the tool does not take is refused, so one session's server cannot write another's case. That binding is against mistakes, not against the session: a session with a shell can read its own `--mcp-config` and start `agentd mcp` for another session, as it can write the event log, so the server is not a security boundary between sessions run as one user.

- `report_progress(summary, approach, items[{id, status, evidence[]}], next_action, risks[], acknowledged[], goal_restatement[{id, text}])`: item ids must be the case's current ones; a status is `not_started`, `in_progress` or `met`, and `met` needs evidence. Evidence is a typed reference agentd checks, never prose: `{"kind":"commit","sha"}` on the session's branch, `{"kind":"gate","sha"}` where a gate agentd ran passed, `{"kind":"file","path","line"}` inside the worktree. `{"kind":"finding","id"}` names a review finding of the case that has its disposition. `ci` references are refused until agentd records CI results for evidence. Every active restriction and waiver the session has not acknowledged since its launch must be in `acknowledged`: a launch is a fresh context, so its first report acknowledges them all again. An evidence reference carries only its kind's fields. The restatement is compared with the goal: an item left out or worded otherwise is a drift flag on the case, and the report is still accepted.
- `raise_decision(type, question, context, why, if_wrong, recommendation, options[{key, label, consequence}], limits, default, deadline, blocking, supersedes)`: a decision for the owner, which `agentd` numbers `D1`, `D2`… for the session and replies with its id. `type` is the narrowest that fits: `yes_no`, `choose_one`, `choose_many`, `number`, `date`, or `text` only when the answers cannot be listed. A question wider than it needs is refused with the type to use: a `text` that names its own options (`(a)`, `b)`…) or asks yes or no, a `choose_one` or `choose_many` of only yes and no, or of one option. `limits` is `{min, max}`: numbers for a `number`, dates `YYYY-MM-DD` for a `date`, counts of keys for a `choose_many`. `default` is a string: `yes` or `no`, a key, keys joined by commas, a number or a date, and it must be an answer the decision takes. A question the same as one the session has open is refused. An answer in the owner's own words keeps the decision open: the session raises it again with `supersedes` naming it, which closes the old one. The decision joins the session's open decisions and is answered and delivered as those of `questions.json` are (see *Owner answers*); the case record keeps every raised decision, the superseded too.
- `request_step(kind)`: `review`, `delivery` or `stop`. The request is recorded with the facts (for delivery, whether a gate agentd ran passed on HEAD) and never moves the case.

A refused call is logged with the wording of why, the session's values left out, and its arguments' hash; its reply says what to fix, values included. A call of a tool the server does not have, or a message it cannot read (over 1 MiB, or not JSON-RPC), is answered as a protocol error and not logged, since nothing reached the case. `agentd cases` shows the latest accepted report beside the facts, with its drift; the item from STATUS.md stays as a fallback for a session without the server, marked unverified.

### Review rounds

Reviewers advise; one party decides. A session configured with `"role": "reviewer"` is offered only `review_findings`, and one with `"role": "judge"` `judge_dispositions` and `raise_decision`; both need the case they serve (a repository and an issue). Each call is a case event, so the rounds are part of the case record. Two reviewers' calls checked against the same round both reach the log, but only the first opens the round; the other is told nothing of it was recorded.

- `review_findings(findings[{id, title, severity, items[], widens_scope, paths[], consequence, suggestion}])`: one call is one round, refused while the last round awaits its dispositions. agentd numbers a new finding `F1`, `F2`… over the case's life. A finding that comes back keeps its id: the reviewer names it (the facts list every finding with its id, its disposition and the judge's latest plan), or gives it again with the same paths and a title like its own. An id the case does not have, or one given twice, is refused. Each finding names the done-when items it bears on, or sets `widens_scope`.
- `judge_dispositions(dispositions[{finding_id, disposition, reason}], plan[{id, step}], lessons[])`: one disposition, `adopt`, `decline` or `defer`, with a reason, for each finding of the latest round, once a round. A finding that widens the scope cannot be adopted: the judge defers it and asks the owner with `raise_decision`.

A round that brings no new findings stops the loop: `converged` when it had none at all, `repeating` when every finding came back. A finding given in three rounds in a row since the last reset also stops it as `repeating`, though the round brought something new. A loop still finding new things stops at the backstop: `policies.rounds.max` rounds (default 3), or the count the owner set with `agentd cases rounds CASE N`, which also resets a stopped loop and counts from there. Reopening a case resets it too; nothing else does; a stopped loop takes no more reviews, and `repeating` and `backstop` mean the case needs the owner. Every stop proposes lessons: the judges' since the last reset and, at a park, what the facts show. `agentd cases` shows the round, the findings awaiting the judge, the stop and the lessons; agentd writes nothing into the repository.

A close is refused while a finding has no disposition. It records each current done-when item as `machine` (an item the owner confirmed machine-checkable; met when its latest report met it with checked evidence) or `owner`, the demo line or N/A with its reason, and every lesson the rounds proposed.

The facts of a fresh session carry the findings and the plan, never the case's progress reports: a reviewer sees the work, not the worker's account of it.

## Publishing

`agentd report --out PATH` writes the report the tracking site publishes, rebuilt from the event log alone. It is JSON: `schema` (`agentd-report/1`), `written_at`, `host` (this machine's name, or `--host`), `mode`, `repositories`, and two one-line digests: `digest` counts only what anyone may see, `owner_digest` counts everything and is for the owner. Each repository, keyed `platform/path` as in the tracking manifest, holds its `cases` (each configured session's state, since when, and its STATUS.md first line), its `deliveries` (requests opened, found already open or merged, or recorded with `mark-delivered`, each filed under the repository it went to), its `questions` (each session's open Questions, the STATUS.md text as last posted to the owner) and its `items`, the new items (see New items): each one's id, kind, title, link, when it happened and was first seen, whether the owner saw it, and its triage's needs, urgency and summary while the triage holds for its text, and nothing else (not who wrote it). An item stays until the owner has seen it and seven days have passed since it was first seen. Mail findings with no single repository are grouped under an empty `repository`. Every entry carries `owner_only`: questions always, everything derived from mail always, items of a repository `agentd` is not configured for (the site cannot tell who may see them), every entry of a repository with `owner_only` set, and sessions that name no repository, grouped under an empty `repository`. A repository whose every entry is for the owner only is marked `owner_only` itself, and repositories that share a forge and project share their entry, which is `owner_only` when any of them is and left out whole when any of their names matches a confidential pattern. Sessions no longer in the configuration are not reported. The report is for one mode, `live` by default or `--shadow`, read as a run of that mode replays the log, so a live report never shows what a shadow run only would have done; a shadow report lists the requests it would have opened as `would-open`. Every text is screened against `confidential_patterns` as they are when the report is written, so a pattern added later still applies to old events: a matching first line is left out, a question, delivery, item, session or repository whose text or name matches is left out whole, and a question whose text was withheld when it was posted is left out. The file is written to a temporary file beside it, synced and renamed over it, so the site never reads half a report; it is readable by its owner only.

## Tests

```bash
./bin/check
```

`bin/check` runs `gofmt -l`, `go vet` and `go test -race`, and fails when Go is missing rather than passing without it. CI runs the same script on every push.

The tests run the supervisor against a fake tmux, forge, git and clock over simulated hours. Each failure the old tools showed is a test: a crash loop parks for the owner and escalates once; a session blocked on the owner is not nudged; an escalation is posted once, and reworded Questions are updates to it; nothing is killed but a rotation, a budget stop or an ended session; shadow mode never acts.
