# agentd-kit

Version 1.0. `agentd` started as phase 1 of a supervisor inside [agentic-kit](https://github.com/PaulSnow/agentic-kit), a fork of Wolf McNally's agentic-coding-starter, and moved here to be its own product: a service for the whole machine that supervises sessions across many repositories, which does not fit a template that governs one repository. `agentd version` prints the version.

## agentd

`agentd` keeps unattended Claude Code sessions going and delivers their work. The deterministic management, watching, restarting, nudging, delivering and routing, runs in this program and runs the same way every time. A model is called in only for judgment, through escalation. It replaces the Python session supervisor in phases; this is phase 1: the event log, the session state machine and the supervisor's policies.

## Running

`agentd` needs Go 1.21 or newer and nothing else.

```bash
go build -o ~/.local/bin/agentd .
```

```bash
agentd run --shadow
```

```bash
agentd run
```

```bash
agentd status
```

`run` reads `~/.config/agentd-kit/agentd.json` (`--config` for another file), replays its event log, then passes over every configured session each `poll_interval`. `--shadow` observes everything and acts on nothing: each action is logged as a `would` event instead (a fetch, which writes nothing to the remote, is the one exception). `--once` makes one pass. `status` prints one row per session from the event log, for the latest run's mode or `--mode live|shadow`: every configured session, those with no events yet too, with the model it runs, why a delivery waits, the escalations given up on, and any action cut short. `config` prints the resolved configuration. `mark-delivered SESSION WORKTREE REF` records a delivery made before `agentd` took over, so it is never repeated. `clear SESSION` lifts a crash-looping session's park. Both write to the event log, and a running `run` reads what they wrote at its next pass. `inventory` lists every repository in the tracking system's manifest, with its open issues and requests and the machines holding a clone, from the tracking snapshot. `report --out PATH` writes `report.json` for the tracking site from the event log (see Publishing). `ui` serves the owner's web UI (see The owner's UI).

Slow work runs in workers, so it never holds up the pass over the other sessions: each delivery (its fetch, gate, pushes and forge calls) and each escalation command runs in a goroutine of its own, one per delivery or escalation at a time, and the next pass starts no second one while it runs. A worker works on a copy of its session's memory: it appends each event to the log as it happens and hands it to the loop, which applies it to the session at its next pass, so the session's state stays the loop's alone, and an outcome a worker logged survives a crash of `agentd` before the loop applied it. A worker appends and queues each event under one lock, so the loop applies them in the order the log holds them; the Questions and dialog escalations carry the episode they were made for, so one that settles after its dialog went away or its Questions closed settles nothing. A delivery that is held, or waiting out its backoff, starts no worker. A failed append stops that worker's job, not the pass. The next pass comes after `poll_interval`, or sooner when another process has appended an owner record to the log (`agentd clear`, `mark-delivered`), which `run` looks for every 15 seconds, so the owner's word is acted on within a minute; what a worker finished is in the log already and is applied at the next pass. `run --once` waits for its workers before it stops; a `run` told to stop waits up to a minute, and a job still running then is cut short, which the next start warns of.

`run` is meant to live in a tmux session of its own, under `nice -n 19`. Only one `run` may use an event log: it holds an exclusive lock on the log's path, with symlinks resolved, plus `.lock` (by default `~/.local/state/agentd-kit/events.jsonl.lock`), and a second `run` exits with an error naming that file.

## Configuration

The configuration is JSON, not the YAML the issue sketched: `agentd` is standard library first, and Go has no YAML parser in it. Features live in this repository; the owner's specifics live outside it, in the config file. [`agentd.example.json`](agentd.example.json) shows every field; unset fields take the defaults in `config.go`, which are the Python supervisor's numbers. Relative paths in the file are relative to the file's own directory, not to where `agentd` runs; `~` expands to the home directory, and `~user` is refused. Every session's `workdir` and `cwd` must exist when the configuration is loaded, so a path that resolved wrongly fails at start, naming the session. An escalation command given as a bare name is found on `PATH`. Paths given on the command line (`--config`, `--log`, the `mark-delivered` worktree) are relative to the working directory.

- `timeouts`: how long one external command may run: `tmux` (default `10s`) for each tmux call, `forge` (default `2m`) for each git, glab and gh call, `escalate` (default `2m`) for the escalation command. Each command runs in a process group of its own, and one still running at its timeout is killed with everything it started; its action fails with an `error` event and the pass goes on. git runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and empty `GIT_ASKPASS` and `SSH_ASKPASS`, so it fails rather than waiting for credentials. It also runs with `GIT_NO_REPLACE_OBJECTS=1`, `core.fsmonitor`, `core.untrackedCache` and hooks off and literal pathspecs, so the worktree's config cannot start a monitor or a hook in `agentd`'s environment or answer for files from a cache. Clean and smudge filters, `core.sshCommand` and a credential helper that the worktree's config names still run; that config is the session's to write.
- `confidential_patterns`: regular expressions, in Go's [RE2 syntax](https://pkg.go.dev/regexp/syntax) and case-sensitive unless they start with `(?i)`, for text `agentd` must never post. An escalation whose text matches one, including Questions copied from `STATUS.md` (screened whole, then cut to 2000 bytes on a UTF-8 boundary), is replaced by a generic message that names the session and says the details were withheld; a `skip` event with `filtered` records it, without the matched text, and the event log never holds the original. A `STATUS.md` first line that matches is logged as withheld. A merge request whose title or text matches is not delivered, and neither is a branch whose name, or any commit message in `origin/<target>..HEAD`, matches; these are screened before the branch is named anywhere. One skip and one escalation say so, without the text, and delivery waits until the text or the patterns change.
- `repositories`: each forge project `agentd` may write to, with its `forge` (`gitlab` or `github`), its `host` (default `gitlab.com` or `github.com`), the `transport` delivery pushes over (`ssh`, the default, or `https`), its `project` path, the `console` escalations go to, the `assignee` for opened requests, and its `policy` (see *Repository policy*): what delivery may write (`delivery.allow`: `push`, `open`, `comment` for a console thread's outcome, and `issue` for an issue Go opens for work that names none, #69), and the `gate`: `gate.argv`, the argv `agentd` runs in the worktree before it pushes (a relative command such as `./bin/check` is run from the worktree), bounded by `gate.timeout` (default `10m`), with a scrubbed environment: `PATH`, `LANG`, `TMPDIR`, `HOME` set to a new empty directory removed after the gate, and the variables `gate.env` names, never `HOME`, `SSH_AUTH_SOCK`, a `*_TOKEN` or a `CLAUDE_*` variable (naming one is refused at load). A gate that needs a cache under the real home, such as Go's module cache, gets it through `gate.env` (`GOMODCACHE`, `GOCACHE`). The gate runs as `agentd`'s user, so files under the real home stay reachable by path; each gate event lists, under `reachable`, what it could still find: the common credential paths (`~/.ssh`, `~/.netrc`, `~/.config/gh` and the like), each configured account's `token_file` and `config_dir` (named by account, never by path), and the ssh agent's socket (`$SSH_AUTH_SOCK`). A HOME the gate left read-only is made writable and removed; one that cannot be removed is an `error` event. The last 64 KiB of its output is kept, and the end of it goes on a failed gate's event unless it matches a confidential pattern. A repository whose policy allows `push` or enables merge without `gate.argv` is refused at load.
- `repositories.<name>.policy.gate.paths`: files or directories, relative to the worktree and without wildcards, that are part of the gate besides the script its argv names (every relative path with a `/` in the argv). The gate that runs must be the target branch's (#3: authority comes from the target branch). Before the gate runs, and again after it, `agentd` asks the configured URL (as for a push) for the target branch's commit, never trusting `origin/<target>`, which the session can move. Each gate path must be at the commit being delivered as the target has it, and on disk too: the bytes, the file modes and the set of files are compared, ignored and untracked files included, and symbolic links are not followed. git's index flags and status are not consulted. A session that changed one is refused delivery of that commit, with a skip naming the paths and one escalation, and its gate is not run; the owner changes a gate through the normal review and merge into the target. Build output kept under a gate directory therefore counts as a change, so name files, not output directories. A gate path that is a symbolic link on the target pins the link, not the file it points to, so name that file too. A gate file changed while the gate runs and put back before it ends is not seen; one still changed at the end is refused. A worktree whose git config has a remote named after the configured URL, which git would use in its place, is refused for the gate check and the push. A gate none of whose paths the target branch has is pinned by nothing and is refused until `gate.paths` names its files (a `make` gate names its `Makefile`, `sh check.sh` names `check.sh`).
  A repository with `owner_only` set has every entry of the published report marked for the owner alone.
- `ui`: the owner's web UI: its `address`, the `hosts` it answers to, the `whois` command, the `owner` login, other configs' `logs` to show and `shadow` (see The owner's UI).
- `accounts`: each Claude login a session may run under, by name, with its `config_dir`, its `token_file`, or both. A restart under an account sets `CLAUDE_CONFIG_DIR`, and for a token account `CLAUDE_CODE_OAUTH_TOKEN`, which the launching shell reads from the token file as the command starts: the launch never puts the token in `agentd`'s memory, the event log, or any process's arguments (a usage reading reads it for that reading and drops it; see Account usage). The launch fails closed: if by then the file cannot be read or holds only white space, the shell stops before starting Claude, so it never falls back to another login. A token file that is missing, blank or white space only, or readable by group or others is refused at load and again before each restart; the session is not restarted, one skip and one escalation say why, and `agentd` never falls back to another account. An account's transcripts are read from its `config_dir`'s `projects` directory. Its `usage` is how its plan usage is read (see Account usage): `auto` (the default), `endpoint`, `headers` or `off`.
- `usage`: the reading of the accounts' plan usage and the placement by it (see Account usage): `enabled` (off by default), `every` (15m), `limit` (90 percent), `api` and `model`.
- `tracking`: the owner's tracking system's output files, which `agentd` reads and never writes: the repository `manifest` (a JSON list of `name`, `platform`, `path`, `active`, `audience` and an optional `note`) and the `snapshot` (each repository's issues, requests and commits, each machine's clones and local work). The manifest is the repository list; a repository is identified by its platform and path, ignoring case. `mail` names the tracking system's mail findings file, beside the snapshot (see New items). Each file is read strictly: one missing, not JSON, or of a shape `agentd` does not know (a field it lacks, a list where it expects an object, a manifest that is not a list, a snapshot without `AsOf` or `Repos`, a manifest entry, snapshot repository or clone on a platform other than `github` or `gitlab`, an issue or request state it does not know, a repository listed twice in either file) is an error naming the file, never a partial read.
- `sessions`: each tmux session, its `workdir` (holding `BRIEF.md` and `STATUS.md`), its `cwd`, its `account` (one of `accounts`; unset means the default login), its `repository`, optional `deliver` specs, and an optional `hold` reason that stops delivery. A session naming an unknown account is refused at load.
- `policies.models`: the model each kind of session runs, as `{model}` in the restart command: `work` (any session that is not a reviewer or judge), `reviewer` and `judge` (configured ones, and those the request loop starts). A repository's `sessions.work_model`, `review.reviewer_model` and `review.judge_model` are taken over these. A kind with no model runs the command's own default, as before: a `--model {model}` pair or a `--model={model}` argument is then left out, and any other `{model}` becomes empty, so the arguments after it keep their places. Put `{model}` in an argument of its own, as the default does: inside a longer one, such as a script, an empty model leaves that script's `--model` taking the next word. A model set while restarts or context rotation are on (both launch through the restart command) and the command has no `{model}` is refused at load, as is a work, reviewer or judge model outside a repository's `sessions.models`. `agentd status` shows each session's model, `default` for none.
- `policies.restart`: restart a gone session with `command`. By default that is `claude` under a login shell with a fresh session id and a prompt built from the session's progress (see *Context and spend*): a fresh context, never `--continue`. `{brief}`, `{status}`, `{session_id}`, `{mcp}`, `{prompt}` and `{model}` are substituted as they are, so the default passes the id, the server, the prompt and the model to bash as arguments of their own (`bash -lic 'exec claude ${4:+--model "$4"} --session-id "$1" --mcp-config="$2" "$3"' agentd ID MCP PROMPT MODEL`), which keeps them data whatever characters they hold; a command of your own should do the same, and should pass `--session-id {session_id}` so `agentd` knows which transcript to measure. `{mcp}` is the `--mcp-config` document that starts the session's case server (see *Case tools*), or one with no servers for a session that works no case. It keeps Claude Code's permission prompts; add `--dangerously-skip-permissions` to your own `command` only if you choose to. Restarts back off exponentially from `backoff_initial` to `backoff_max`, counted within `window`. A session gone while its `STATUS.md` has open Questions is `blocked-on-owner` and not restarted until the owner answers them (see *Owner answers*). The command ends with Claude itself, so the pane dies when Claude exits; `agentd` starts sessions with tmux's `remain-on-exit`, so a dead pane keeps its exit status (`#{pane_dead_status}`) and last screen, and is restarted with `respawn-pane`, which tmux refuses for a live pane.
- Crash loops park. Each disappearance of a session `agentd` saw alive or restarted is a `crash` event with its cause: the exit status when tmux kept it, and the hash of the last screen. A restart that fails is a crash too, its error the cause. A crash whose cause repeats an earlier one, or the `max_crashes`-th crash (default 3) however far apart, parks the session as `crash-looping` with one escalation. A parked session is never restarted, nudged or typed into, and being seen alive again does not clear it: only `agentd clear SESSION`, which writes a `clear` event that a running `agentd` reads at its next pass.
- `policies.nudge`: type `message` into a session whose screen has not changed for `stall`, at most `max` times per idle episode, then escalate once. A session with open Questions is never nudged. With nudging on, a session that ended its turn with work left is `idle` at once, not `working`: its last folded turn is a summary made since it was last launched, its transcript's last line, when read, ends the turn, it has a STATUS.md, and its screen ends at the input prompt (an empty `>` or `❯` line, or one showing only Claude Code's `Try "…"` placeholder, among the last six, and no `esc to interrupt` within the four lines above those; text typed at the prompt, a placeholder of other wording, or a status line taller than the window pushes the prompt out and leaves the session to `stall`). Once `settle` has passed since the turn ended and since the screen last changed, `agentd` types `continue_message` (one line) followed by the progress facts a restart prompt hands, read from STATUS.md (`why` `continue`, the brief, progress file, item, state, next steps and last merge; not a case's tools or rulings, which the session's context holds): a nudge, counted against `max`, typed once per ended turn (a turn whose end the transcript dates within the second or two the typing takes is taken as before it, and waits out `stall`). A turn the session ends after any nudge answers it, however soon: the nudge count and the idle clock start again from its end. The ended turn is judged from the transcript agentd launched the session under, while the transcript's last line is the newest file's, so another Claude writing in the same directory can hide an ended turn. Facts that match a confidential pattern are left off the line, and the `nudge` event records the message and the facts' hash, never the facts. A session continued `max` times in a row since its launch with the same facts is escalated once and then waits out `stall` like a turn that has not ended; `max` 0 continues nothing. A rotation due at a checkpoint the session reached comes first: its turn is not continued while the rotation waits out the grace or its backoff, unless the rotation has given up or its account refused it. DONE, open Questions and a blocking decision are judged first, so none of them is continued, and a turn that has not ended waits out `stall` as before. A CI fix (`policies.ci`) waits for a session to be DONE or idle, so it replaces a session whose turn ended with work left at once.
- `policies.usage_limit`: the screen `pattern`, a regular expression like every pattern in the configuration, that means wait; when it clears, `resume_message` is typed once, and only into a session that can take it: never one that is DONE, has open Questions, or shows a dialog.
- `policies.answers`: the `pointer`, one fixed line typed into a session when the owner has answered it, pointing at `answers.json` (see *Owner answers*).
- `policies.trust_prompt`: the `pattern`, a regular expression that must match a whole line of the visible screen, less indent and box border, so it is the prompt's own question and not the words quoted in a diff, a dialog or a session's output (by default it matches both "Do you trust the files in this folder?" and "Is this a project you created or one you trust?", the latter with the rest of its paragraph on the line; a pattern of your own replaces the default, so it needs both wordings), and the `keys` that confirm the selected option (by default `Enter`; only `Enter`, `C-m` and `KPEnter` are accepted, because any other key could move the cursor, pick an option, or cancel and exit). The menu is answered by the option that says Yes, found by its text, never its position: Claude Code has preselected "Yes, proceed" first in one version and "No, exit" first in another, and has drawn the options numbered (`1. No, exit`) and, now, without numbers; a menu without numbers is the last run of lines above the footer, at most nine, one of them carrying the cursor. When the cursor is elsewhere, `agentd` sends only the arrows that move it to that option, and sends the confirm keys on a later screen that shows it selected, so `Enter` never goes while a rejecting option is selected. Only the options below the last question line count, so a menu left higher on the screen is not read as its. A menu without a visible cursor (`❯`, or `>` on a terminal without Unicode), the `Enter to confirm` footer or exactly one accepting option gets nothing, with one skip, and the owner is told once the same screen has lasted a pass; so are keys still showing the same prompt after `policies.nudge.stall` (counted whether nudging is on or not). A relaunch forgets the screen the keys went to, so the new Claude's prompt is answered afresh. It is answered only when the pane runs in the session's configured `cwd` and any directory the dialog prints, as a whole line, is that one, compared with symbolic links resolved; for any other directory the owner is told once and nothing is sent. A printed path that wraps, or has a space, is not read as one: a wrapped one only makes `agentd` refuse, and the pane's own directory is still checked. Before launching a session `agentd` reads Claude Code's state file for its login (`<config_dir>/.claude.json`, or `~/.claude.json` with no account) and, when neither the directory nor one above it is trusted there, tells the owner once per session and directory how to trust it ahead; the launch goes on, and shadow mode says what it would tell. A missing or unreadable file says nothing. Keys are sent at most once per screen hash, only when the prompt is on the visible screen, only in the session's start phase (since it was first seen or last restarted, before it was seen in any other state, or later while it has not been seen ready since its launch, at its input prompt or with a transcript written, and the screen shows the trust menu whole: a prompt can show after a screen `agentd` did not recognise), and never to a session with open Questions. The `trust` action records the directory. It is the one menu `agentd` ever answers; after the start phase a menu on screen is a dialog. No line is typed, and no key but the trust keys sent, while the visible screen shows the trust prompt's question: a nudge, a resume, an answer pointer, a decline or `console post --to` is skipped or refused, whatever the dialog patterns say and even with trust answering off, while a pattern is set; a blank line never matches it. A session whose input prompt `agentd` never recognises and that writes no transcript is never seen ready, so a trust menu drawn whole in it is answered, in its own directory only, rather than taken for a dialog.
- `policies.dialog`: `patterns`, regular expressions for a Claude Code permission or confirmation dialog on the visible screen (by default `Do you want to`, a `❯ 1.` option menu, and `Enter to confirm`). A session showing one is `blocked-on-owner`, the reason names the pattern, and nothing is typed or sent to it. One escalation is posted per dialog episode (from the first pass that shows a dialog to the first that shows none, whatever the screen does meanwhile), and at most one per 30 minutes per session. A screen with a dialog's shape is one too, with no pattern needed: a line ending in a question mark (less indent and box border; not a quoted `>` line or a session's own `⏺` line) followed within four lines by options numbered 1 and 2, one of them under the `❯` cursor, which is how a subagent's permission dialog shows as well as the main session's. A session whose screen has not changed for `stall` while its transcript's last turn is an assistant tool call is treated the same way: it is most likely waiting at a permission prompt. `decline_after` (off, `0s`, by default) declines a dialog still showing that long: `Escape` is sent once per episode, through the typing safeguards, which a refusal lets the agent adapt to; only a screen with a dialog's shape is declined, never one a pattern alone matches. The time counts from the first pass that showed the dialog's shape, and a dialog is declined only once its escalation was posted, which then says when it will be; a dialog still showing at a later pass is escalated once more. Nothing ever approves a dialog: `Escape` is the only key, and it is not configurable.
- Stillness is judged without timers: the screen hash that `stall` counts from, and that every typing action compares before it types, is taken with the spinner glyph and its verb, elapsed-time counters (`4m 12s`), token counts (`↓ 8.1k tokens`) and clock times replaced by fixed text, so a session stopped under a running counter is still. Timings in a session's own output read as fixed too. The other side of it: a long tool call whose screen shows only a moving counter, with no new transcript turn, is still too, and after `stall` is escalated as probably waiting at a permission prompt. A parked session is never typed into.
- `policies.pane_commands`: the values of tmux's `#{pane_current_command}` that mean the pane runs Claude Code (default `claude`, what a native install reports; an npm install reports `node`). Before typing a line or sending keys, `agentd` asks tmux what the pane runs, and skips with one `skip` event naming the command when it is anything else, such as the shell left after Claude exited; then it reads the screen again, and types nothing, with a skip, if the screen changed since the pass read it. A pane that has run anything else for longer than `policies.nudge.stall` is escalated once.
- `policies.context`: rotate a session whose context is over `threshold` tokens (default 120000) once `grace` (default 5m) has passed since a merge it reached whose subject matches `checkpoint` (default `^Merge [#!][0-9]+\b`, an issue's merge, not a merge of the base into a branch or a pull); `enabled` by default. See *Context and spend*.
- `policies.budget`: `session_tokens` and `run_tokens`, caps in input-equivalent tokens on one session's spend and on every session's together, and `stop_at`, an RFC 3339 time. Zero or absent is no cap. Reaching one stops the session (see *Context and spend*).
- `policies.escalate`: the command run once per escalation key, with `{console}` and `{message}` substituted. It is optional: without it an escalation, and a feed line, is logged only, as its `action` (or `feed`) event, and the UI shows it in its console. `default_console` receives the escalations of sessions that name no repository and match no `consoles` entry; without a command, a session whose escalations would go to a console no repository or `consoles` entry has is refused at load, since they would show nowhere.
- `ops`: the operations console (#63, *The operations console* below): `console` (its name, default `ops`), `supervisors`, every agentd process on the host by name, the page included, each `{"config": PATH, "tmux": SESSION}`, the config it runs and the tmux session it runs in, and `repo`, the agentd-kit clone an install builds from; `binary`, the agentd an install replaces, defaults to the running one. One agentd process, the one whose config has the block, serves the console for all of them. It is checked at load: at least one supervisor, each config a file that exists, each tmux session a plain name of its own, `repo` a git clone, and a console name no repository's console has. The console is listed as one under `consoles`, titled Operations.
- `consoles`: consoles that are no repository's, `{NAME: {"title": "...", "sessions": ["glob", ...]}}`: a general chat console, an infrastructure console, a project without a forge. The UI lists each after the repositories; posts and replies work for it; a reply there is an instruction for no repository, delivered only to a session it addresses. A session that names no repository and matches one of its `sessions` globs (the first console by name) escalates to it. A name a repository, or a repository's `console`, already has is refused at load.

A session's Questions section has one open escalation at a time. It opens when Questions become non-empty and the escalation is posted once. While they stay open, each change to their text posts one short `update` to the same console that names the session, says the questions changed and gives the new text (filtered like an escalation), at most one per change and one per pass, and at most one per 30 minutes per session, carrying the text current when it is posted; rewording never posts a new escalation. When the section empties, or the session is DONE, the escalation closes, and a later non-empty Questions section posts a new one. The episode number and the text last posted are rebuilt from the log, so a restart re-posts nothing and a change made while `agentd` was down is one update.

## States and evidence

A session is `starting`, `working`, `idle`, `blocked-on-owner`, `usage-limited`, `done`, `failed` or `crash-looping`. Every transition comes from evidence and names it in the log:

- whether the tmux session exists, by exact name, and whether its pane is dead, with its exit status;
- the hash of the visible screen plus the 40 lines of history above it, and how long since it changed, with a nudge's own echo not counted as change;
- the patterns (usage limit, trust prompt, dialogs) matched against the visible screen only, so a prompt that has scrolled away is never answered;
- what tmux says the pane is running, asked before anything is typed;
- `STATUS.md`: its first line, whether its last line is `DONE`, and whether its Questions section asks anything: a line that says none are open (`none`, `(none)`, `none open`, `No open questions`, `n/a`, or a parenthesised line such as `(none open; answered on ...)`, where `none` is followed by punctuation and a reason, wrapped or not up to the line that closes it, over plain lines only) asks nothing, unless it has a question mark or asks for something (`but`, `need`, `please`, `must`, `until`, `blocked`, `waiting`, `approve`); every other line under the heading counts; a line inside a ```` ``` ```` or `~~~` fenced code block is content, never a heading, so a `# comment` in a snippet neither ends nor starts a section (a fence still open at the end of the file is taken as a typo, and the file is read without fences);
- the transcript's last turn, role and stop reason, read from the tail of the newest transcript for the session's directory when one exists. A fresh transcript keeps a static screen from counting as idle, as during a long tool call. Sessions sharing a directory share transcripts, so this is supporting evidence only.

## Context and spend

A Claude session re-reads its whole context on every model call, so a session that has run for hours spends most of its tokens re-reading a context it does not need: its progress is in its progress file, the issues and the branches. `agentd` keeps contexts small.

- **Measure.** A worker reads each session's transcript, only the bytes appended since the last read, with its subagents' transcripts (`<id>/subagents/*.jsonl`). A call written as several lines with one message id counts once, with its last line's usage. The context is the latest main-chain call's input, cache write and cache read; the spend is `input + 1.25 × cache write + 0.1 × cache read + 5 × output`, over every transcript measured for the session. A `usage` event records a transcript's totals when they change. The transcript is the one `agentd` launched the session under (`--session-id`); for a session it did not launch, or whose launched transcript has not appeared 10 minutes after the launch (a command that does not pass `{session_id}` on), the newest transcript in the session's directory is taken and marked a guess. A guess counts only while it is the session's current transcript. When a launched transcript never appears, live mode skips and escalates once: it does not rotate or hold a session to its budget on a guess. A transcript with no call yet is unknown, shown as `?`, never zero. `agentd status` shows each session's context, spend and rotations.
- **Rotate at a checkpoint.** A checkpoint is a merge: the newest merge commit reachable from the head of the session's `cwd`, logged as a `checkpoint` event when a newer one appears (the first one seen is a baseline and is not a checkpoint; going back to an older merge, by checking out an older branch, is none, and so is a merge whose subject `policies.context.checkpoint` does not match). A session whose context is over `policies.context.threshold` is rotated once `grace` has passed since a checkpoint it reached after it was launched, so it has recorded the merge first: `respawn-pane -k` starts the restart command in its pane with a fresh session id. Never for a session that is starting, waiting on the owner, usage-limited, done, stopped or parked, and never twice for one merge. A rotation is a `rotate` action, not a crash, and it does not count toward the restart limits or the backoff. Live mode rotates only on a transcript it launched; shadow mode also records the rotation it would make on a guess.
- **Rotate a work session at the end of its round.** A `work` session agentd started has a second checkpoint: the end of a turn it took since it was launched, whether it reported DONE or ended a fix round with work left. Over the threshold it is rotated at once (DONE, once its delivery is recorded: a delivery held or waiting, on a dirty worktree, a missing request text or a CI fix, holds the rotation off until it settles), never mid-turn: its last turn is an end-of-turn summary, its transcript ends the turn and its idle prompt shows. The screen is read again first, as before typing a line, so a line typed meanwhile is not cut off; a `console post --to` that lands in the moment between that read and the restart is still lost with the old session. It is rotated once for a turn, and the fresh session, under the threshold, is not rotated again for its own first turn. Its rotation's facts add its `branch` and the `instruction` it was last given: the latest prompt in its transcript that is not withheld and not one of `agentd`'s own lines (the restart prompt, the nudge, continue, resume, answers or CI pointer), as its turn was logged, cut at 300 bytes. The next instruction posted to it with `console post --to` lands in the fresh context. Over 20 rounds of 30 calls each adding 1k tokens to a 20k start (the measured shape of the largest work session), a test that models the calls' context, and rotates where `agentd` does, puts the average context per call at 80.5k rotated against 320.5k not.
- **The restart prompt.** A rotated or restarted session's prompt is a fixed instruction followed by one compact JSON document of what `agentd` recorded: why (`rotation`, `restart`, or `answered` with `answers`, the path of `answers.json`), the brief's and the progress file's paths, the current item and its state, the last merge, the next items, and for a rotated work session its branch and last instruction. The items come from the first table in `STATUS.md` with a `State` column; its first column names the item, and items whose state starts with merged, done, deferred, closed, dropped or skipped are finished.
- **Budget.** A session whose spend reaches `policies.budget.session_tokens`, every session once the run's spend reaches `run_tokens`, and every session at `stop_at` is stopped: one `stop` action with the reason, then `kill-session` of that exact session. A stopped session is `stopped`: not restarted, typed into or counted as crashed until `agentd clear`; after a clear its session cap counts from its spend at the clear (recorded by the run as it applies the clear, so a replay reads the same base), while the run cap and `stop_at` must be raised or moved first. A session that is DONE is left to deliver. A rotation that fails `max_restarts` times for one merge is escalated once and not tried again. Live mode counts only transcripts it launched.

## Briefs, turns and started sessions

There is no coordinator session: `agentd` runs each repository's request loop itself (see *The request loop*, #53). A coordinator an earlier version ran is no longer supervised: after the upgrade, stop its tmux session (`tmux kill-session -t NAME`), since nothing else stops it or holds it to a budget; its old track stays in `agentd status` as history. A reviewer or judge it started is left to the owner too, since the loop ends only the judgment sessions it started itself: end each with `agentd sessions end NAME`, or it keeps a place under `sessions.max`. A configuration that still has `repositories.REPO.coordinator`, `policies.coordinator`, `policies.models.coordinator` or a policy's `sessions.coordinator_model` is refused at load, each key named with what replaced it. Log events an earlier version wrote for a coordinator (its claim, wakes and approvals) are read and ignored.

- **A session's brief.** `sessions.NAME.brief`, a list of paths (relative ones against the configuration's directory), names the parts agentd writes the workdir's `BRIEF.md` from, in order, at each start and rotation: each part's trailing space trimmed, a blank line between them. A changed part so reaches the next start, and the brief no longer drifts from its parts. It is written as part of the launch, so a start or rotation refused for another reason, such as its account, leaves the last one. A part that cannot be read refuses the start or rotation: a skip and one escalation name its path, once for each error, as an account's are, the `BRIEF.md` written last stays, and the launch goes ahead once the part reads. A brief that cannot be written fails the launch: a restart's counts as a crash, as answers that cannot be written do, and a rotation's is retried and escalated as any failed rotation. The restart or rotation records each part's path and hash. With no `brief`, `BRIEF.md` is the owner's to write, as before. Shadow mode writes nothing.
- **Turns.** The worker that reads a transcript for usage also logs each main-chain prompt in the user's own words and each text an assistant turn ended with as a `turn` event, a prompt at most 300 bytes and a reply at most 16 KiB, its text left out when it matches a confidential pattern. Each is logged once by its line, so a restarted `agentd` reading the transcript from its start logs none again. A prompt is a real one only (#56): a tool result, a meta line, a compaction's summary (`isCompactSummary`), and an entry the harness injected, which begins with a tag it also closes, such as `<task-notification>`, `<system-reminder>`, `<bash-input>`, `<bash-stdout>` or `<command-name>`, are not prompts; such a block beside a typed one is dropped and the typed text kept. While a message from the owner waits on the session, each tool it runs is logged too, as a `tool` turn (*The console chat*).
- **Sessions agentd starts.** A repository with a `sessions` entry has its loop start the sessions it needs: a work session for the next queued case, and a reviewer or judge for a request's round.

  ```json
  "repositories": {"widgets": {"sessions": {"root": "/srv/agentd/widgets", "clone": "/srv/src/widgets", "target": "main"}, "policy": {"sessions": {"accounts": ["work"], "max": 4}}}}
  ```

  A started session's name is `REPO-<branch slug>-<6 hex of the branch>`, with `-review` or `-judge` for those kinds, so a branch and kind have one session; a start for a running name or past the policy's `sessions.max` (default 4) is not logged, and the loop says why in a skip. Its account is placed by usage when the policy has `sessions.fallback`, else it is the first of `sessions.accounts`. The fold holds the first start of a name and none past the `max` the start recorded, so a replay under another `max` agrees. A start is a shared `session` event; the sessions started and not ended are a projection of the log beside the configured ones, which every fold reads, so a replay rebuilds them. Before it is supervised, a started session is provisioned in a worker (a `provision` action, a would-be one in shadow, retried on the restart backoff and escalated after `max_restarts` failures): `root/NAME` with `BRIEF.md` (a fixed instruction and compact JSON: repository, kind, branch, issue, target, worktree, mr_file), `STATUS.md` when there is none (one that ends in DONE loses that line and notes the new start; its notes stay), and the worktree `root/NAME/work` unless it is there, added from `clone` after a fetch: a work session's on the branch as the clone or origin has it, else cut from `origin/target`; a reviewer's or judge's detached at that branch's commit, since its worker has the branch out. A branch that a configured session's worktree has out cannot be added; its provision fails and goes to the owner. Then it is a session like any other: launched with the restart command, restarted, rotated, budgeted and nudged, and where the repository allows push it delivers a draft request to `target` from `root/NAME/MR.md`. The loop ends the sessions it is done with; the owner's `agentd sessions end NAME` ends any: an `end` action stops its tmux session, once (escalated when that keeps failing), and it leaves the projection; its workdir and worktree stay. A start of the same branch and kind later is a new session with a fresh record (restarts, crashes, deliveries) and a new brief, in the same workdir and worktree; while the end's stop is still due it waits, so the old Claude never runs on as the new session. A provision is keyed by its start, so a late outcome of an earlier start's provisions no later one. A reviewer started again keeps its detached worktree at the commit it was added at; its brief names the branch to check out again.

## Event log

One JSONL file, append-only, one line per observation and action. Every line is version 2 of the format (`v`), with `time`, `session`, `kind`, the `mode` of the run that wrote it (`live` or `shadow`; `mark-delivered` and `clear` write `owner`, which both modes read) and exactly one typed payload, named for its kind: `start`, `stop`, `observe`, `transition`, `act` (for `intent`, `action` and `would`), `skip`, `crash`, `clear`, `error` or `warning`. Each payload has its own fields; nothing is an untyped detail. A line of another version, an unknown field, kind or mode, a missing mode, or a payload other than its kind's is malformed; `agentd` reads no older format, so a log from before this one is refused and is started afresh. Kinds are `start`, `stop`, `observe` (logged when the evidence changes), `transition`, `crash`, `clear`, `intent`, `action`, `would`, `skip`, `error` and `warning`. Every action is recorded before it is taken, as an `intent` with a random `intent` id, and its outcome after, as an `action` or an `error` repeating the id. When any append fails, the pass stops: the action whose intent could not be written is not taken, nothing more is done until the next pass, and `run --once` exits with the error. An `intent` with no outcome is an action cut short by a crash of `agentd`: the next `run` logs a `warning` naming it, `status` shows it, and an escalation, Questions update, nudge, resume or trust keys cut short this way count as done, so the owner and the session never see them twice. The file is created readable by its owner only (`0600`). Each append holds an exclusive `flock` on the file, so `mark-delivered` never interleaves with `run`, and is synced to disk before the action counts as recorded; an append whose write or sync fails is cut back out of the file, so it never leaves a fragment, and an event `agentd` could not read back is refused before it is written. At startup a malformed line is corruption: `run` refuses to start and names the line. Only a malformed last line that lacks its newline is a write cut short; `run`, `mark-delivered` and every append cut it off first and log a `warning` with its length, so a new record never lands glued to the fragment. An `observe` event carries `unchanged_s` only once the screen has been seen; until then the time is unknown and the field is absent.

The log is the only state, and one function reads it: `apply` folds an event into the state of one mode. Replay at start, the live path (each event is appended, then applied; apart from the screen memory a pass keeps between its own observations, which the observe event it logs then records, the supervisor changes its memory of a session in no other way) and every view (`status` and `report`) go through it, so a replay always rebuilds what the running `agentd` had. Live and shadow stay one log with a mode on each event: a run applies only the events of its own mode, plus the owner's records, so a shadow run's `would` events never use up a live run's restarts, escalations or deliveries, and a live run's actions never shape the shadow's decisions. In shadow mode `would` events count toward the shadow's own counters, so the once-per-key rules show in the log as they would have run. A restart shadow mode only would have made starts nothing, so a session still gone at the next pass has not crashed: shadow never records a crash for it or parks it, and logs the restart again on the backoff schedule.

## Safety

- Process control is by exact session name only. The tmux surface has no listing and no pattern; its only kills are a rotation's `respawn-pane -k` of the session's own pane, and the `kill-session` of that one session by a budget stop or the end of a session agentd started.
- Nothing is typed or sent as keys into a session that is DONE, has open Questions, is blocked on the owner or shows a dialog, or whose pane is not running Claude.
- Every forge write goes through one client wrapped with the per-repository policy. It can push, open and comment where `delivery.allow` says so, and merge where `merge.enabled` says so, by the policy's method: a fast-forward, the forge's merge call pinned to the head (a merge commit or a squash), or the policy's own command; it never rebases or forces.
- No escalation, merge-request text, branch name or commit message that matches a `confidential_patterns` entry is posted or pushed, and none is logged.
- An error that git, `gh`, `glab`, a gate or the escalation command reports, a poll's error, and a skip's reason, is logged as `(withheld: matches confidential pattern N)` when it matches a `confidential_patterns` entry.
- The gate that decides a delivery is the target branch's: a session that changed it is refused (see `gate.paths`).
- Escalations, Questions updates and deliveries are keyed and posted once, across restarts of `agentd`. Before pushing, the forge is asked for an existing request on the branch: an open one, or a merged one whose head commit is the worktree's current HEAD, or whose head the target already contains while HEAD has nothing the target lacks (the forge rebased it before merging). One found is recorded as the delivery, with the HEAD it covers, so a lost reply or a lost log never opens a duplicate. Commits count as ahead of the target only when the target lacks their changes, so a branch rebased onto a squash merge has nothing to deliver; a merged request for older commits does not count, so new commits on a reused branch name are delivered. `mark-delivered` accepts only a worktree named in the session's deliver specs.
- Delivery pushes to one URL built from the configuration alone, `git@<host>:<project>.git`, or `https://<host>/<project>.git` with `transport: https`; never to `origin` or any remote the worktree names. The push names the exact commit that was checked, `<sha>:refs/heads/<branch>`, never whatever HEAD has become, and runs with hooks off (`-c core.hooksPath=/dev/null`, `--no-verify`). It is refused, with one skip, when git config rewrites that URL (`insteadOf`, `pushInsteadOf`), or when the git config changed while the gate ran. Origin still decides what the fetch brings and what counts as ahead, so every fetch and push URL it has (`git remote get-url --all` and `--push --all`; credentials never logged) must name the configured project on the configured host, or one skip says why and nothing is pushed. `glab` and `gh` are pointed at the configured host, and requests from forks are left out when looking for an existing request.
- Nothing is delivered without a gate `agentd` ran itself. Delivery runs the repository's `gate` on the worktree's exact HEAD and records a `gate` event with the command, the commit, the exit status and the duration. It pushes only when the gate exits 0 and the tree is still the one it ran on: HEAD unmoved and the worktree clean. A failing gate is retried on the backoff schedule and given up on that commit after `max_restarts` failures, with one escalation; a new commit gets fresh tries; a tree that changed under the gate is skipped, and the next pass gates the new tree. Shadow mode logs the gate it `would` run and runs none. The gate's script and the files `gate.paths` names are the target branch's, but what it tests (the code, and tests such as a `TestMain` that exits 0) is the session's own, as is the worktree's git config that the fetch and push read: the gate protects against honest mistakes and a session rewriting its own check, not against a hostile session.
- A worktree on the deliver target itself, or on a detached HEAD, is never pushed; one skip says why, and it is delivered once it moves to a branch.
- A failed action is not retried every pass: retries follow the restart backoff and stop after `max_restarts` tries, with one skip or escalation saying so.
- Every external command runs under a timeout, and when it hangs its whole process group is killed; a hung tmux is an error, never taken for a gone session.
- Shadow mode performs no tmux write, no push or open, and runs no escalation command; escalations and Questions updates are logged as `would` events. It does fetch, which changes only the worktree's remote-tracking refs and nothing on the remote, so its delivery decisions use current refs.

## New items

`agentd items` lists what changed since the owner last looked, newest first: `--new` only the items not yet marked seen, and `--seen ID,...` marks items seen. Each item has #7's shape: an `id` that stays the same however often it is seen, its `kind` (`issue`, `merge_request`, `discussion`, `mail_question` or `mail_report`), its repository (`platform/path`), title, link, when the source says it happened, its author, when `agentd` first saw it, and whether it is for the owner only. Before listing, `items` reads the tracking files. Snapshots are compared through a cursor, the `AsOf` of the snapshot read last: an issue or request created since then is a new item, and an open one updated since then is a `discussion`, one per update. The first snapshot read is the baseline and makes no items. Every mail finding is an item for the owner only, keyed by its thread; one whose subject or summary asks something is a `mail_question`, any other a `mail_report`. Items, cursors and the owner's marks are events (`item` and `cursor` with mode `shared`, facts both modes read; `seen` with mode `owner`), so a replay rebuilds them and an item is never listed twice. A file that cannot be read is an error naming it and changes nothing: the list is never emptied or rewritten by a bad file. A bad mail file leaves the snapshot read; mail waits while the manifest or snapshot cannot be read, since its items take their repositories from them. Each cursor only moves forward, so an older file read again adds nothing. Mail findings carry a day, not a time, and sort as that day's midnight in UTC.

## Polling the forges

With `poll.github` or `poll.gitlab` set, `agentd run` asks the forges itself every `poll.every` (default `15m`), in a worker, through the `gh` and `glab` logins already in place: no credentials of its own. What it finds becomes items, with the ids the tracking snapshot gives (`platform/path#N`, `!N` for requests), so an issue both find is one item. Only the manifest's repositories count; without a readable manifest a source is unknown.

- **GitHub:** `GET /notifications` (read ones too, 100 per page) with `If-Modified-Since` from the last `Last-Modified`, which is the `github` cursor. A 304 means nothing changed, costs no rate limit, and makes no event. `X-Poll-Interval` is honoured when it is longer than `poll.every`. A notification of an issue or pull request updated since the cursor is a discussion of it, unless it is not an item yet and was opened since the cursor: then one more call reads when it was opened, and it is a new issue or request. One already an item as opened since the cursor (the snapshot may find it first) adds nothing. Other notifications (check suites, releases) are not items.
- **GitLab:** each active repository's issues and merge requests with `updated_after` the `gitlab` cursor, and the pending to-do list for to-dos made since, on any manifest repository. One opened since the cursor is new; one only updated is a discussion. The new cursor is two minutes before the poll began, so a clock skew misses nothing. It moves with every poll that worked, but its event is written only with a poll record, so quiet polls write nothing and a restart asks again from the last record's cursor. Each list is read in pages of 100, up to ten; a longer one makes the poll unknown rather than leave out what is past it.
- **Cursors and gaps.** The first poll of a source is its baseline and only sets its cursor. Each cursor is an event, so a restart neither misses nor repeats. A source that fails leaves its cursor where it was, writes none of the items it found before failing, and is shown as unknown, never as "nothing new"; the next poll asks from the old cursor. A CLI's error status and message are kept in the error.
- **Cost and health.** A `poll` event records a poll that found items, moved its cursor, failed or recovered, and at least every six hours a heartbeat; each counts the quiet polls since the last record and all their calls. `agentd status` shows each source's health, its last record, its calls and polls; a source whose last record is older than six hours and two intervals, or any source while `agentd` is stopped, is shown as unknown, since no one is polling it. A source turned off is not shown. The tally is kept in memory, so a restart loses the quiet polls since the last record from the count.

### CI

With `poll.ci` set, `agentd run` watches the pipeline of every request a session delivered (and every one the owner recorded with `mark-delivered`) every `poll.ci_every` (default `5m`), in a worker, through the same `gh api` and `glab api` logins, on the repository's host. It reads the request (GitLab: the merge request's head pipeline and its jobs; GitHub: the pull request's head check runs). On a failure it reads the target branch's latest pipeline, and for a failure that is the branch's own, the end of the first failing job's log. A request merged or closed is no longer watched.

- **Whose failure.** A failure is the branch's own unless the target is red, every job failing on the request fails on the target too, no job the target fails passes on the request, and the request's title or description names neither the target's red commit nor its pipeline. A request that passes what the target fails, or says it fixes it, is the target's fix and never waits for itself. Any other failure on a red target waits until the target is green, and any failure waits while the target's latest pipeline has not settled (GitLab: its latest finished pipeline is read). A merged-results pipeline counts as the head's.
- **Fix session.** On its own failure, the delivering session, once DONE or idle, is relaunched through the restart policy's command with `why: "ci-fix"`, `policies.ci.pointer`, and a `ci` fact: the request, its head, the failing jobs and the log excerpt (its last 40 lines without timestamps, GitLab section markers or colour codes, at most 3000 bytes, withheld whole when it matches a confidential pattern; empty when no failing job's log can be read). Delivery waits until that session has finished its turn, then pushes its new commit to the same request. A `ci-fix` action is not a restart or a crash.
- **Bounds and decisions.** Fix sessions per request count against `policies.restart.max_restarts` in its `window` and follow its backoff. The same cause again after a fix (the same failing jobs and an excerpt that matches once clocks, counters, durations and commit hashes are stripped), seen on the head the fix delivered, or the count used up, raises a decision on the session, `C1` on, with `retry` (one more fix session) or `leave`; a retry that meets the same failure asks again. It is answered on the UI like any other, does not count against the session's own open decisions, and leaves its `D` numbering alone. `C` and a number is reserved in `questions.json`.
- **Events and views.** Each change of a request's CI is a `ci` event: its state (`pending`, `success`, `failed`, `none`, `unknown`, `merged`, `closed`), head, target state, verdict (`own` or `target-red`), failing jobs and cause. A forge that cannot be asked is `unknown`, never green. `agentd status`, the UI (beside each repository's requests), the report and `agentd cases` show each request's CI. Once `agentd` has stopped, or with `poll.ci` off, status and the report show the CI as unknown, and so does the report for a record older than the head a fix delivered.

### Merge when green

A repository whose policy sets `merge.enabled` may have its requests merged by `agentd` (#1, D2; #35). Off by default. Enabling it needs `gate.argv`, `gate` in `merge.require`, `merge.targets` (the branches `agentd` merges into) and `merge.authors` (the forge usernames whose requests count as ours), so it never means any target or any author. With `poll.ci` set, every `poll.ci_every` each watched request is merged when all hold: the CI watcher has recorded its head since its latest delivery (it is what knows the head); what `merge.require` names holds at that head (default `gate` and `ci`; `gate` always): `ci`, the CI record is `success` (never `none`: a pipeline not yet created, cancelled or skipped is not green), `gate`, agentd's gate passed on that exact head, `review`, the session's case stopped its review rounds `converged`; its session has no open blocking decision or Questions; the forge says the request is open with that same head and not a draft (GitHub: its `mergeable_state` is `clean`, `has_hooks` or `unstable`, since moving the branch skips the pull request's own review rules; a state not yet computed is waited for); the repository's own `.agentd/policy.json` at the target's tip, if any, leaves merge on and is not withheld (see *Repository policy*); the request's target is in `merge.targets`, its forge author in `merge.authors`, neither its number nor any of its labels is in `merge.exclude`, and each of `merge.approvals` approved it (GitHub: an `APPROVED` review on the head commit that is still its reviewer's latest review other than a comment, read from one page of 100; GitLab: the request's `approved_by`, which GitLab keeps across a push unless the project resets approvals, so it is not tied to the head); for `merge.method` `fast-forward` (the default), the head is a fast-forward of the target's tip (GitHub: the compare is `ahead`; GitLab: the merge base is the tip, and the project's merge method is `ff`, since any other would make a merge commit, and its squash option is not `always`, which would write a commit nobody gated); and the request and the target's tip, asked again just before the merge, have not changed. (A GitLab request retargeted in the instant between that second look and the merge call is not caught.) The merge, through `glab` or `gh` with prompts off and the forge timeout, is by `merge.method`: `fast-forward` is GitLab's merge call pinned to the head (`sha`, `squash=false`) or, on GitHub, which has no fast-forward merge method, a move of the target branch to the head without force; `merge` and `squash` are the forge's merge call pinned to the head (GitLab `squash` false or true, under the project's own merge method; GitHub `PUT pulls/N/merge` with `sha` and `merge_method`); `command` runs `merge.command`, an argv with `{repository}` (the project path), `{request}`, `{head}` and `{target}` substituted, with no shell and prompts off. Otherwise a `skip` event says why, once per head and reason, and nothing is done; CI still running, and a CI record the watcher has not yet brought up to the latest delivery, are waited for without one. A `merge` action records the request, its head, the target's tip and the method; a request is merged once, and a merge cut short is not tried again. A failed merge call is retried with the restart policy's backoff, `max_restarts` times per head. Then a skip says it was given up; the request stays open for the owner, and no decision is raised. Shadow mode merges nothing; since its gate is only a would-be gate, it records that the head was not gated.

### Every request

In a repository whose request loop `agentd` runs (see *The request loop*), the CI watcher also lists the open requests each round (GitLab `merge_requests?state=opened`, GitHub `pulls?state=open`, one page of 100) and watches each one no session delivered: its `ci` events and records carry the repository's track `requests:REPO` (#36, #53), whose escalations go to the repository's console. A request that leaves the list is still asked until the forge says merged or closed. Every record also holds the request's author (screened), whether it is a draft, whether it has an open discussion (GitLab: `blocking_discussions_resolved` false, or a resolvable thread not resolved, from one page of 100 discussions; GitHub: a reviewer's latest review other than a comment requests changes, from one page of 100 reviews, since REST has no thread state and branch protection's conversation resolution already shows as `blocked`; a full page holds the request as if one were open), the run that judged its head (the pipeline id, or the oldest check run's, so a job run again tests the same commit), and `base`: for a GitLab merged-results pipeline, the first parent of the merge it ran on; otherwise the target's tip when that run was first seen, running or settled, kept across a forge error, and `unknown` when the tip could not be asked then (a later tip never stands in for it). A run first seen settled took its base from a tip that may have moved while it ran, which is not caught. A merged-results pipeline counts for the head only while the head is its merge commit's second parent, so one left from an earlier head, after a push whose pipeline was skipped, is not green. A busy request whose first page of 100 discussions or reviews is full is held as if one were open.

- **Approval.** The loop approves a request no session delivered at the head its review rounds converged on (a `loop` event with step `approve`; see *The request loop*). An approval counts only while the request's head is that sha, so a push after it holds the merge until the loop reviews the new head. An `approval` event an earlier version's coordinator logged is read and counts for nothing.
- **Merging.** A request no session delivered merges under *Merge when green*, except that agentd's gate never ran on it, so `merge.require` is replaced by `ci` and `review`, and `review` is met only by the loop's approval at its head. For a delivered request `review` is met by its case's rounds converging at its head. A draft, or an open discussion, holds either kind; the discussions are read again when the merge is checked and just before it. Skips and merges of a request no session delivered are recorded on the repository's `requests:REPO` track.
- **A moved base.** With `ci.retest_on_base_move`, a request whose target tip is no longer the `base` its green run was recorded at is retested before it merges, once per head and tip: on GitLab a `retest` action asks for a new pipeline (`POST merge_requests/N/pipelines`, on the merge result where merged results pipelines are on), through the allow-listed forge client under `merge`; when the new run is green the watcher records the new base and the merge goes ahead. A base `unknown` counts as moved. While no new run has come after a retest, a skip says it is waited for. A retest call that fails is retried with the restart policy's backoff, `max_restarts` times per head and tip, then given up with a skip. GitLab answers a project whose CI rules make no merge-request pipelines that the new pipeline would be empty: that answer (in GitLab's English wording) is not retried. The request is skipped with that reason, and the owner gets one escalation per head saying so and what would let it merge: merge the target into its branch as a merge commit (a branch pipeline then runs on the new tip), add merge-request pipeline rules, or turn off `ci.retest_on_base_move`. A later tip is asked once more, in case the rules changed. agentd does not write to the request's branch itself. GitHub has no call that retests a pull request's merge result, so there the merge is skipped with that reason. A base never recorded, because the tip could not be asked, is not taken as moved.
- **Red CI.** A request no session delivered whose own CI failed is recorded with its failing jobs and a log excerpt (at most 600 bytes); no session is relaunched to fix it, and it does not merge while red.

With `ci.required`, `ci` is added to `merge.require` for delivered requests too. A request by an author outside `merge.authors` is watched, in the pack and never merged; `review.others` decides only whether the request loop reviews it (*The request loop*).

### Repository policy

Each repository's rules that `agentd` checks mechanically are one typed `policy` in the owner's configuration (#35), not prose in a session's brief:

```json
"policy": {
  "delivery": {"allow": ["push", "open"]},
  "gate": {"argv": ["./bin/check"], "timeout": "20m", "env": ["GOCACHE"], "paths": ["Makefile"]},
  "merge": {"enabled": true, "method": "fast-forward", "command": [], "targets": ["main"], "authors": ["widget-bot"],
            "exclude": {"numbers": [12], "labels": ["do-not-merge"]}, "approvals": ["lead"], "require": ["gate", "ci", "review"]},
  "review": {"reviewer_model": "", "judge_model": "", "rounds": {"max": 3}, "others": "review-only", "others_max_age": "14d"},
  "ci": {"required": true, "retest_on_base_move": false},
  "scope": {"reserved": {"numbers": [7], "labels": ["owner-only"]}},
  "sessions": {"accounts": ["work"], "max": 4, "models": [], "budget": {"session_tokens": 2000000, "run_tokens": 0}, "fallback": [], "work_model": ""},
  "confidential_patterns": ["widgets-internal-[0-9]+"]
}
```

The old repository keys (`allow`, `gate`, `gate_timeout`, `gate_env`, `gate_paths`, and `sessions.accounts`/`sessions.max`) are gone, not aliased: a configuration that still has them is refused. `review.rounds.max`, when set, is the backstop of the repository's cases in place of `policies.rounds.max`. `scope.reserved.numbers` are issues the loop never starts; `scope.reserved.labels` are matched where agentd sees labels, a request's own labels when it is about to merge, which hold it. `sessions.budget` caps each of the repository's sessions and all of them together, beside `policies.budget`. Each repository's `confidential_patterns` are added to the global ones, and everything agentd screens is screened with them all. The patterns a repository's own file adds screen what the supervisor and its workers log, escalate, feed and pack; the case tools' server, console instructions and the report screen with the configuration's patterns only. `ci.*` is acted on (*Every request*); `review.reviewer_model`, `review.judge_model`, and `sessions.work_model` choose models (`policies.models`); a work, reviewer or judge model outside the owner's `sessions.models` is refused at load (a repository's own file that narrows the list past a chosen work, reviewer or judge model holds: that kind runs the narrowed list's first model instead); `review.others` and `review.others_max_age` (default `14d`; a duration such as `36h`, or a whole number of days such as `14d`) choose which requests by other authors the request loop reviews (*The request loop*); `sessions.fallback` is checked and shown but not yet acted on.

A repository may add rules of its own in `.agentd/policy.json` on its target branch, in the same shape, read through the forge at the target's tip when a request into one of the owner's `merge.targets` is about to merge (at most 16 KiB); a request into any other branch is refused before its file is read. Its keys may only narrow the owner's policy: turn `merge.enabled` off; a subset of `merge.targets`, `merge.authors`, `sessions.accounts` or `sessions.models`; more `merge.exclude`, `merge.approvals`, `merge.require`, `scope.reserved` or `confidential_patterns`; a lower `sessions.max`, `sessions.budget` or `review.rounds.max`; `review.others` `review-only`; a shorter `review.others_max_age`; `ci.*` turned on; and `merge.method`, `merge.command`, `gate.*`, `review.*_model`, `sessions.*_model` and `sessions.fallback` only as the owner has them (an empty list is the same as none). `delivery.allow` is the owner's alone. A lower `review.rounds.max` is taken when it is below the backstop in force. A key that would widen the policy, or one the policy has not, is refused; a file that is no JSON object or too long is refused whole (`file`). The keys that narrow apply. A file that matches one of the configuration's confidential patterns (never one a file added, so a file cannot withhold itself) is withheld: nothing of it is logged, and merges into its target are off until it or the patterns change; it is screened again at every read. What was read is a shared `policy` event, once per repository, target and file hash, with the tip, the compact file and the keys applied and refused, so every process narrows the same way. As the read is recorded, a refusal or a withheld file goes to the owner once, as an escalation naming the keys (two requests to the same target checked in the same round may each send it; a post that fails is not retried, and the refusal stays in `policy show`). The file is read at the target's tip at every merge check, so a file that narrowed the policy does not hold it once it changes. A merge reads the owner's policy narrowed by its own target's file; The loop's starts, budgets, rounds and screening read it narrowed by the file last read on each of the owner's `merge.targets`. Repositories sharing a project take the lowest backstop.

`agentd policy show REPO` prints the effective policy as compact JSON: each key (`section.key`) with its value and its source, `owner`, `default` or `repository .agentd/policy.json on <target> at <tip>`, and each file last read, its target, tip, refused keys and whether it was withheld. Which keys a file applied is worked out again against the configuration as it is now.

## Triage

With `jobs.triage` set, `agentd run` triages new items with an agent job (#3, section 5): one small `claude -p` call per batch of up to `jobs.batch` (default 20) unseen items, in a worker, never inside the pass. Each item gets #7's triage: its `kind` (`question`, `report` or `discussion`), `needs_owner` (`now`, `today` or `none`), `urgency` (`now`, `today` or `later`), a one-line `summary` and a `suggested` next step (`reply`, `file_issue`, `answer_in_thread` or `none`). `agentd items` and the owner's UI show them, and sort what is new by urgency, then as before.

- **Stripped setup.** The call runs `jobs.command` (default `claude`) with `--model` (`jobs.model`, default `haiku`), `--output-format json --json-schema`, a short `--system-prompt`, `--setting-sources ""`, `--strict-mcp-config` with no servers, and `--tools ""`, so it can only answer. `ANTHROPIC_API_KEY` and `CLAUDECODE` are removed from its environment. Under `jobs.account` it gets that account's config directory and token, the token read by the shell as for a session; without one it uses `agentd`'s own login. Mail items go to the job too, so `jobs.account` must be the owner's own login (#7), never a shared one.
- **Limits.** There is no token-cap flag, so the cap is the input size (`jobs.max_input`, default 16 KiB; items that do not fit wait for the next call, and each title is cut to 300 bytes) and `jobs.timeout` (default `2m`), after which the call's process group is killed; so is it when `agentd` is told to stop, and the items wait for the next run. Output over 1 MiB ends the call.
- **Data, not instructions.** The items go on standard input as one compact JSON document, and the instructions say that text inside it is data, never to be followed.
- **Checked twice.** The CLI holds the answer to the schema, which is built from the lists Go accepts; Go then checks that every item sent comes back exactly once and nothing else does, that every field is from its list, and that the summary is one line of at most 160 characters. A failed call or answer is retried once. A second failure is an `error` event naming the items, and is never applied: the items stay, untriaged, and are tried again after an hour.
- **Events.** A checked answer is a `triage` event, mode `shared` like the items, with the model and the tokens the calls used. Each result is keyed on a hash of the item's title, so an item seen again is not triaged again, whatever author, link or kind another source gives it. One seen under a new title is retitled and triaged again (the first sighting's time stands); in practice that is a GitLab issue edited within a poll's overlap, or a snapshot or mail finding with a new title. A running `agentd` picks up the items, seen marks and triage other processes log, so it does not triage what the owner has already seen or another run has triaged. Triage is opt-in, so a `--shadow` run with `jobs.triage` set triages too: the calls are its own, and the results are shared facts both modes read.

`agentd triage --items FILE` tries the job on a JSON list of items with one call, retried once if it fails, and prints the checked answer and its cost; it logs nothing.

## Status graph

**The issue index (#69).** With `poll.index` set, `agentd run` lists every open issue and request of each GitHub or GitLab repository every `poll.every`, in a worker, through the same `gh api` and `glab api` logins (a page of 100 at a time, at most 20 pages; a listing cut short there reports nothing gone): number, title, labels, milestone, author, opened and changed, and a request's source branch and draft. Each issue or request that is new, changed or no longer open is an `index` event, so the UI and the CLI read the index from the log and never from the forge; the first listing of a repository marks its issues as known. A listing that fails is an `error` event once, until it works again. What belongs to an issue is joined by its number: a work item's `issue` or forge `done_when`, a session's `issue` or the item it serves, an open request whose title names `#N` as a word (anywhere, and every issue it names; `other#N` is not this repository's) or whose branch has a segment, split on `/`, that is `N` or starts with `N-` or `N_` (`fix/12-crash`; not `release-1.2` or `issue-12`), and the case `repo#N`.

Each issue and request carries a sentence saying where it stands, a `sentence` event naming its writer: the status check copies its summary to the issue its session works (`status`); the request loop writes a request's place, and its issue's where no status check writes it, when the place changes (`loop`); and with `jobs.sentences.enabled` a small model (`jobs.sentences.model`, else the jobs' model) writes an idle issue's from its fields, body and latest comments (`idle`), once per change on the forge, never for the first listing, and not again until the issue changes; a failed call is tried again after an hour. A sentence matching a confidential pattern is withheld. When the owner's work names no issue, Go opens one for it (title and one line naming the item) where `delivery.allow` lists `issue`, logged as an `issue` action; elsewhere a `skip` says why it opened none. Its title is the agent's and goes to the forge as written, so one that matches a confidential pattern, or names a session (configured or started) or another configured repository as a word in any case, opens none either, with a `skip` saying why. Work whose `done_when` is an issue's closing names that issue. The open runs on the loop, bounded by the forge timeout, and one that fails is logged and not tried again.

With `jobs.status.enabled` set, `agentd run` asks a small model for each active session's status every `jobs.status.every` (default `5m`, at least a minute), and the console draws the answers as a graph in the session's panel (#57). It runs under the jobs' `command`, `account` and `model` (default `haiku`), with the same stripped setup as triage: a short system prompt, no tools, no settings and no MCP servers.

- **Who is checked.** Only by a live run: a shadow run's checks would repeat the live run's calls. A session agentd has observed that runs, on this machine: not one that is done, stopped, failed, crash-looping or parked, and not one on another host. A session with nothing new since its last check (no transcript entry, no STATUS.md line changed, no commit, no CI change) is not sent and has no record; it is looked at again a period later.
- **Its input.** One JSON document: the session's name, kind and issue; what Go measured (state, context, spend, tools run and failed, commits); the previous record; and the transcript since the last check with the bookkeeping removed. Every prompt someone wrote, all of the session's own text and every tool call are kept, each call's long strings cut in their middle (a command at 600 bytes, anything else at 300); each tool output keeps its first and last three lines, and a failed one is kept whole up to 2000 bytes. Ids, timestamps, usage, the duplicated copies of results and the entries the harness injected are dropped. Alongside go STATUS.md's added and removed lines (its start whole on the first check after a restart), the commits since the last check's head and the CI changes of the session's requests. The input is held to `jobs.status.max_input` (default 20 KiB: under 12k tokens, since a transcript's JSON of code and commands measured 1.75 to 2 bytes a token): the outputs of tools that did not fail are cut to one line at each end first, then every string of a call's input to 150 bytes, then failed outputs to 500 bytes, then every call's input strings and output to 80 bytes (the prompts and the session's text stay whole), and only then are the earliest entries dropped, one at a time, and counted. On recorded transcripts the busiest five minutes (0.5–1.5 MB of transcript, 20–50 tool calls) come to 20–36 KB before fitting and at most 20 KiB sent; all of about 400 five-minute windows recorded kept every call. A real call on haiku read about 12k tokens for 21 KB.
- **Its answer.** One record: `session`, `phase` (`design`, `code`, `test`, `review`, `merge`, `ci` or `idle`), `progress` (0 to 1), `blocked` and `blocker`, `risk` (`low`, `med` or `high`), and a one-line `summary` and `next` of at most 200 characters. The CLI holds it to the schema and Go checks it again; an answer that fails, or a failed call, is not retried and is not a guess: the check's `status` event carries the error and the graph shows a gap.
- **Events.** Each check is a `status` event for its session: where its window ended in which transcript, the head, the facts, the record or the error, the model and the tokens the call used. A restarted agentd starts the next window where the log says. Records and errors are screened against `confidential_patterns`.
- **The graph.** Each session's panel draws its checks over the last six hours, a bar each, its height the progress and its colour the phase, a blocked one in the alert colour and a failed one as an outlined gap, with the latest record and what the checks cost today. The console shows the day's total over its sessions.

`agentd status-check --transcript FILE [--window 5m] [--input] [--call]` builds the input for the window at the end of a transcript and prints its size (and with `--input` the input itself); with `--call` it makes the one call and prints the checked record and its cost. It logs nothing.

## Repository context

Agents need context without being handed everything (#60). `agentd` keeps it in two layers for each repository, and agents query it through the tool server.

- **State: one card per topic.** A card says what is true now about an issue (`#N`), a request (`!N`), a session (`session:NAME`) or the repository (`repo`): its title, status, a two-sentence summary, the rules in force, the questions open for the owner, the known problems and the related topics. Every claim names in `src` the history records it was drawn from. A card is at most 4000 bytes of JSON; each revision is a `card` event with its `rev`, so old ones are kept.
- **Curators keep the cards.** With `jobs.curator.enabled` set, when a decision, answer, instruction, ruling, comment, CI result, merge, status record or commit lands on a topic, `agentd run` waits until the topic has been quiet for `quiet` (default `2m`, or `max_wait`, `10m`, since the first), at least `gap` (`10m`) after its last curation. Then it calls the jobs' model (haiku by default) with the card and only the records new since, at most `max_input` bytes (16 KiB). The curator answers with a diff. Go applies it only when every claim cites a record it was given, a rule in force or an open question leaves or changes only with a record new since the card's last revision, and the card stays within its size. Otherwise the diff is refused and logged, and the next curator is sent the same records with the reason. Two sources that disagree become an open question for the owner, and the rule stays in force. The repository's card is curated the same way from the topic cards that changed. A repository has at most `per_day` curations a day (300). A topic never curated is curated only for records within `lookback` (`72h`). A shadow run curates nothing.
- **History: everything, rarely read.** The records are drawn from the event log (decisions, answers, the owner's instructions and rulings, status records, prompts and replies, failed tools, commits, CI results, merges, escalations, posts) and from issues' and requests' threads, read from the forge when an item arrives on one or an agent asks, and logged as `thread` events, screened. Each record has an id drawn from its source, and topics drawn from its fields and from the `#N`, `!N` and paths its text names; a path names an area, `area:DIR`.

The tools, on every session's server and, with `agentd mcp --repository NAME [--as NAME]`, on a server of their own for an agent that works no case:

- `state(topic?)` returns the card, or the repository's. `find(q, limit?)` returns the topics whose cards match, and topics with history but no card.
- `history(ids | topic, since?, kinds?, budget_tokens?, more?, why, question?)` returns records by id, or on a topic newest first, cut to the budget (default 4000 tokens, at most 32000, counted as bytes × 4/7), with `more` for the next page. `why` is `spec`, `debug-decision`, `verify-claim` or `missing-from-state`; the last also tells the topic's curator what was missing.
- `ask_expert(question, record_ids?, topics?, budget_tokens?)` calls `policies.models.expert` (default `opus`) with the stripped setup and read-only tools (Read, Grep, Glob) in the session's worktree, or the repository's clone. It answers `{"answer","confidence","used"}`. Its tokens count against `jobs.expert.budget_tokens` a repository a day (500,000).

Issues carry their own context:

- `issue_body(title, facts, owner_records?, record_ids?, topics?)` returns the body for an issue an agent files. Go writes it: the owner's words quoted whole from the records named, the facts, the records with their ids, and the rules in force and open questions of each topic's card, each with its sources. An id history does not hold is refused.
- A console thread (#59) that ends with a decision or an outcome about an issue or request calls `PostOutcome`. Go posts it there as a short comment labelled as an agent's, naming the thread and its sources. This happens only where the repository's `policy.delivery.allow` lists `comment`, and it is logged as a `comment` action. A shadow run logs what it would post, and an outcome that matches a confidential pattern is refused. The next read of the thread brings the comment into history.

Every call is a `query` event with its size. `agentd context stats REPO [--since 24h]` reports how many questions state answered alone (no history call by the same agent within five minutes), the history calls by reason, and the curators' and the expert's tokens. `agentd context card REPO [TOPIC]` prints a card.

## Scheduled jobs

`jobs.scheduled` lists commands `agentd` runs on a schedule (#51), so agent work that ran from an outside cron, under one fixed login and unseen, is supervised like the rest:

```json
"jobs": {"scheduled": {
  "digest": {"at": "06:30", "argv": ["./bin/digest"], "cwd": "/srv/widgets", "account": "b", "timeout": "20m"},
  "sweep":  {"every": "2h", "argv": ["claude", "-p", "Sweep the open requests."]}
}}
```

- **Schedule.** Exactly one of `every`, a duration, or `at`, `HH:MM` each day in `agentd`'s local time. An `every` job runs on its first pass and then every `every` after its last slot, and a slot missed while `agentd` was down runs once, late. An `at` slot runs up to an hour late; an older one is not run, and the next is. The log keeps each job's last slot, so a restarted `agentd` neither repeats nor loses one.
- **Its run.** `argv` runs in `cwd` (relative to the configuration's directory; none, that directory) in a worker, never inside the pass, one run of a job at a time: a slot due while its last run still runs is a `skip`, not run later. It runs as the triage job does: its environment loses `ANTHROPIC_API_KEY` and the calling session's variables, and under `account` it gets the account's config directory, and its token is read from the token file by the shell that execs `argv`, so it is on no command line and in no event. Without an account it uses `agentd`'s own login. At `timeout` (default `30m`) its process group is killed, as when `agentd` stops. One run at a time holds while `agentd` runs: a run whose `agentd` was killed outright is ended as `stopped` by the next one, which does not know whether it still runs, and runs the job's next slot.
- **Events.** A `job` event records each run's start, with its slot, and its end: exit code, duration and, for a failure, up to 300 bytes of its standard error, screened against the confidential patterns. Its output is not kept; a job that wants a log writes one itself.
- **Failures.** Three failed runs in a row are escalated once to the default console, naming the job and its latest error; a run that succeeds ends the streak, and the next streak is escalated again. A `stopped` run, killed because `agentd` stopped or found with no end after a restart, neither fails nor succeeds.
- **Shadow mode** runs nothing and records the run it would start, once a slot. The owner's UI lists each job beside the accounts: its schedule, its last start, exit code and duration, and whether it runs or fails.

## Account usage

`agentd accounts` reads every configured account's plan usage now and prints one line each: the five-hour and weekly utilization in percent with their resets, and whether overage is on, or why it could not be read (#39). It logs nothing.

`agentd accounts --report [--json]` reads no account: it prints each account's token use from the event log (#64). Each session's spend, as measured from its transcript, is charged to the account it was started on. Each job's spend is charged to `jobs.account`; the jobs are triage, status, curator, thread agent and `ask_expert`, and a reviewer's or judge's session counts as the review or judge job. A spend whose account was not recorded, including one on the default login, is the `unknown` account's. Each report gives:

- the latest five-hour and weekly percent with their resets;
- the weekly percent over the current week, with a gap where a reading is missing;
- tokens today (from local midnight) and this week, split into the top five sessions by name and the jobs by kind;
- the burn over the last 6 hours;
- the weekly percent projected at the reset at that rate, flagged when it reaches `usage.limit`.

The overview page shows the same in each account's chip, and serves it as `/accounts.json`. When an account's projection reaches the limit, or a session is placed on an account that is not the first of its repository's `sessions.fallback`, agentd posts one `info` entry to the console of the repository that charged the account most in the last 6 hours, naming the sessions using it. It posts at most one per account every 6 hours.

- **Reading.** The token is the account's `token_file`, else the OAuth access token in its `config_dir`'s `.credentials.json`, read only as a regular file. It is read for each reading and dropped, never logged or printed: any text a reading returns has the token taken out first, an error names a token file by its base name only, and a redirect is never followed. `usage.api` must be https (http only to this machine). A `.credentials.json` token past its `expiresAt` is not sent: Claude Code refreshes it only while it runs under the account, so an idle account read this way may read as expired until it runs again. `endpoint` asks `{api}/api/oauth/usage` (`five_hour`, `seven_day`, `extra_usage`). `headers` makes the minimal request Claude Code makes, one token of `usage.model` with Claude Code's system line, and reads its `anthropic-ratelimit-unified-5h-*`, `-7d-*` and `-overage-status` headers; it costs one tiny call. `auto` asks the endpoint and falls back to the headers when the token may not read it (HTTP 401 or 403, a token without the profile scope).
- **Events.** With `usage.enabled`, `agentd run` (live only: a shadow run makes no reading of its own) reads each account every `usage.every`, in a worker. A reading is an `account` event, mode `shared`, no session, with the numbers only, or its error, screened. It is logged when a utilization moves by a percent or more, a reset, overage or the error changes, or, saying the same, after an hour or half of the time a reading stands for (three `every`), whichever is sooner, so a steady account never goes stale. The fold keeps each account's latest reading, its numbers across a failed one.
- **Placement.** A session agentd starts in a repository whose policy has `sessions.fallback` is recorded with no account. Before preparing it, `agentd` places it on the first fallback account whose latest reading is no older than three `every` and has both utilizations under `usage.limit` (with `usage` off, the first fallback account; an account whose `usage` is `off` always counts as having room). The placement is a shared `session` event of action `place`, naming the start's id and the account; the fold sets the session's account once, so it never moves to another account afterwards. While no fallback account has room, the start waits: a skip once, and one escalation per start, when every fallback account was read and is at or over the limit, naming each one's utilization and reset, or when the readings have not come for three `every` since the start; never only because the first reading is not in yet. A start recorded for placement never starts on the default login, even if the fallback order is taken out of the policy while it waits. A shadow run places nothing and waits for the live run's placement. An earlier fallback account this run has not yet read is waited for, never passed over for a later one, since a placement holds for good; a run just started reads before it places, and counts a start's wait from when it began reading. The fallback order widens the accounts a placed session may go on beyond `sessions.accounts`; the default login is never a fallback. Without a fallback order, the first of `sessions.accounts` is used as before.
- **Views.** The UI's top bar shows a chip per account: its utilizations and resets, overage, how long ago it was read, and whether it has room, is over the limit, or is stale.

## Nodes and the hub

`agentd` runs on every machine (#29). One machine runs `agentd hub`, which holds the event log and the policy; every machine runs `agentd node`, which watches its own clones and reports to the hub. Not every machine can reach every other, but each can reach the hub, so a node asks and the hub answers. The hub never calls a node.

- **The connection.** `hub.address` is one IP address on the private network, never a name or every address. Each host in `hosts` has its own `token_file` (mode 0600), and its node holds the same token in `node.token_file`. The hub serves `POST /v1/report` and nothing else. A request without a host's token is refused (401) and nothing it sent is logged. A token used for another host's name is refused too (403), so one node cannot report as another.
- **Events, in order.** Each tick (`node.every`), the node sends a report of the clones the hub has it watch, plus the results of any commands. Each event is numbered in its host's sequence. The hub appends to its log, as `node` events (mode `shared`, no session), only those that continue that sequence. An event it already has is acknowledged, not appended again, so a node whose answer was lost may send again. A batch that skips a number is refused (409) with the number the hub holds, and the node renumbers from there. A node the hub cannot hear keeps its results and only its latest report. After a failed post it first asks the hub what it holds. The hub tells events apart by number alone, so run one node per host: a second process with the same token would have its events taken as ones the hub already holds.
- **Policy.** `repositories.NAME.clone_on` lists the hosts that must have a clone, at `node.repos_root/<forge host>/<project>` (default `~/repos`). The hub's answer lists the clones to watch and the commands its record allows. Today the only command is a clone of a repository whose latest report says it is absent, from the URL delivery uses. The node clones into a new directory beside the path, bounded by `node.clone_timeout` (default 30m), and renames it into place only once the clone is complete. A clone that fails, times out or is stopped with the node leaves nothing at the path. Only a node killed outright mid-clone can leave a `.agentd-clone-*` directory beside it, which the node never takes for the clone and the owner may remove. After a failed clone the hub waits `hub.retry_after` before asking again.
- **Safe actions only.** A node acts only on the hub's commands, and checks each one itself first. It refuses a command for a repository it does not watch at that path, a path outside its root, or a path where anything already exists. A clone that exists gets no command at all, whatever its state: dirty, stashed, ahead or behind, or holding open methodology state (`node.open_state`, default `.kickoff`). It is reported as it is. A scan takes none of git's optional locks, so not even the index is refreshed. A node never deletes, resets, pulls, rebases, moves a clone or changes a remote.
- **Sessions on a host (#15).** `repositories.NAME.sessions.host` puts the repository's started sessions on that host. It must be in `hosts` and in the repository's `clone_on`. It needs `policy.sessions.accounts` and is not allowed with `policy.sessions.fallback`, because placement by usage reads accounts on this machine. The account is `policy.sessions.accounts[0]`; a start with none, which a repository's own policy file can leave, is refused. The start event records the host and the account, and nothing changes either one later. The log's fold holds the first start of a session name until it is ended, whatever host a later start names, so one repository, branch and kind has one session, from the log alone. `agentd run` does not supervise such a session: it is left out of the sessions agentd runs here, which neither prepare, launch, restart, stop nor show it. The hub asks the host's node, in its answer, to start each such session until the node returns a result for that start, and to stop each one that was ended until it returns a result for that end. A command that failed is asked again after `hub.retry_after`, and a start waits for its name's stop. The node checks each one itself. The account must be in `node.accounts` with its `config_dir` present on this host; there is no other account and no other host. The repository must be one it watches, with its clone there. No tmux session of the name may be running. `node.launch` (`{brief}`, `{status}` and `{model}` filled in) and `node.sessions_root` must be set. The node writes BRIEF.md and STATUS.md in `node.sessions_root/NAME`, adds the worktree `work` from its clone, and starts tmux there under the account; a token file is read in the launch line, never logged. It writes `.agentd-node` in the workdir, holding the start's id, and stops only a session the hub has it watch whose workdir holds that mark, so never one of the owner's own; one not running is stopped already. A start whose session came up though tmux reported an error is done when asked again, by its mark. The node reports whether each of its placed sessions runs. Not yet built: watching their screens, nudging, answering dialogs, delivering and restarting on the host, so a session that ends shows as `gone` and the owner ends it or starts it again. Since such a session never delivers, the repository's loop never ends it: each holds one of `sessions.max` until the owner ends it with `agentd sessions end`, and the loop starts no more beyond the max.
- **Unknown.** `agentd nodes` prints each host's clones from the log: branch, and clean, dirty, stashes, ahead or behind, or open state. A host whose last event is older than `hub.silent_after` (default 10m), or that never reported, shows as `unknown` with what it last reported, never as missing or idle. A node sends nothing while it clones, so a clone that runs longer than `hub.silent_after` shows its host as unknown until the clone ends. It then prints each placed session: its host, account, repository and state (`starting`, `running`, `gone`, `failed` with the node's reason, `stopping` with the node's reason when a stop is refused), or `unknown` while its host is unknown or cannot tell whether it runs. Such a session is never shown as gone or idle and never started elsewhere.

## The owner's UI

`agentd ui` serves the owner's web UI on `ui.address` until interrupted (#41; it replaced `agentd page`, and serves the consoles' view #37 asked for). `ui.address` must be one IP address and port (the machine's private-network address, never every address). Every request is checked before anything is read. Its `Host` header must be one of `ui.hosts` (by default the address itself; case is ignored), so the UI reached through another name is refused. It must not come from the UI's own address or from loopback (an IPv4 address written as IPv6 too), so a process on this machine cannot borrow the machine's own identity. Then `ui.whois`, an argv with `{addr}` replaced by the caller's address and port, must name `ui.owner`: the command prints the caller's login on its first line, or a JSON object whose `UserProfile.LoginName` is the login, as a private network's `whois --json` does. It runs under the tmux timeout; an answer is kept for a minute per address, at most four run at once, and a failure is logged. Anyone else, and anyone whois cannot name, gets 403.

**One server, many logs.** `ui.logs` lists other agentd config files (relative to this one), such as a second team's when it runs under a config of its own. Each config's event log is one source, named after its config file; with `ui.shadow` (off by default) each config's shadow run is one more, named `NAME-shadow`. Each source is a projection of its log: one state, folded by the same `apply` as `run` and `status`, brought up to date with only the lines appended since the last request. Repositories are merged across the sources by their configured name. Every form names its source, so an answer or a mark goes to the log that holds the decision or the item.

**Pages.** Server-rendered HTML, one embedded stylesheet with light and dark colours from one token set, system fonts, laid out for a phone as well as a desktop. The content security policy allows the UI's own `/ui.css` and `/ui.js` only. The script fetches the UI every 30 seconds and swaps in each refreshable section, unless the owner is typing or has changed a field in it; without it the UI is complete.

- `/` (#69, level 1) opens with a sentence across the repositories (how many issues and requests are open and being worked, and which repositories have issues waiting on the owner), a table with a row per configured repository (open issues, being worked, requests, waits on you, last change, linked to its page; a repository the index does not list says so), and the token meter: each account's share of its week with its reset day, and today's tokens by what spent them, opening to the split by kind, repository and session. Then the console box for every repository. The rest of the page follows, folded.
- `/`: a chip per source (live or shadow, when it started or stopped, its spend against `policies.budget.run_tokens`, `stop_at`); **Needs you**; and **Repositories**, one card each.
- **Needs you** is worked out from each source's state as it is now, never from the escalations' history, so an item goes when its condition clears (a dialog gone, a session moved on): each open decision not yet answered (STATUS.md's Questions as one text decision, `questions.json`'s, those raised through the tools), and each session blocked on the owner with no decision of its own, usage-limited, crash-looping, stopped or failed. A `done` session is never listed. Each card names the repository and the session, how long it has waited, and the question rendered as Markdown, with its control: buttons for `yes_no` and `choose_one`, boxes for `choose_many`, a field for a `number` or `date`, and a text box only for `text`; the others may also be answered in the owner's own words. A decision with a default has a deadline field.
- A repository's card lists its working sessions as rows (state, STATUS.md's first line as the session reports it, context, spend, last turn), its open requests with CI, those it delivered and the outside ones its loop watches (#36: author, draft, open discussion), its new items with a form that marks them seen, and its finished sessions folded into a count. It links to its console.
- `/console/REPO`: the repository's open needs, its reply box, a panel per session (#56 D: its state, the tool it runs now or, while it works, the last one it ran, read from its transcript when the page is asked, how many of its questions wait on the owner, its last reply, folded when long, and a box addressed to it, not for a reviewer or judge nor a finished session), then its history newest first, 50 messages a page (`?page=N`), from every source: feed posts, escalations of its sessions, posts to its console (`agentd console post`, with their kind), its sessions' turns (`prompt` and `reply`, linked to the session), the owner's instructions and imported history. `/console/NAME` is a console under `consoles` the same way, its title from the configuration, its reply recorded for no repository. A reply is the owner's instruction for that repository (#33), `from: "ui"`, recorded in the live source that runs the repository's request loop, whose sessions read it (else the first live source that configures the repository), as a console reply is. Messages are kept in time order, the latest 200 per repository and source, so imported history never pushes out what is new; a shadow source shows only its own run's messages and items, not the owner's records again.
- `/repo/REPO` (#69, level 2): a sentence saying where the repository stands (its open issues and requests, how many need the owner and how many are being worked, its last change), from the issue index (`poll.index`); a repository it does not list says so. Then the **issue box**: every open issue in one bordered box of fixed height that scrolls inside itself, under a header that stays put with the count ("N issues, K need you, W being worked, S shown"), a sort and a filter. Each row has the issue's number, title, state word (needs you, working, stopped, open), its sentence and who wrote it (or a note that the forge's title stands), its requests, its last change, and when it waits on the owner the question with its options. Sorts: needs-me (the default: what needs the owner, then what is being worked, then the rest by last change), last-change, working (the longest-running session first), has-mr (by where its foremost request stands in the loop), newest and oldest (by number), stale, and the forge's own grouping by label, milestone and author, which compare with A to Z as a to z, character by character by code point, in no locale. The page's script and the command line sort the same rows the same way. The filter keeps the rows holding every word given, in title, sentence, labels, milestone, author, or an item's or a session's id, and matches `#N` or `!N` against the issue and its requests. Sort and filter run in the page's script over the rows and are kept per repository in the browser's local storage, so sorting never fetches. Then the **MR box**, the same kind of box for open requests: number, title, author, its issue, the loop's place as a sentence, CI, last change; sorts: loop (what waits on the owner, then fixing, judging, reviewing, merging, waiting for CI, outside), last-change, ci-failing, newest and oldest (by number); `agentd console REPO --mr-sort S` sorts it on the command line. A request opens its issue's page at the request. The console's event list is the page's **history** link; on an issue's page, **history** is the issue's every step. Home's waits-on-you number opens the repository's page sorted by needs-me.
- `/repo/REPO/issue/N` (#69, level 3): the issue's title, state word and every ref that belongs to it (work items, sessions, requests, case, labels, milestone, author); its sentence, with its writer and age; each open decision on it as a card (what is asked, what came back, what Go checked, each option with one line of what it does), whose answer posts to `/respond` as the console's buttons do; what has been done as dated steps (the issue's and its requests' steps the log folded: opened and retitled on the forge, sentences, work item steps, sessions started on it, loop rounds), the latest 12 with **every entry** behind a link; and **next**: each open item's done-when in words and what Go waits on, and each request's place. Built from the log alone: a page load calls no forge and no model.
- `/session/SOURCE/NAME`: the session's row and needs, a box to message it (#56; not for a reviewer or judge), its activity (#56 C: the latest 30 tools it ran and the one it runs now, read from the last 512 KiB of its transcript when the page is asked, never logged; each a one-line target screened whole then cut at 160 bytes, a failed one marked with its exit code), its latest turns, its STATUS.md rendered as Markdown (read only as a regular file, never through a link, and withheld whole when it matches a confidential pattern), and its last 40 events, newest first.

Markdown is rendered by a small built-in renderer over escaped text: paragraphs, headings, lists, code spans and fences, bold, and links to `http` and `https` only. No raw HTML passes. Sessions, questions and escalations go through the report's screening, so the UI leaves out what the report leaves out as confidential, and every message, turn and event is screened again. Every other text is escaped by `html/template`.

`agentd console --repository REPO import FILE` imports the old console's history once: one JSON object per line, `{"at": RFC 3339, "from": "...", "text": "..."}`, with `repository` to name another. Each line is a `feed` event of phase `imported`, mode `owner`, carrying its own time and author; a line already imported (the same repository, time and text) is skipped, a screened line keeps no text, author or `to`, and a file with a bad line (not JSON, a field of the wrong type, or no time or text) imports nothing. A field import does not use is ignored. The feed's fold ignores the phase; the console shows the lines in time order.

**No rollback past #69's events.** The event log's reader refuses what it does not know, an unknown field, kind or step, as every version's reader has: there is no tolerant reader and no compatibility path. A binary from before #69 therefore refuses the whole log at the first event #69 writes: an `index` or `sentence` event, an instruction with a scope (a console box's message at home, a repository or an issue), or a `loop` event with step `skip` or `stop`. Once a #69 binary has written one, which it does as soon as `poll.index` lists a repository, a loop or status sentence is written, or the owner writes in a console box, the log cannot be rolled back to an earlier binary: keep the previous binaries (`agentd.SHA`, kept beside the installed one by an install, as `ops_rollback` uses them) for the logs they wrote, and go forward from #69, not back. Its configuration is refused too, as #63's and #68's keys are: a binary from before #69 fails `agentd config` on a config that sets `poll.index`, `jobs.sentences` or `delivery.allow` holding `issue`, so an install's rollback to one is put back. Nothing puts back a refused log.

### The console box at each level (#69)

Each of the three pages ends with the same console box, scoped to its level: `home`, `REPO` or `REPO#N`. It posts to `/reply` with the scope, through the same origin and token checks, and the exchanges at that scope stay on the page as a conversation, newest last. What is written is an instruction that carries its scope:

- **At home**, a message that names one configured repository is that repository's; one that names none is answered by the home thread: one call on the jobs' model, given each repository's level (its sentence, the issues that wait on the owner and those being worked, its open requests), today's tokens and the earlier exchanges at home, with no session content and no tools.
- **At a repository**, a question is answered by the repository's thread agent, given the repository's issue index besides its usual facts. Nothing written at home or at a repository is handed to a running session: a hand-over the agent sets is dropped, and work it reads starts a session of its own, as the issue the message names (`#N`, when it names one) or a new one.
- **At an issue**, the message is addressed to the issue's session when one works it, and typed into it at its next turn (once its turn ended, or its screen is still under `policies.nudge`), or at once when the owner ticks **now**, which the box offers only while a session that takes messages works the issue (a message sent with now when none does is refused, and nothing is recorded); with no session, the repository's thread agent takes it, given the issue's page (sentence, open decisions, steps, next, requests, its sessions' status), and work it reads is that issue's.
- A message that is only one of the options of the level's one open decision (its key or label, or yes or no) is that decision's answer, recorded as its button records it.

**The levels on the command line.** `agentd console REPO` prints the repository's page in the same sentences: its state sentence, the issue box and the MR box, and its console's exchanges; `--issues` prints the issue box alone, `--sort` one of its ten sorts and `--filter WORDS` its filter, and `--history` prints every step the log folded for the repository's issues and requests, oldest first. `agentd issue REPO N` prints the issue's page: refs, sentence, the open decisions with each option's consequence, the latest steps (`--all` for every one) and next. `agentd console ask home|REPO|REPO#N TEXT` writes in that level's console box, `agentd console message --to SESSION [--now] TEXT` writes to a session (at its issue's scope, at its next turn unless `--now`, when it works one), and `agentd console reply --entry ID [--choice KEY|--yes|--no] TEXT` answers an entry as its card does. They read and write the log through the same code the pages use. The older forms (`reply CONSOLE TEXT`, `post`, `inbox`, `import`) are unchanged, and a repository named like one of the console's words is refused.

### The console and its threads (#56, #59)

The console is one conversation box, newest last. The page carries the latest 50 entries, fetches older ones as the owner scrolls up, and polls `/console/REPO/entries` (JSON) every few seconds for what changed. Every entry (a post, a turn, a decision, a feed line, an escalation, something waiting on the owner, a session's progress report) has an id, and the owner responds to one in its context: a click opens its form, with a decision's own options or quick words, and free text. `/respond` names only the entry; Go fills in `re` from the log: the entry's id, kind, session and time, its text as shown (screened), and a decision's question and options. An answer to an open decision is recorded as `/answer` records it, settling that decision only. The response goes, with `re` and any `answer`, as one record in `instructions.json`, to the session that wrote the entry (or the one the owner picks in "To:"), and is threaded under the entry with that session's activity and reply. The sessions are one line of chips that filter the box.

A response no session is to take (about an entry agentd wrote, or free text with no entry) goes to a **thread agent**: one headless `claude -p` started for it alone (`jobs.thread`: `model`, default the jobs' model; `max_input`, default 16 KiB; `timeout`, default 5 minutes), reading in the repository's clone with Read, Grep and Glob, and asking the context tools (#60) for what it needs. It is given the entry, the thread so far (its latest 10 records), the owner's message, the session the entry is of in a line, and the running sessions. It answers, or hands the work to a running session of the repository, which then receives the owner's record as any other; it may name a decision's or a work's outcome on an issue or a request, which Go posts there (#60 §4). Its answer, the tools it ran, its input's size and its tokens are logged in the `route` event, and the answer is threaded under the entry. A follow-up in the thread starts a new agent with the thread so far: no context grows past its thread. An agent that fails is started once more; then the response fails, saying why. A chat session an older agentd started (#56 A) is ended once nothing of the owner's is open on it.

Each session's page has its own message box: a message there goes to that session.

Every message routed since #56 carries `route: true`, and `to` when it addresses a session; agentd never routes an instruction recorded before #56. At the start of each pass, agentd routes each message that is not yet delivered:
- to the session it addresses;
- else to a thread agent started for it (above).

A `route` event records where a message went, or why it waits or failed. A message addressed to a session never goes anywhere else: it waits while that session is parked, stopped or limited, and fails when the session is finished or gone, or is a reviewer or judge (whose page has no message box, and whose name `/reply` refuses). A message also fails when its text matched a confidential pattern (it was never logged), when it was sent on a console without a repository and addresses no session, or when its repository has no clone or session worktree here for a thread agent to read. A console that feeds several repositories routes to the first one's thread agent. Delivery works as answers do, at once, mid-turn too: agentd writes `instructions.json` in the session's workdir (the latest 20 routed there; `new` marks those not handed over before) and types the one fixed line `policies.instructions.pointer` into a working or idle session, through the usual safeguards. It is never typed into a session waiting on the owner's answers. The owner's words are never typed. A session that is gone before it answers is launched again with its unanswered messages (`why: "instructed"`), which the new session takes afresh. A session is not rotated while a message waits on its answer.

The fold threads the rest from the log under the message:
- delivered (the `instruct` action, or the restart that carried it);
- taken (the session's first prompt after the delivery);
- each tool it then ran: a `tool` turn read from the transcript, with the tool, a one-line target (screened whole, then cut at 160 bytes) and the outcome, `failed` with the exit code a command's result names. Tools are logged only while a message waits on that session, so the log does not grow with every long-running session's tool calls;
- its reply (the summary that ends that turn), logged whole up to 16 KiB.

While a message is delivered and unanswered by a session that can still answer it, for up to 2 hours, the loop passes every 5 s instead of every `poll_interval`, and the console page refreshes every 5 s instead of 30. An owner record wakes the loop within 2 s (`WakeCheck`, formerly 15 s), and the message is routed and delivered in that pass.

`POST /answer`, `/deadline`, `/seen` and `/reply` are the UI's writes. `/reply` takes an optional `session`, the session the message is for. Each must also carry the UI's own `Origin` and the token the UI put in its forms, a random value made each time it starts, compared in constant time, and goes back to a path of the UI's own. The UI's referrer policy is `same-origin`, because under `no-referrer` a browser sends a form's `POST` with `Origin: null`; other sites still get no referrer. That stops another site in the owner's browser from posting. It cannot stop a program running as the owner on another of the owner's machines, which whois names as the owner too: it can read the UI, token and all. The UI limits what such a program can do: marking items seen hides nothing for good (`agentd items` lists every item); an answer or an instruction reaches a session only as data, with the fixed pointer line typed, never the text; and every mark and answer records the address it came from.

## Work items: told means done (#66)

The owner: "I am asking how we fix this infrastructure in go so when it is told to do something it actually does it." A message is not an obligation; a work item is. When a thread agent reads the owner's message as asking for work, its answer carries `work`: a title, a brief, and `done_when`, the observable end state that is true only once the work is done. Go then holds the work as an item in the log until that end state is checked true, or the owner closes it:

- `done_when` is one of `{"kind":"url","url":U,"contains":S}` (a page whose body holds S, such as a version string), `{"kind":"forge","ref":"#N","state":"closed"}`, `{"kind":"forge","ref":"!N","state":"merged"}`, `{"kind":"forge","ref":TAG,"state":"tagged"}`, `{"kind":"file","path":P,"contains":S}` (a file of the assigned session's worktree, else the clone), `{"kind":"status","contains":S}` (the session's STATUS.md), or `{"kind":"owner"}` when only the owner can say. Work whose `done_when` Go cannot check as written is refused, and the agent is asked again.
- An item is `open`, `assigned`, `acknowledged`, `working`, `blocked` (with the question), `done` (with the evidence) or `declined`. Only Go changes the state, from what it observes; a session's or an agent's words never close an item.
- The owner's message goes where #65 sends it: to the session the agent handed it to (a running one, or a finished one whose tmux still runs, which agentd reopens), else to a work session started for it. Once that route settles, the item opens and is assigned to that session, which is typed one fixed line naming the item's id and `items.json` (the item, the owner's words and attachments, and the protocol below); the owner's words are never typed. An `open` item with no such session (the route failed, or the session was taken off it) is assigned to a work session agentd starts for it (`REPO-owner-SLUG-ID-N`), briefed with the owner's message and the agent's facts as #65 briefs one, and with the item. When none can be started (no sessions entry, sessions placed on another host, `sessions.max` reached), the owner is told once, with the sessions holding the places, and the item stays open. After three sessions, the owner is told and the item waits for the owner. A session started for the item or its message that is taken off it is ended; any other has the item dropped from its `items.json`.
- An item `assigned` and not named (in STATUS.md or on the screen) within `items.ack_within` (default 10 minutes) is typed again once, then given to a new session.
- A session names the item in STATUS.md to take it (`working`), writes `ID blocked: QUESTION` to ask the owner (the item's entry and a console line carry the question; the owner's words on the entry go to the session), and `ID done: EVIDENCE` to claim it.
- A claim triggers the check at once; Go also checks every `poll_interval` while the item is open, and logs a result when it changes. A true check closes the item with the check and its result, timed, as evidence. A claim the check refutes is told to the owner and typed back to the session. With `done_when: owner`, a claim is the owner's to answer: done, or not done.
- A session that writes DONE with its item not done (its check false), or ends, stops or is parked, gives it back: the item is `open` again, with the session's last STATUS.md as a note, and assigned anew.
- An item with no change of state and no change of its session's STATUS.md for `items.escalate_after` (default 2 hours) is told to the owner once, with what was tried.

Open items are the first thing on each repository's console: the id, the owner's words (cut), state, age, the session, the last progress and `done_when` with the last check. Each takes the owner's answer: `done` (by hand, with a word as evidence), `not-done` (to a claim only the owner can judge), `reassign` or `decline`; words alone go to the item's session. `agentd items` lists the open items before the tracking items; `agentd items --work [--all] [--json]` lists them alone.

Nothing goes where Go cannot reach: an item is assigned only to a session Go supervises here, the thread agent is told that the running sessions it is given are the only ones reachable, and `agentd console post --to` refuses a session agentd does not run, naming it.

## Releases: done when they run where they must (#67)

The owner: "why the go infrastructure cannot generate the proper [project] browser, and the proper [project] signers so we can deploy code that will generate and sign the requested withdraw". Go could build a release. It could not place one, and it did not know what "the release works" means. A repository's `deploy` says both:

- `deploy.targets` names where a release must run. A target of ours has a `host`, a route (`via: node` for a host in `hosts` whose agentd node runs the steps, or `via: ssh` with `node`, the host in `hosts` whose node holds the ssh access), a `check` (`url` with `contains`, or `json_path` with `value`, by default `{tag}`; what it looks for must name `{tag}`, or it would hold for every release), and `steps`. An ssh target whose `node` is no host in `hosts` is refused, and so is one from agentd's own host (`node.name`) unless it sets `own_host`. A target of kind `fleet` is other people's machines: `heartbeats` is the URL that says what each member runs (a list, an object holding one, or an object by member; `fields` names the keys when guessing fails), and `threshold` is how many members must run the tag.
- **A release is a work item.** When `deploy.clone` (by default the sessions clone) gets a new tag matching `deploy.tags` (default `^v[0-9]`), Go opens the item "release TAG running". The tags there when Go first reads the clone open nothing; `agentd releases open REPOSITORY TAG` opens an item for one of them. One release of a repository deploys at a time: a newer item marks any older one still open `superseded`. The item is listed with the work items (#66) on the console and in `agentd items`. Its done_when is every target's check: each of ours, and each fleet at its threshold. The item records the release's `compat` rule, read from a `compat:` line in the tag's notes or in the CHANGELOG section naming the tag.
- **The gate runs the system, not the build.** `deploy.gate.argv` (`{tag}` filled in) runs in a fresh detached copy of the clone at the tag, with an empty HOME, PATH, LANG, TMPDIR and the variables in `deploy.gate.env`, bounded by `deploy.gate.timeout` (default 30m). Its output is attached to the item. The item stays `built` until the gate passes. A tag whose gate fails is `withdrawn`, the owner is told with the output's end, and nothing deploys it. A repository with no gate is recorded as having none, and its release goes on.
- **What is ours, Go deploys.** While the item is `deploying`, the hub asks the node that runs a target's steps (its host, or its ssh node) for the first step not done, one at a time. The node runs a step only when `node.deploy` names the target as `repository/target`, and, over ssh, `node.ssh` names the host: what a node may do is its own configuration's to allow. A step is its `run`, then its `check`, each bounded by its `timeout` (default 10m). When either fails, its `rollback` runs, and the result says which failed, whether the rollback held, and the output's end. A failed step blocks the item, the owner is told, and nothing runs again until `agentd releases retry REPOSITORY TAG`, which asks for the failed step again, never for those done before it. Only the node that runs a target's steps can report them. A step's success counts as progress only: a target holds only when its check does, and every step is done.
- **What is not ours, Go reads and asks for.** Go polls each fleet's heartbeats on `poll.every`, and logs the reading (each member's version and last-seen time) when a version or a member changes, or hourly. A fleet whose members run more than one version is `mixed`. A member is on the tag when its version is the tag, with or without its `v`, or the tag with a `+build` or git describe suffix; a pre-release such as `-rc1` is not. What the heartbeats and checks say is screened like any other party's text. The reading is the fleet's card (topic `fleet:TARGET`, written by Go) and one of the thread agents' fresh facts, as are the release items. So "which signers are on v3.38.x" is answered from state. Once a release deploys, its fleets' operators are asked once to run it, naming those not on it and the compat rule. The message goes on the repository's console, and through the fleet's `notify` command (`{message}` filled in) when it has one. The message holds member names from the heartbeats, kept to letters, digits and `._@:+/-`; pass `{message}` as an argument, never into a shell's command line. Each pass records who is still behind. After the fleet's `escalate_after` (default 24h) the owner is told once, with that list. Go never claims a fleet is done; only its threshold can say so.
- The item is `running` (done) only when every check holds in the same pass, and the owner is told. A shadow run leaves releases alone: it reads, posts and deploys nothing. `agentd releases` prints each item: its state, compat, gate and each target's last check.

## The design before the work (#68)

The owner: "Why do I have to use this session to make the go infrastructure work? This is defeating the purpose of the go infrastructure." Work the thread agent reads in the owner's message that no running session covers (no `hand_to`) is designed before any session starts on it:

- The item opens `designing`, and the owner's message waits on it, saying so. Go runs the **designer**: one headless `claude -p` (`jobs.designer`: `model`, by default the strongest of `policies.models`' work, reviewer and judge models, fable over opus over sonnet over haiku, else `opus`; `max_input`, default 64 KiB; `timeout`, default 15 minutes; `off: true` turns the step off and work starts as #65 starts it). It is given the owner's words and files, the thread, the running and finished sessions, the cards and the issues a thread agent is given, and the agent's reading of the work; it reads the clone with Read, Grep and Glob and agentd's `state`, `find`, `history` and `ask_expert`.
- It writes the brief in the owner's briefs' shape: what exists and is reused (with paths), what is missing, the design (numbered), where it runs, out of scope, and acceptance; its open questions; `done_when`, which replaces the agent's; and a rating of what the change touches (production, deployment, spend). Go quotes the owner's words as what was asked. What every round cost is logged on the item.
- The item is then `designed`, and the brief is the design entry `b:ID` on the console: **go**, **change** (the owner's words, alone or with the choice, go back to the designer for one more round, given the design before; three rounds in all) or **decline** (nothing starts, and the owner's message is answered). A designer that fails is run again after two minutes; after two failures the entry offers the same answers with the agent's brief standing in, or, when a later round failed, the earlier design marked as not answering the change. Words with no choice after the go go to the item's session.
- `repositories.NAME.policy.design.auto: true` lets a design go on without the go when Go finds it contained: it touches no production, deploys nothing, spends no more than `design.spend_limit_usd` (default 0), and its `done_when` is neither a url check (work out in the world) nor the owner's word. The design is still posted, answered by agentd, and the owner is told. A repository's own file may only turn `design.auto` off or lower the limit, and one agentd cannot read turns it off. The rating is the designer's, who read issues and files others may write: set `design.auto` only where those are trusted, since the work then starts with no one having read its brief.
- The designer may take 40 model turns, since it reads the code first. Its input is cut to `max_input` with the thread last; a later round is given the earlier design's brief, questions and `done_when`.
- On go, the item is assigned as any other (#66): Go starts its work session, whose BRIEF.md is the design, its Questions the designer's, then how agentd tracks the item; the owner's message goes to it, and its reply answers it. A reviewer or judge Go starts for that session's branch is given the design as `standard` in its facts, to review against.

Work handed to a running session is that session's to design, and goes to it as before.

**Go keeps its own room.** A start that finds its repository at `sessions.max` (a work session for the owner's work or an item, the loop's next case, a reviewer or judge) ends a finished session agentd started there, the oldest first: a work session that wrote DONE, its deliveries made (or refused, with the reason), or that stopped, crash-looped or was parked with at least one request delivered, and every request it delivered merged or closed; with no open work item and no message routed to it and not yet delivered. The loop's next case, one place short of the place it keeps for judgment sessions, makes room the same way. The end carries why, and the console is told which session went and for what. A session at work, one whose request is still open (its fix rounds are its own), a reviewer or judge, and a chat session are never ended for room; when every place is held so, the start is refused and the owner told, as before.

## The operations console (#63)

The owner asked for "a way to talk to an AI to manage the whole go infrastructure." The console named by `ops.console` is that: a message there goes to the **ops agent**, a thread agent (#59) like the others, short-lived, one `claude -p` per message with the thread so far, reading in `ops.repo` with Read, Grep and Glob. As it starts, Go reads it the live facts (#62): each supervisor, up or down (its tmux pane runs agentd or not), its sessions by state, or why its config does not load; each account's plan usage; the installed binary's commit (as Go stamped it) against the clone's `origin/main`; and the latest ten changes with where each stands. Its tools, on `agentd mcp --ops`, are its own: it is given neither the repositories' context tools nor any shell, and only `ask_expert` besides.

The reads need no approval:
- `ops_status`: each supervisor's `agentd status` table as JSON, whether its process is up, which is this one, the installed and main commits, and the kept binaries.
- `ops_accounts`: each account's plan usage, read now, once per account name across the supervisors' configs.
- `ops_config`: a supervisor's resolved config as `agentd config` prints it, every key that names a token, secret, password, credential or `config_dir` redacted, and every string matching a confidential pattern withheld.
- `ops_tail`: the last N lines (at most 200) of a supervisor's tmux pane, each line naming a credential's key cut and each matching a confidential pattern withheld.
- `ops_events`: the last N events (at most 50) of a kind in a supervisor's log, each as JSON cut at 2 KiB, withheld whole on a match.

The change tools only propose. Each checks the change, records it in the ops-serving log as an `ops` event (`proposed`, id `o…`), and answers with its entry, `o:ID`; the same change while one waits is not proposed twice. The console shows each as a yes-or-no decision entry with the exact change:
- `ops_config_set`: a JSON-pointer (RFC 6901) set or delete on one supervisor's config file. The edit is made in the file's text, so every other line stays as written, and checked to mean exactly that change on the decoded document. The result must pass the check `agentd config` makes (written beside the file, so relative paths resolve as its own, and loaded); one that does not is never proposed. The entry shows the unified diff. A pointer through a credential's key is refused.
- `ops_restart`: a supervisor, in its tmux session, the owner's way: Ctrl-C, then, once the pane no longer runs agentd, Up, and Enter only when the line Up recalled runs agentd (else the line is cleared and nothing is run). A supervisor that is down beyond doubt when it is proposed (its pane is there and runs a shell) is restarted without a yes, if it still is when agentd comes to it; the process serving the console never is.
- `ops_install`: a commit on the clone's `ops.branch` (by default `main`; fetched; it must be an ancestor of `origin/BRANCH`); the entry lists the commits it brings over the installed one.
- `ops_clear` and `ops_end`: `agentd clear` and `agentd sessions end` on a supervisor's session.
- `ops_rollback`: back to a kept binary, `agentd.SHA` beside the installed one.

Go carries a change out only when the owner answers yes on its own entry, from the page: the answer is the owner's instruction carrying the entry, which Go filled from the log, so a yes is to that change and no other. Words alone go to the ops agent and settle nothing; a second answer is refused. The run serving the console carries out one change at a time, in the order proposed: it logs `started` before anything is done, so a change is never done twice; then the change, from what the log recorded, checked again against the files as they are now; then `done`, `failed` or, on a no, `declined`, with the outcome, which also answers the owner's yes under the entry.
- A config set is written only on the file the diff was shown against (by its hash), as the same edit (by the result's hash), after the check again; the old file is kept as `FILE.bak-ops-YYYYMMDDTHHMMSSZ`, the new one renamed over it; then every supervisor that runs the file is restarted. One that fails the check now is not written.
- An install builds the commit in a clone of its own that shares the clone's objects (so the clone's checkout and worktrees are untouched, and Go stamps the commit), keeps the installed binary as `agentd.SHA` (`agentd.unknown-HASH` when it names no commit), swaps the new one in with one rename, runs `agentd config` with it on every supervisor's config, and restarts every supervisor. On any failure, a config the new binary refuses or a supervisor that does not come up on it, the kept binary is put back and the supervisors already restarted are restarted on it. A rollback is the same swap from a kept binary.
- The process serving the console restarts itself last, from a process of its own session that outlives the Ctrl-C it sends; it logs `started` again with what it did, and the next agentd there reports the change done once it is up, on its commit. While it restarts itself it starts no other change. After an install or rollback, when the pane does not run agentd a minute after the restart, that process puts the kept binary back and starts it again. The swap is logged as it is made (`swapped`), so a change any other way left started is reported cut short, with the kept binary put back when it had swapped one, and never carried out again. A binary kept from before #63 does not know the `ops` key, so `agentd config` with it fails and a rollback to it is put back.
- Who may answer: the yes is taken only from the page (`from: "ui"`), in the ops console, on the change's own entry, unwithheld. The page and the log are the owner's, but any program running as the owner can reach both, a session's agent with a shell among them; run work sessions under another user, or not on this host, where that matters.

**Go installs itself (#68).** With `ops.watch` naming a configured repository (its forge and project), the run serving the console fetches `ops.branch` (by default `main`, into `origin/BRANCH`, a `--single-branch` clone too) every `poll.ci_every` and looks at its tip. When the forge reports that commit's CI green (every GitHub check run completed as success, neutral or skipped, or with no check runs its combined status a success; the GitLab commit's last pipeline a success), the tip is ahead of the installed commit, and it is neither installed nor proposed yet, Go proposes its install itself, as `ops_install` would, and says so on the ops console. With `ops.auto_install: true` the install needs no yes while that setting holds: it is carried out at the next pass like any install, the old binary kept and put back when `agentd config` or a restart fails, and the ops console is told what was installed and what changed (the commits it brought), or why it was put back, the self-restart's included. Turned off, a proposal made under it waits on a yes. No proposal is made while an install is under way, an install of the commit already installed does nothing, and a tip once proposed is not proposed again, whatever came of it. A watch that cannot fetch or ask the forge logs an error, once until the reason changes. A binary from before #68 does not know these keys, so `agentd config` with it fails on a config that sets them, and a rollback to one is put back.

## Owner answers

A session asks the owner in two ways. Every running session writes its questions under Questions in STATUS.md, and that keeps working: the section is one decision of type `text`, its id `status-` and a hash of the section, so a reworded section is a new question. A session may also raise decisions in `questions.json` in its workdir, in #3's `raise_decision` shape: `{"decisions":[...]}`, each with an `id` (letters, digits, `-` and `_`, at most 32, and not `D` or `R` and a number, which agentd gives raised decisions and the owner's rulings), a `type`, the `question`, its `context`, `why`, `if_wrong` and `recommendation`, for a `choose_one` or `choose_many` the `options` (each a `key`, `label` and `consequence`), optional `limits`, `default` and `deadline`, and `blocking`, as for `raise_decision` (see *Case tools*). The file is read only as a regular file, never through a link, and at most 64 KiB. Each field has a length limit, and a file that breaks a rule is refused whole and logged once (the decisions read before stand). A changed file is a `decision` event, so a replay rebuilds what was raised. Its words are screened against `confidential_patterns` first: a decision that matches is logged by its id, type, option keys and whether it blocks, and the UI shows it without a form, so the owner answers it from the session itself.

The owner answers in the UI, under Needs you, below each decision (what is true today, why it came up, what breaks if the call is wrong, the recommendation): `answer` (`true` or `false`) for a `yes_no`, `choice` (an option's key) for a `choose_one`, `choices` (distinct keys, as many as its limits allow) for a `choose_many`, `value` (a number, or a date `YYYY-MM-DD`, within its limits) for a `number` or a `date`, `text` for a `text`, or, for every type but `text`, `other`, the owner's own words instead, which is delivered but does not settle the decision. A decision's default is applied only when the owner sets a deadline on it on the UI (a `deadline` event, mode `owner`, bound to the decision as it was asked) and that deadline passes with no answer: `agentd` then records the default as the answer, an `answer` event of the run's mode marked `by_default`, with the note `the default, applied at the owner's deadline`, and delivers it as any other. The session's own `deadline` is only shown as a suggestion. A question with no owner deadline is never decided for the owner. STATUS.md's Questions are shown as the file holds them now, and offered for an answer only while they are the section `agentd` last read, so an answer is to the text the owner read. The answer is checked against the decision as the log holds it and recorded as an `answer` event, mode `owner`, keyed by the decision id, with the address it came from and a hash of the decision as it stood. A decision reworded since, or an id raised again for another question, no longer has that answer and waits for the owner again. A blocking decision, or STATUS.md's Questions as they stand, no longer holds the session as `blocked-on-owner` once it has a binding answer, or any answer not yet delivered; an answer in the owner's own words holds it again once delivered. Answers are owner events, so one given through the UI's shadow source is delivered by a live run too.

In live mode `agentd` writes every answer to the session's open decisions to `answers.json` in its workdir, `{"answers":[...]}` in the same shape, through a temporary file renamed over it, then types `policies.answers.pointer`, one fixed line pointing at the file, through the typing safeguards and only into a session that can take a line (working, idle, or waiting on its own questions; never one showing a dialog, the trust prompt or the usage limit). The answer itself is never typed. At most one line is typed into a session per pass, so the pointer waits a pass after a resume, and an idle session is not nudged in the pass its pointer is typed. A file that cannot be written is tried again on the restart backoff, and a delivery cut short by a crash of `agentd` is made again. A session that is gone with answers waiting is restarted, once the file is written, with the pointer line in its prompt and the file's path in its facts; every later fresh session's facts name the file too. Each answer is delivered once: a delivery marks the answers it carried, by decision and the time each was given, so a replay delivers nothing again and an answer given meanwhile is still delivered. Shadow mode records the answers and the delivery it would make, and writes and types nothing.

## Consoles

With `policies.feed.enabled` (off by default), each repository's console receives a plain line for each thing the UI shows of that repository: a decision a session raised that does not block, each settled CI result of a delivered request's head (`success`, `failed`, `merged` or `closed`), each delivery, each merge `agentd` made (not one cut short, whose outcome is unknown; its request's CI record saying `merged` is not a second line, unless the CI watcher saw the merge before the merge's own outcome was logged), and each new item of that repository not yet seen. A blocking decision, and STATUS.md's Questions, are in the session's escalation, which goes to the same console, and are not fed again. The line goes through `policies.escalate.command`, when it is set, with `{console}` the repository's `console` (else its name) and `{message}` the line. Each line has a key that stays the same however often the state lists it, and is posted once: a `feed` event (no session, the run's mode) records the intent, then `posted`, `failed` or `gave-up`, or in shadow mode `would`, so a restart does not post it again. An intent with no outcome counts as posted, as an escalation's does: a post cut short by a crash or a stop, or whose failure could not be logged, is not made again, and nothing warns of it. A failed post is tried again on the restart backoff, `max_restarts` times. A pass posts at most 10 lines, and the rest follow in later passes. The first pass that feeds a repository records a `baseline` of its lines already there and posts none of them: when the feed is turned on, when a repository is configured later, or taken out and put back, and when the feed is turned on again after it was off (a `paused` event records once that the feed was off, or which repositories left). Each line is screened against `confidential_patterns` before it is posted or logged, then its text is cut so the line, with the reply it ends with whole, is at most 1000 bytes; a match posts a line naming only the repository, and the event records the pattern's number, not the text.

The owner replies in a console through `agentd console reply CONSOLE TEXT...`, which the console's tool runs with the reply (`--shadow` answers the shadow run's decisions). `SESSION ID ANSWER` answers a decision, read by its type: `yes` or `no`, an option's key, keys separated by commas, a number or date, or text; `other: ...` gives the owner's own words. A fed decision's line ends with the reply to type, its id written `ID@VERSION`: a reply to such a decision without a version, or naming one the decision no longer has, reworded or raised again since, is refused, so a late reply cannot answer another question. A blocking decision's escalation shows its id but not its version or option keys; it is best answered on the UI. `seen ID...` marks items seen. The reply goes through the same checks and records as the UI's `POST`, from `console:CONSOLE`, so it is an owner event that wakes a running `agentd` within the wake check. A reply is refused unless the session's, or the item's, repository feeds that console, so one repository's console cannot answer for another.

Any other reply is an owner instruction for the repositories that console feeds: a `seen` naming no known item, or words that do not begin with a session and one of its decisions or a word like a decision's id (`D3`, `R1@…`). A `seen` naming some known items and some unknown, or an answer with an unknown decision, stays an error. The instruction is an owner event (`instruction`, id `I…`, from `console:CONSOLE`), screened with the confidential patterns (its text, and its hash, left out when one matches); each reply is recorded, the same words twice too. agentd routes it (#56, *The console chat* below); `agentd console inbox` still reads it. A reply in a console under `consoles` is an instruction with that `console` and no repositories, delivered only when it addresses one of that console's sessions. Any other console that feeds no repository takes no instruction. The console's tool is expected to run `agentd console reply` for every owner reply; its own inbox stays readable as before.

Sessions post to a console, and read the owner's replies there, through `agentd` itself, so no outside console program is needed (#42). Both write to the log of the configuration given with `--config` (the default as for every command), so the old command names can point at the configuration the UI serves.

- `agentd console post [--kind KIND] [--from NAME] [--to SESSION] CONSOLE TEXT...|-` records a `message` event (mode shared, no session): an id `M…`, the console, the kind (`info` by default, `decision`, `delivered`, `ci` or `finished`), the author (`--from`, by default the name of the tmux session it runs in, else `cli`) and the text, Markdown, at most 16 KiB; `-` reads it from standard input. CONSOLE is a repository's console (its `console` key, else its name) or one under `consoles`; any other is refused. The text and author are screened with the confidential patterns: on a match both are left out and the event records the pattern's number, and the UI shows the post withheld. `--to SESSION` also types the text into that tmux session first, as one line (line breaks and tabs become spaces; any other control character is refused), by its exact name, with a nudge's checks: the session exists, its pane runs one of `policies.pane_commands`, and its screen shows no dialog (a `policies.dialog` pattern or a dialog's shape); a refusal records nothing. The event says it was typed.
- Session turns (#38): each prompt a session is given (the owner's or agentd's) and the text it ends a turn with, read from its transcript, is posted to the session's console as a `message` event of kind `prompt` or `reply`, from the session, with an id `T…` made from the session, transcript and line. It is posted right after its `turn` event, which is logged once by its line, so a restart posts none again (a crash between the two loses that post; it never repeats it). The text is the turn as read from the transcript (at most 20 KiB, so a prompt is posted whole though its `turn` event keeps 300 bytes), screened whole with the confidential patterns (with the session's name), then cut at `policies.feed.turn_length` bytes (16 KiB by default, the whole reply as logged; 40 to 20480). The page shows a message, reply or turn longer than 1200 bytes up to a line break near there, with "Show all" unfolding the rest; a match posts it without its text, still from the session. A turn read more than an hour after it was written (from a transcript agentd reads for the first time, of a session it did not launch, or written while agentd was stopped for longer), or with no time, is logged but not posted, so a backlog does not flood the console. The console keeps the latest 200 turns apart from its other messages, so turns never push those out. Which turns are posted is `policy.feed.turns`: `all`, `prompts` (prompts only) or `off`, set on a session (`sessions.NAME.policy.feed.turns`), else on its repository (`repositories.REPO.policy.feed.turns`), else `all`. This does not depend on `policies.feed.enabled` and runs no command: the UI shows the turns. A shadow run posts none, since the live run posts the same turns, and a session whose console no repository or `consoles` entry has posts none.
- `agentd console inbox [--from NAME] CONSOLE` prints the owner's instructions for that console that this reader (`--from`, as above) has not read, oldest first, one compact JSON object a line (`id`, `text` or `withheld`, `from`, `at`), and records them read with one `inbox` event naming their ids, so a second call prints nothing. A reply that answers a decision or marks items seen is not an instruction and is not printed: it reaches the session through its answers file, as it always has. Each reader has its own reading.
- `agentd console import` also reads the outside console program's lines: `ts` (Unix seconds, fractional), `from`, `kind`, `text` and `to` (the session a line posted with `--to` was typed to, kept on the imported line); their other fields, such as `edited`, are ignored; a line's `repository`, or `--repository`, may name a console under `consoles`.

## Cases

A case is one issue. A session names its issue with `issue` (the number in its `repository`), and its case id is the issue item's id: forge, project and number, such as `gitlab/example-org/widgets#17`. The case is a projection of the event log, never a separate store. A `case` event carries exactly one of:

- **pack:** the facts document a restart or rotation handed the session, as compact JSON, with its hash;
- **report:** what the session's STATUS.md table says (the current item, its state, the next items), logged when it changes;
- **ruling:** the owner's one-shot restriction or waiver (`R1`, `R2`… for the case's life, kept verbatim), or the case closed or reopened. Closing expires the case's restrictions and waivers.
- **goal:** the issue's done-when items, recorded by the owner with `agentd cases goal CASE FILE` (`-` reads standard input) from the list under the body's "Done when" heading. Items are `A1`, `A2`… for the case's life: recording the goal again keeps an unchanged item's id, gives an edited one the next id and marks the old one superseded. Every item is the owner's to judge for now;
- **call:** a session's call of one of its case tools, accepted or refused with why (see *Case tools*). A call is a shared fact, read by the live and the shadow run.

The state comes from facts, never from the report, and from the sessions that name the case now (a session moved to another issue stays listed but no longer speaks for it): closed by the owner; needs you while a session waits on the owner or is parked; stopped by the budget; delivered once a session's work went out; working; or not started, which includes issue items no session works yet.

`agentd cases [--json] [--shadow]` prints the cases ranked (for the live run, or the shadow run's with `--shadow`): the owner's pins first, then what needs the owner, then the repository's priority this week, then triage urgency, the oldest waiting and the id; closed cases last. Pins and priorities come from `tracking.priorities`, the weekly review's file: `{"week":"2026-W43","repositories":[{"repository":"gitlab/example-org/widgets","priority":1}],"pins":["gitlab/example-org/widgets#17"]}`. A field agentd does not know refuses the file; without the file the ranking has no pins and no repository order. `agentd cases rule CASE restriction|waiver|close|reopen [TEXT]` records a ruling; a close's text is the demo line, saying how to see the change working, or `N/A: reason` (see *Review rounds*).

### Case tools

A session that works a case reports through tools, not prose. `agentd mcp --session NAME` serves them over MCP on standard input and output, bound to that session's case; the restart command's `{mcp}` starts it for every session agentd launches, and the fresh session's facts name the tools, the current done-when items and the active rulings with their text. A call never names a case, and an argument the tool does not take is refused, so one session's server cannot write another's case. That binding is against mistakes, not against the session: a session with a shell can read its own `--mcp-config` and start `agentd mcp` for another session, as it can write the event log, so the server is not a security boundary between sessions run as one user.

- `report_progress(summary, approach, items[{id, status, evidence[]}], next_action, risks[], acknowledged[], goal_restatement[{id, text}])`: item ids must be the case's current ones; a status is `not_started`, `in_progress` or `met`, and `met` needs evidence. Evidence is a typed reference agentd checks, never prose: `{"kind":"commit","sha"}` on the session's branch, `{"kind":"gate","sha"}` where a gate agentd ran passed, `{"kind":"file","path","line"}` inside the worktree. `{"kind":"finding","id"}` names a review finding of the case that has its disposition. `ci` references are refused until agentd records CI results for evidence. Every active restriction and waiver the session has not acknowledged since its launch must be in `acknowledged`: a launch is a fresh context, so its first report acknowledges them all again. An evidence reference carries only its kind's fields. The restatement is compared with the goal: an item left out or worded otherwise is a drift flag on the case, and the report is still accepted.
- `raise_decision(type, question, context, why, if_wrong, recommendation, options[{key, label, consequence}], limits, default, deadline, blocking, supersedes)`: a decision for the owner, which `agentd` numbers `D1`, `D2`… for the session and replies with its id. `type` is the narrowest that fits: `yes_no`, `choose_one`, `choose_many`, `number`, `date`, or `text` only when the answers cannot be listed. A question wider than it needs is refused with the type to use: a `text` that names its own options (`(a)`, `b)`…) or asks yes or no, a `choose_one` or `choose_many` of only yes and no, or of one option. `limits` is `{min, max}`: numbers for a `number`, dates `YYYY-MM-DD` for a `date`, counts of keys for a `choose_many`. `default` is a string: `yes` or `no`, a key, keys joined by commas, a number or a date, and it must be an answer the decision takes. A question the same as one the session has open is refused. An answer in the owner's own words keeps the decision open: the session raises it again with `supersedes` naming it, which closes the old one. The decision joins the session's open decisions and is answered and delivered as those of `questions.json` are (see *Owner answers*); the case record keeps every raised decision, the superseded too.
- `request_step(kind)`: `review`, `delivery` or `stop`. The request is recorded with the facts (for delivery, whether a gate agentd ran passed on HEAD) and never moves the case.

A refused call is logged with the wording of why, the session's values left out, and its arguments' hash; its reply says what to fix, values included. A call of a tool the server does not have, or a message it cannot read (over 1 MiB, or not JSON-RPC), is answered as a protocol error and not logged, since nothing reached the case. `agentd cases` shows the latest accepted report beside the facts, with its drift; the item from STATUS.md stays as a fallback for a session without the server, marked unverified.

### Review rounds

Reviewers advise; one party decides. A session configured with `"role": "reviewer"` is offered only `review_findings`, and one with `"role": "judge"` `judge_dispositions` and `raise_decision`; both need the case they serve (a repository and an issue). Each call is a case event, so the rounds are part of the case record. Two reviewers' calls checked against the same round both reach the log, but only the first opens the round; the other is told nothing of it was recorded.

- `review_findings(findings[{id, title, severity, items[], widens_scope, paths[], consequence, suggestion}])`: one call is one round, refused while the last round awaits its dispositions. agentd numbers a new finding `F1`, `F2`… over the case's life. A finding that comes back keeps its id: the reviewer names it (the facts list every finding with its id, its disposition and the judge's latest plan), or gives it again with the same paths and a title like its own. An id the case does not have, or one given twice, is refused. Each finding names the done-when items it bears on, or sets `widens_scope`.
- `judge_dispositions(dispositions[{finding_id, disposition, reason}], plan[{id, step}], lessons[])`: one disposition, `adopt`, `decline` or `defer`, with a reason, for each finding of the latest round, once a round. A finding that widens the scope cannot be adopted: the judge defers it and asks the owner with `raise_decision`.

A round that brings no new findings stops the loop: `converged` when it had none at all, `repeating` when every finding came back. A finding given in three rounds in a row since the last reset also stops it as `repeating`, though the round brought something new. A loop still finding new things stops at the backstop: `policies.rounds.max` rounds (default 3), or the count the owner set with `agentd cases rounds CASE N`, which also resets a stopped loop and counts from there. Reopening a case resets it too; nothing else does; a stopped loop takes no more reviews, and `repeating` and `backstop` mean the case needs the owner. Every stop proposes lessons: the judges' since the last reset and, at a park, what the facts show. `agentd cases` shows the round, the findings awaiting the judge, the stop and the lessons; agentd writes nothing into the repository.

A close is refused while a finding has no disposition. It records each current done-when item as `machine` (an item the owner confirmed machine-checkable; met when its latest report met it with checked evidence) or `owner`, the demo line or N/A with its reason, and every lesson the rounds proposed.

The facts of a fresh session carry the findings and the plan, never the case's progress reports: a reviewer sees the work, not the worker's account of it.

## The request loop

A repository with a `sessions` entry has its request loop run by `agentd` itself, in Go, the same way every time (#53); Claude is called only for bounded judgment sessions. Each pass, every open request of the repository, delivered by one of its sessions or listed by the CI watcher with no session behind it, is carried one step on, once it is in the loop:

- **Who is in the loop (#55).** A request enters only when it is no draft, its target is one of `merge.targets`, its author is in `merge.authors` (or `review.others` is `review-only` and the forge says it was updated within `review.others_max_age`, default 14 days), and its number is in neither `merge.exclude.numbers` nor `scope.reserved.numbers` (a reserved number is matched against the request's number, though GitLab numbers issues and merge requests apart). The number is matched against the policy narrowed by every target's file; the rest against the policy for the request's own target, as its merge reads it. This holds for delivered requests and those no session delivered alike, and is judged again every pass: a draft enters the pass after it leaves draft, and a request that leaves the loop has its reviewer or judge ended, as one merged or closed does. A request whose head the watcher has not yet recorded is in and waits for it; so is one whose last answer was a forge error, which starts nothing and shows as waiting for CI until the next answer. A request by another author whose last update the watcher has not recorded, as in a record an earlier version wrote, is held as `update unknown`: no step starts for it, and its reviewer or judge is not ended, until the watcher's next answer records the time. A request outside the loop is still watched for CI; nothing else is done with it, and `agentd status` lists it once as `loop REPO REF: outside the loop (WHY)`, WHY being `draft`, `target`, `author`, `stale`, `excluded` or `update unknown`. `agentd status` judges `stale` at its own clock, as the live loop judges it at its pass, since crossing the age writes no event.
- **Review.** When the request's head has not been reviewed for the next round, `agentd` starts a reviewer (`kind` `reviewer`, `policies.models.reviewer`), named and provisioned as a started session is, for the request's branch (`request-N` when no session's branch names it), detached. Its facts carry `review`: the request, its url, the head to check out and the target. Its `review_findings` round is recorded in the request's case: the work session's issue, or, for a request no session delivered, its own case `REPO!N` (GitLab) or `REPO#N` (GitHub). Once the round is recorded, `agentd` ends the reviewer.
- **Judge.** A round with findings starts a judge (`policies.models.judge`), which disposes each finding with `judge_dispositions` or asks the owner with `raise_decision`; the request then waits for the owner, and the answer reaches the judge as any answer reaches its session. Once the round is disposed, `agentd` ends the judge.
- **Fix round.** A disposed round that adopted a finding relaunches the work session, once it is done or idle, with a `fix-round` action: its STATUS.md loses its DONE, its facts carry the rounds (the findings with their dispositions and the plan), and its prompt says to fix the adopted ones on the same branch. Its next delivery pushes the new commits to the open request, as a CI fix's does; the new head is reviewed as the next round. A fix round that delivers no new commit waits for the owner. A round that adopted nothing is reviewed again at the same head: the reviewer sees the dispositions, and findings that come back stop the rounds as `repeating`, for the owner, since reviewer and judge disagree. A request no session delivered has no work session: adopted findings there wait for the owner.
- **Merge.** Review rounds that stop `converged` hand the request to *Merge when green*; in such a repository `review` is required of every request, whatever `merge.require` says. For a request no session delivered, `agentd` records its approval at the head the converged round reviewed (a `loop` event with step `approve`). Review counts only for the head the converged round reviewed: a head that moved since, by a CI fix or the request's author, is not merged and waits for the owner, whose `agentd cases rounds CASE N` reviews it. `repeating` and `backstop` wait for the owner, as in *Review rounds*.
- **A failed judgment session.** A reviewer or judge that is stopped (its spend cap or the stop time), crash-loops, fails, finishes without its call, or is ended before it makes it fails its step: a `loop` event with step `failed` and the reason, the session ended, and one escalation to the repository's console for each failure. A reviewer or judge that asked the owner waits for the answer instead, DONE or not; while it waits it holds its place under `sessions.max`. A reviewer or judge whose request left the loop, merged or closed by hand, or whose case was closed, is ended. Its brief tells a judgment session to make its call before it writes DONE. Only that request waits; the rest of the repository's loop goes on. `agentd loop retry REPOSITORY REQUEST` is the owner's record that takes the step again. `agentd loop skip REPOSITORY REQUEST` takes a failed review as clean: its round counts as reviewed with no findings, and the request goes on as converged at the head that review was of, through CI to the merge by policy. `agentd loop stop REPOSITORY REQUEST` leaves the request alone, its reviewer or judge ended, until a retry takes it up again. The request's card on its issue page, or on the repository page when no listed issue shows it, offers the same three, each written by the same function as the command (#69). Caps are the sessions' own budgets.
- **What to start next.** Where a looped repository runs fewer started sessions than its `sessions.max`, `agentd` starts one work session a pass on the top case of the `agentd cases` ranking that the owner queued, meaning pinned, or in a repository the week's priorities list (`tracking.priorities`): an issue not reserved by the policy's `scope.reserved`, with no session and not started, on branch `issue-N`. A looped repository's `sessions.max` is 2 or more, and one place under it is kept for the judgment sessions the work asks for. A work session `agentd` started is ended once every request it delivered is merged or closed, so its place goes to the next case.

Every step is a `loop` event (repository, request, case, head, step, session, round, reason); where a request stands is worked out each pass from those events, its case's rounds, its CI record and its judgment sessions, so a replay agrees and `agentd status` shows, for each request, `loop REPO REF: PLACE (reason)`, where PLACE is reviewing, judging, fixing, waiting for CI, merging, waiting for the owner, or outside the loop. Shadow mode records the review or judge it would start and starts nothing. Judgment sessions are counted in `sessions.max`; a step with no room waits, with one skip for each round saying so.

## Publishing

`agentd report --out PATH` writes the report the tracking site publishes, rebuilt from the event log alone. It is JSON: `schema` (`agentd-report/1`), `written_at`, `host` (this machine's name, or `--host`), `mode`, `repositories`, and two one-line digests: `digest` counts only what anyone may see, `owner_digest` counts everything and is for the owner. Each repository, keyed `platform/path` as in the tracking manifest, holds its `cases` (each configured session's state, since when, and its STATUS.md first line), its `deliveries` (requests opened, found already open or merged, or recorded with `mark-delivered`, each filed under the repository it went to), its `questions` (each session's open Questions, the STATUS.md text as last posted to the owner) and its `items`, the new items (see New items): each one's id, kind, title, link, when it happened and was first seen, whether the owner saw it, and its triage's needs, urgency and summary while the triage holds for its text, and nothing else (not who wrote it). An item stays until the owner has seen it and seven days have passed since it was first seen. Mail findings with no single repository are grouped under an empty `repository`. Every entry carries `owner_only`: questions always, everything derived from mail always, items of a repository `agentd` is not configured for (the site cannot tell who may see them), every entry of a repository with `owner_only` set, and sessions that name no repository, grouped under an empty `repository`. A repository whose every entry is for the owner only is marked `owner_only` itself, and repositories that share a forge and project share their entry, which is `owner_only` when any of them is and left out whole when any of their names matches a confidential pattern. Sessions no longer in the configuration are not reported. The report is for one mode, `live` by default or `--shadow`, read as a run of that mode replays the log, so a live report never shows what a shadow run only would have done; a shadow report lists the requests it would have opened as `would-open`. Every text is screened against `confidential_patterns` as they are when the report is written, so a pattern added later still applies to old events: a matching first line is left out, a question, delivery, item, session or repository whose text or name matches is left out whole, and a question whose text was withheld when it was posted is left out. The file is written to a temporary file beside it, synced and renamed over it, so the site never reads half a report; it is readable by its owner only.

## Tests

```bash
./bin/check
```

`bin/check` runs `gofmt -l`, `go vet` and `go test -race`, and fails when Go is missing rather than passing without it. CI runs the same script on every push.

The tests run the supervisor against a fake tmux, forge, git and clock over simulated hours. Each failure the old tools showed is a test: a crash loop parks for the owner and escalates once; a session blocked on the owner is not nudged; an escalation is posted once, and reworded Questions are updates to it; nothing is killed but a rotation, a budget stop or an ended session; shadow mode never acts.
